Model Training

Updated: 2026-08-27 scikit-learn MLPRegressor LightGBM Ranker 4 horizons CS v2 active

Overview

GrowMyStocks runs two parallel prediction paths for every ticker. The per-ticker MLP path fits a fresh model on each stock's own history — flexible but slow. The cross-sectional (CS) path trains one model across the entire universe, enabling transfer learning where tickers with sparse history still get informed predictions.

The CS model is the primary path today; the per-ticker MLP is the fallback when the CS artifact is missing or fails to load. A third model — the LightGBM ranker — scores relative attractiveness across the universe and powers the Discovery feed.

Cross-Sectional (CS) — Primary Path

  • Trained once on all stocks simultaneously
  • Stored in models/long_term_cs_v2.pkl
  • Loaded once at Python process start
  • ~292 survivor tickers + 120 sector leaders in training set
  • Direction accuracy is the headline quality metric

Per-Ticker MLP — Fallback Path

  • Fit on each stock's own historical sequence
  • No stored artifact — trained live per prediction request
  • 45-day lookback window (SEQ_LEN = 45)
  • 50 epochs (N_EPOCHS = 50), seed 42
  • Used when CS model artifact is absent or corrupt

Prediction Horizons

The pipeline is split into two horizon groups, each with its own model file and feature mask. Splitting avoids the short-horizon noise contaminating the long-horizon model and vice versa.

The 1y output is not a trained model head — it is extrapolated from the 6m prediction using the trajectory builder in predict_core.py. This avoids requiring 252+ days of forward data for training labels.

Training Pipeline

The full training cycle has five stages. Each stage produces an artifact consumed by the next.

📡 Raw Data yfinance OHLCV + macro ETFs
🏗️ Build Dataset build_ranking_dataset.py
🏷️ Extend Labels extend_long_term_labels.py
🧠 Train CS Model train_long_term_cs.py
🏆 Gate & Promote retrain_pipeline.py
🚀 Inference predict_weighted_analysis.py

Stage Details

Stage 1 — Build Ranking Dataset (build_ranking_dataset.py)

Pulls historical OHLCV + macro data via yfinance for all tickers over a trailing window. For each snapshot date D and each ticker, computes the GREEN feature vector using only data available as-of D. Writes rows to ranking_training_snapshots table. Also computes the 20-day forward return label for the ranker.

  • Snapshot cadence: weekly or monthly (--cadence)
  • Default window: configurable via --start / --end
  • Idempotent: skips dates already in the table
  • No-leakage constraint: only data at or before date D is used

Stage 2 — Extend Long-Term Labels (extend_long_term_labels.py)

Adds forward_return_63d and forward_return_126d columns to ranking_training_snapshots. Computes them from per-ticker price history (one yfinance pull per ticker, cached). Recent rows can't have labels yet (the future hasn't happened) — those stay NULL and are excluded from training.

Stage 3 — Train CS Model (train_long_term_cs.py)

Reads resolved-label rows from ranking_training_snapshots, time-splits 80/20 by date (not random split — avoids future leakage), trains a 2-output MLPRegressor on [return_63d, return_126d], fits a StandardScaler, and persists models/long_term_cs_v2.pkl + models/long_term_cs_v2_manifest.json.

Time split: train on dates < 80th percentile date
            val   on dates ≥ 80th percentile date
This is critical: random split would leak future patterns into training.

MLP Architecture

Both horizon-specific models use scikit-learn MLPRegressor. The long-term model has wider hidden layers because 3m/6m predictions need to integrate more disparate signals (macro + fundamentals + long-horizon momentum). The short-term model is intentionally smaller — its feature mask is roughly half the column count, so the same effective capacity-per-feature is maintained at lower compute cost.

Cross-Sectional (CS) Model

The CS model is the key architectural innovation over the per-ticker approach. By training across all tickers simultaneously, the model learns cross-stock patterns (sector rotation, macro sensitivity clusters) that a per-ticker model can never see.

How it differs from per-ticker training

Per-Ticker MLP (legacy)

  • Trains on one stock's 45-day window sequences
  • Only sees that stock's own history
  • Data-sparse tickers (IPOs, thin history) get poor fits
  • No transfer learning across sectors
  • ~13 min for full universe backtest

Cross-Sectional CS v2 (current)

  • Trained on all tickers' snapshots together
  • Sector one-hot encoding enables cross-sector learning
  • Sparse-history tickers benefit from universe patterns
  • Single model artifact loaded once — faster inference
  • Time-split validation guards against future leakage

Direction Classifier Head (CS v2)

CS v2 added a LogisticRegression classifier head trained on non-neutral rows (rows where the 63d forward return is outside ±2% deadband). It outputs direction_confidence_1w (probability of up move) and direction_signal_1w ('up'/'down'/null). A conviction gate at 0.55/0.45 threshold filters weak signals to null.

The direction classifier is the primary driver of the direction accuracy metric — the headline number tracked in backtests and displayed on the dashboard.

Regime Detector

Before predictions are made, a Gaussian Mixture Model (GMM) classifies the current market regime. The regime then modulates how aggressively the model extrapolates trends. A bull regime boosts confidence; a bear regime dampens long-term price targets.

GMM Configuration

  • K = 3 or 4 components (selected by BIC)
  • Features: VIX level, SPY 30d return, credit spread, yield curve slope
  • Dirichlet smoothing α=0.05 — prevents literal 100% probability claims
  • Rebuilt per-prediction from trailing macro window

How Regime Affects Predictions

  • Bull: 1.0× long-term multiplier (neutral baseline)
  • Bear: dampens 6m/1y price targets
  • High VIX: Low-beta stocks get a flight-to-quality boost; high-beta get a floor at 0.55×
  • Regime columns are appended to feature vectors via extend_with_regime_cols()

Gate Thresholds

Short-Term Gate (ST_DIR_MIN_DELTA)

Challenger must improve 5d or 21d direction accuracy by at least 0.5 percentage points over the champion's held-out validation set.

Ranker Gate (RANKER_SPEARMAN_MIN)

Challenger ranker must improve Spearman rank correlation by at least 1.0 percentage point on the held-out validation set.

Full Step-by-Step Retrain Commands

Run these from the project root (/var/www/html/moneygoup) with the virtualenv active. Each step must succeed before the next.

Step 1 — Build the ranking dataset (GREEN feature snapshots)

Pulls OHLCV + macro history for the entire universe and writes snapshot rows to ranking_training_snapshots. Use --incremental for weekly maintenance; omit it for a full historical rebuild.

# Incremental refresh — only snapshots since the last stored date
python3 scripts/build_ranking_dataset.py --cadence weekly --incremental

# Full rebuild over a specific window
python3 scripts/build_ranking_dataset.py \
  --start 2023-01-01 --end 2026-08-01 \
  --cadence weekly

# Smoke test — 5 tickers, dry-run (no DB writes)
python3 scripts/build_ranking_dataset.py \
  --tickers AAPL,MSFT,NVDA,JPM,XOM \
  --dry-run

Step 2 — Extend 63d / 126d labels

Adds forward-return labels to the snapshot rows built in Step 1. Idempotent — skips rows that already have non-NULL labels. Recent rows stay NULL (the future hasn't happened yet).

# Normal run — compute missing labels
python3 scripts/extend_long_term_labels.py

# Force-recompute all labels (e.g. after a data correction)
python3 scripts/extend_long_term_labels.py --recompute

# Subset — useful for debugging a specific ticker
python3 scripts/extend_long_term_labels.py --tickers AAPL,MSFT

Step 3 — Train the long-term CS model directly

Trains the 2-output MLP on rows with non-NULL forward_return_63d / forward_return_126d. Writes models/long_term_cs_v2.pkl and models/long_term_cs_v2_manifest.json.

# Standard training run (80/20 time-split, default hidden layers 256/128/64)
python3 scripts/train_long_term_cs.py

# Custom hidden layers and more iterations
python3 scripts/train_long_term_cs.py \
  --hidden 256,128,64 \
  --max-iter 300 \
  --val-frac 0.2 \
  --seed 42
The hidden layer default in train_long_term_cs.py is 256,128,64 — wider than the per-ticker long-term MLP (192/96/48) because the CS model trains across the full universe and needs more capacity.

Step 4 — Full orchestrated retrain via retrain_pipeline.py

Runs all steps (build dataset → extend labels → train → gate check → promote) in one command. Use this for scheduled maintenance.

# Full retrain — all models, incremental dataset refresh
python3 scripts/retrain_pipeline.py --target all --incremental

# Long-term CS model only
python3 scripts/retrain_pipeline.py --target long_term --incremental

# Short-term model + ranker only
python3 scripts/retrain_pipeline.py --target short_term
python3 scripts/retrain_pipeline.py --target ranker

# Dry-run — full pipeline but don't overwrite any artifacts
python3 scripts/retrain_pipeline.py --target all --dry-run

# Skip freshness check (force retrain even if data looks stale)
python3 scripts/retrain_pipeline.py --target all --no-freshness-check
After a successful retrain, the new artifact is automatically promoted to models/long_term_cs_v2.pkl. Restart the prediction service (or let the next deepmoney_sync run spawn a fresh Python process) to pick up the new model — it loads once at process start.

Ranker Model

Alongside the price-prediction MLP, a LightGBM ranker scores relative attractiveness across the universe. It powers the Discovery feed — surfacing the most promising tickers regardless of whether you hold them.

LambdaRank variant (ranker_v1_lambdarank.txt)

  • Optimizes for correct relative ordering (rank correlation), not absolute price level
  • Training label: 20-day forward return percentile within snapshot cohort
  • Feature set: identical GREEN set from ranker_features.py
  • Produces raw_score, rank_pct (0–100)

Regression variant (ranker_v1_regression.txt)

  • Predicts the 20-day forward return directly
  • Used as a sanity check / ensemble blending signal
  • Less stable than LambdaRank for ranking tasks but easier to interpret

Ranker Inference (score_ranker.py)

Called once per deepmoney_sync run by analyzer.ts. Receives a batch of all candidate tickers in a single JSON payload (not one-per-ticker), computes GREEN features for each, scores them with LightGBM, percentile-ranks within the batch, and returns {ticker, raw_score, rank_pct, hist_vol_30} to stdout.

The batch-per-run design is critical: ranking is inherently relative. Calling the ranker per-ticker would produce a score that can't be compared across tickers.

Backtesting & Validation

Backtesting runs the prediction pipeline against historical dates, then resolves the outcomes when those horizon dates arrive. The database stores every prediction and every resolved actual so you can measure accuracy over any time window.

How It Works

📅 Historical Date as-of snapshot
🔬 Simulate Prediction backtest_predictions.py
💾 Log to DB prediction_tracking
⏱️ Wait for Horizon T+5 / T+21 / T+63 / T+126
✅ Resolve resolve_predictions.py
📊 Measure Accuracy backtest_results.py

Step 1 — Run the backtest

backtest_predictions.py time-travels to a historical date, fetches data as-of that date, runs the full prediction pipeline, and writes results to prediction_tracking (or prints them if --dry-run is set).

Single date snapshot

# Simulate what the model would have predicted for AAPL on a specific date
python3 scripts/backtest_predictions.py AAPL --as-of-date 2026-01-15

# Multiple tickers, single date, dry-run (no DB writes)
python3 scripts/backtest_predictions.py AAPL MSFT NVDA \
  --as-of-date 2026-03-01 --dry-run

Rolling window — one prediction per trading day

# Run weekly predictions from a start date forward (up to --max-days)
python3 scripts/backtest_predictions.py WMT \
  --from-date 2026-04-01 --max-days 90

# Step through a date range at 30-day intervals (default step)
python3 scripts/backtest_predictions.py AAPL TSLA \
  --start-date 2025-06-01 --end-date 2026-06-01 \
  --step-days 30

# Weekly steps — denser coverage, more DB rows
python3 scripts/backtest_predictions.py MSFT \
  --start-date 2025-01-01 --end-date 2026-01-01 \
  --step-days 7

# Overwrite existing rows for a re-run after a model change
python3 scripts/backtest_predictions.py AAPL \
  --from-date 2026-01-01 --max-days 180 --overwrite

Step 2 — Resolve predictions

resolve_predictions.py fetches actual closing prices for matured horizon dates and stamps actual_price, actual_direction, and was_correct on the prediction_tracking rows. Run it daily in production; run it manually after a backtest to immediately score results.

# Resolve all unresolved predictions across all horizons (1w, 1m, 3m, 6m)
python3 scripts/resolve_predictions.py
Rows with a horizon date in the future are skipped — they'll be resolved automatically once the date arrives. Run this again after each horizon matures.

Step 3 — Measure accuracy

Per-ticker accuracy (backtest_results.py)

Queries prediction_tracking and computes direction accuracy, price MAE, and confidence calibration broken down by horizon and ticker. Prints a console report.

# All resolved predictions, all model versions
python3 scripts/backtest_results.py

# Filter to a specific model version
python3 scripts/backtest_results.py --model-version v3split

# Require at least 30 resolved rows to report a segment (raise bar for signal)
python3 scripts/backtest_results.py --min-runs 30

# 10 confidence calibration bins instead of default 5
python3 scripts/backtest_results.py --conf-bins 10

Universe-wide aggregation (aggregated_backtest_results.py)

Same metrics as backtest_results.py but aggregated across all tickers — direction accuracy by sector, market-cap bucket, and per-symbol outlier scan. Best used after a full-universe backtest run.

# Default run — all tickers, all horizons
python3 scripts/aggregated_backtest_results.py

# Filter to a model version
python3 scripts/aggregated_backtest_results.py --model-version v3split

# Per-symbol outlier scan on 1m horizon (finds tickers the model gets wrong most)
python3 scripts/aggregated_backtest_results.py --outlier-horizon 1m

# Limit outlier scan to large-cap tickers only
python3 scripts/aggregated_backtest_results.py \
  --outlier-horizon 1w --market-cap-bucket large

Generating Reports

Two scripts generate HTML reports that can be opened in a browser. Both write to the doc/ directory.

Per-Ticker Accuracy Report (report_backtest.py)

Generates a self-contained HTML file showing predicted vs. actual prices, direction accuracy, and confidence calibration for one or more specific tickers. Output goes to stdout or a file you specify.

# Report for a single ticker — print to terminal
python3 scripts/report_backtest.py AAPL

# Write to a file in doc/
python3 scripts/report_backtest.py AAPL \
  -o doc/backtest_aapl.html

# Multi-ticker report
python3 scripts/report_backtest.py AAPL MSFT NVDA TSLA \
  -o doc/backtest_faang.html

# Filter by model version
python3 scripts/report_backtest.py WMT \
  --model-version v3split \
  -o doc/backtest_wmt_v3split.html

# Filter to a specific date range
python3 scripts/report_backtest.py AAPL \
  --from-date 2026-01-01 --to-date 2026-06-30 \
  -o doc/backtest_aapl_h1_2026.html

Multi-Ticker Comparison Report (backtest_comparison.py)

The richest report. Picks a random (or specified) set of tickers, runs backtests for each over a date range, and generates an interactive HTML report with Chart.js price charts, accuracy tables, and side-by-side horizon comparisons. Always writes to doc/backtest_comparison.html.

# Random tickers, default date range (last ~3 months, weekly steps)
python3 scripts/backtest_comparison.py

# Specific tickers
python3 scripts/backtest_comparison.py \
  --tickers AAPL MSFT NVDA TSLA JPM XOM

# Diverse market-cap mix — auto-picks small/mid/large tickers
python3 scripts/backtest_comparison.py \
  --diverse-caps --diverse-count 12

# Custom date range with 7-day step (denser backtest)
python3 scripts/backtest_comparison.py \
  --tickers AAPL MSFT NVDA \
  --start-date 2026-01-01 --end-date 2026-08-01 \
  --step-days 7

# Last 90 days (--days shorthand, overrides --start-date)
python3 scripts/backtest_comparison.py \
  --days 90 --tickers AAPL NVDA TSLA

# Skip running new predictions — regenerate report from existing DB data only
python3 scripts/backtest_comparison.py \
  --tickers AAPL MSFT --skip-backtest
Output is always at doc/backtest_comparison.html. Open it in a browser: file:///var/www/html/moneygoup/doc/backtest_comparison.html

Typical End-to-End Workflow

Here's the full sequence to run a fresh backtest and generate a comparison report for a specific set of tickers:

# 1. Run the backtest (writes predictions to DB)
python3 scripts/backtest_predictions.py AAPL MSFT NVDA TSLA \
  --start-date 2026-01-01 --end-date 2026-08-01 \
  --step-days 7 --overwrite

# 2. Resolve all matured horizons (stamps actual_price + was_correct)
python3 scripts/resolve_predictions.py

# 3. Check per-ticker accuracy in the terminal
python3 scripts/backtest_results.py --model-version v3split

# 4. Generate the comparison HTML report
python3 scripts/backtest_comparison.py \
  --tickers AAPL MSFT NVDA TSLA \
  --start-date 2026-01-01 --end-date 2026-08-01 \
  --step-days 7 --skip-backtest

# 5. Generate individual per-ticker reports if needed
python3 scripts/report_backtest.py AAPL MSFT NVDA TSLA \
  --from-date 2026-01-01 --to-date 2026-08-01 \
  -o doc/backtest_tech4_2026.html

# 6. Universe-wide aggregation (if you ran many tickers)
python3 scripts/aggregated_backtest_results.py \
  --outlier-horizon 1w
