MoneyGoUp — Authentication Flow

This document is the single reference for how user authentication works in MoneyGoUp: how accounts are created, how users log in, how passwords are reset, and how the platform enforces security at every step. It reflects the current state of the codebase as of May 17, 2026.

Recent Changes — May 17, 2026
  • Password policy hardened — minimum raised from 6 to 8 characters; at least one digit (0–9) is now required. Applied to both registration and password reset on the server (Zod schema) and mirrored by client-side checks on the UI pages.
  • Register page UI widened — card changed from max-w-md / p-4 to max-w-xl / p-2. Login page now uses the same wider layout.
  • Password hint text added — both the Register page and the Reset Password page display "At least 8 characters and one number." below the password field.
  • Register API response updated — field names changed to userId and approvalStatus; email is no longer echoed back.
  • Test suite extended — no-digit and boundary (exactly 8 chars) cases added to register and reset-password test files; jest.mock('@/lib/email') added to register tests to prevent real email sends during test runs.

0 System Summary

MoneyGoUp uses NextAuth.js v4 with a Credentials provider backed by a MySQL user table. Sessions are JWT-based. The platform enforces a manual admin approval gate — users can register but cannot access any protected resource until an administrator approves their account.

Password hashingbcryptjs, cost factor 10

1 Security Layers

Every authentication-related API route passes through multiple independent security controls before reaching business logic:

Origin Check (checkOrigin) — Blocks requests from untrusted origins ↓ Rate Limit (checkRateLimit) — Per-IP token bucket; 429 if exhausted ↓ Zod Schema Validation — Rejects malformed or policy-violating input (400) ↓ Business Logic — DB lookup, bcrypt compare, token validation ↓ Response

Origin Check

The checkOrigin() utility (src/utils/originCheck.ts) validates that the Origin or Referer header matches the expected application domain. Applied to all state-changing auth routes (register, reset-password POST, forgot-password).

2 Password Policy Updated May 2026

Current requirements (enforced at API level and client-side):
  • Minimum 8 characters
  • Maximum 100 characters
  • Must contain at least one digit (0–9)

These rules are defined in Zod schemas in two server-side routes and are independently enforced client-side before the API call is made. Both layers must agree — a request that bypasses the UI still cannot create a non-compliant password.

LocationEnforcement mechanismBehavior on failure
Register page (src/app/register/page.tsx) JavaScript check in handleSubmit before fetch() Sets inline error; API call never made
Reset Password page (src/app/reset-password/page.tsx) JavaScript check in handleSubmit before fetch() Sets inline error; API call never made
POST /api/auth/register Zod z.string().min(8).max(100).regex(/\d/) HTTP 400 with validation message
POST /api/auth/reset-password Zod z.string().min(8).max(100).regex(/\d/) HTTP 400 with first failing Zod message
Password hint text: Both the Register page and Reset Password page display "At least 8 characters and one number." directly below the password input field to set user expectations before submission.

3 Registration Flow

New users self-register at /register. Accounts are not immediately active — they are placed in a pending state and require admin approval.

User fills Register form (/register) ↓ Client-side check: password ≥ 8 chars AND contains digit [fails] → inline error displayed, form blocked [passes] ↓ POST /api/auth/register { username, email, password } ↓ Origin check → Rate limit → Zod validation ↓ SELECT: email already exists? → 409 "An account with this email address is already registered." SELECT: username already taken? → 409 "This username is already taken." ↓ bcrypt.hash(password, 10) INSERT users (username, email, password_hash, approval_status='pending') ↓ sendRegistrationEmail() via Resend [failure is non-fatal; logged as warning] ↓ HTTP 201 → { message, userId, approvalStatus: "pending" } ↓ User sees success banner: "Registration successful! Your account is pending admin approval..." ↓ Admin reviews account in /admin/users → approves or rejects

Registration API — Key Details

Success response:

{
  "message": "Account created and awaiting admin approval",
  "userId": 42,
  "approvalStatus": "pending"
}

Registration confirmation email is sent via Resend using the resend_reg_api_key environment variable. The email informs the user that their account is pending admin review. If the Resend API call fails, the error is logged as a warning and the registration still succeeds — the user account is created regardless.

4 Login Flow

Authentication is handled entirely by NextAuth.js. The login page at /login calls signIn('credentials', ...) from the NextAuth client SDK, which invokes the authorize callback in src/lib/auth.ts.

User fills Login form (/login) ↓ signIn('credentials', { username, password, redirect: false }) ↓ NextAuth authorize callback (src/lib/auth.ts) ↓ Rate limit check by IP (loginLimiter) ↓ SELECT users WHERE username = ? [not found] → return null → "Invalid username or password" [found] ↓ bcrypt.compare(password, password_hash) [mismatch] → return null → "Invalid username or password" [match] ↓ evaluateApprovalStatus(approval_status, rejected_reason) [pending] → throw ACCOUNT_PENDING_APPROVAL → "Your account is awaiting admin approval." [rejected] → throw ACCOUNT_REJECTED → "Your account request was rejected." [approved] ↓ UPDATE users SET last_login = NOW() (async, non-blocking) JWT issued → HttpOnly session cookie set ↓ window.location.href = '/dashboard' (hard redirect to pick up fresh session)

5 Password Reset Flow Updated May 2026

The password reset flow spans two pages and three API calls. It is designed so that an attacker cannot discover whether a given email address is registered (all responses to the forgot-password step are identical).

Step 1 — Request a Reset Link

User visits /forgot-password ↓ POST /api/auth/forgot-password { email } ↓ Origin check → Rate limit (3 req/15 min per IP) ↓ Zod: valid email format? [no] → HTTP 200 success (identical to success — no enumeration) [yes] ↓ SELECT users WHERE email = ? AND approval_status = 'approved' [not found or not approved] → HTTP 200 success (silent) [found] ↓ DELETE existing unused tokens for this user INSERT password_reset_tokens (user_id, token_hash=SHA-256(rawToken), expires_at=+1hr) sendPasswordResetEmail(email, resetUrl) via Resend ↓ HTTP 200: "If that email address is registered, you will receive a password reset link shortly."

Step 2 — Validate the Token (page load)

User clicks email link → /reset-password?token=<64-char hex> ↓ Page mounts → GET /api/auth/reset-password?token=... ↓ token.length === 64? [no] → { valid: false, message: "Invalid or missing reset token." } [yes] ↓ SHA-256(rawToken) → lookup in password_reset_tokens [not found] → { valid: false, message: "Invalid or expired reset link." } [found] ↓ token.used_at IS NOT NULL? → { valid: false, message: "This reset link has already been used." } new Date() > expires_at? → { valid: false, message: "This reset link has expired." } [all pass] → { valid: true } ↓ Page renders password form (if valid) or error + "Request New Reset Link" button (if invalid)

Step 3 — Submit New Password

User enters new password + confirmation ↓ Client-side check: password ≥ 8 chars AND contains digit AND passwords match [fails] → inline error, API call blocked [passes] ↓ POST /api/auth/reset-password { token, password } ↓ Origin check → Rate limit (5 req/15 min per IP) Zod: token length === 64, password min 8 + digit [fails] → HTTP 400 with first Zod error message [passes] ↓ SHA-256(token) → lookup in password_reset_tokens [not found] → HTTP 400 "Invalid or expired reset link." [used] → HTTP 400 "This reset link has already been used." [expired] → HTTP 400 "This reset link has expired." [valid] ↓ bcrypt.hash(newPassword, 10) UPDATE users SET password_hash = ?, modified_at = NOW() WHERE id = ? UPDATE password_reset_tokens SET used_at = NOW() WHERE id = ? ↓ HTTP 200 { "message": "Password updated successfully." } ↓ Page shows success banner → redirects to /login after 3 seconds
Token mechanics: A 32-byte cryptographically random value is generated (randomBytes(32).toString('hex')), producing a 64-character hex string. Only the SHA-256 hash of this string is stored in the database. The raw token travels only in the email link URL and in the user's request — it never appears in the database.

All auth routes are excluded from the middleware session guard — they are listed in the matcher negative lookahead so unauthenticated users can reach them freely.

8 Middleware Route Guard

src/middleware.ts

All application routes (pages and API routes) that are not explicitly excluded are protected by the NextAuth.js middleware wrapper. A valid JWT session token must be present, or the request must carry the x-api-key internal secret header.

Public paths (no session required)

  • /api/auth/** — all NextAuth and custom auth routes
  • /login
  • /register
  • /forgot-password
  • /reset-password
  • /_next/static/**, /_next/image/** — build assets
  • /growmystock_logo.svg, /favicon.ico

Internal API bypass

Requests carrying the header x-api-key: <DEEPMONEY_INTERNAL_SECRET> skip session validation entirely. This is used by the Python DeepMoney sync scripts to call protected API endpoints from the server without a user session.

9 User Roles

The role column on the users table controls what each account can access.

RoleAccess levelQuota limits
user Standard — access to all core features within quota Enforced — watchlist, portfolio, and daily lookup caps apply
superuser Elevated — higher quota limits than standard users Enforced — same structure, higher thresholds
admin Full — access to admin console, cache stats, user management None — unlimited access to all resources

Role is embedded in the JWT at login and available throughout the session via session.user.role. Because the role is cached in the token, an admin role change takes effect at the user's next login.

10 Account Approval States

The approval_status column controls whether a registered account can log in.

StatusMeaningLogin outcome
pending Newly registered; awaiting admin review Blocked — error: "Your account is awaiting admin approval."
approved Admin has reviewed and granted access Allowed — session issued
rejected Admin has denied the account Blocked — error: "Your account request was rejected."
Password reset restriction: The forgot-password route only sends a reset email if the target account has approval_status = 'approved'. Pending and rejected accounts cannot reset their passwords via email — the endpoint silently returns success to prevent enumeration.
