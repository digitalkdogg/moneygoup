MoneyGoUp — Authentication Flow

This document is the single reference for how user authentication works in MoneyGoUp: how accounts are created, how users log in, how passwords are reset, and how the platform enforces security at every step. It reflects the current state of the codebase as of June 12, 2026.

Recent Changes — June 12, 2026
  • Middleware module renamed — The Next.js middleware entry point now lives at src/proxy.ts (previously src/middleware.ts). All behaviour (NextAuth withAuth wrapper, per-request nonce-based CSP, x-api-key internal bypass) is unchanged; only the filename moved. Documentation paths in the Middleware section and System Summary table have been updated accordingly.
  • Public paths list expanded — The middleware's PUBLIC_PATHS array now also covers the marketing/legal/SEO surface so those pages still receive the nonce CSP without requiring a session: /, /contact, /api/contact, /legal/privacy, /legal/terms, /legal/disclaimer, opengraph image routes, /sitemap.xml, and /robots.txt.
  • Internal-bypass minimum secret strength documented — Both isInternalRequest() (used by route-level rate limiters) and the middleware-level x-api-key short-circuit refuse to honour DEEPMONEY_INTERNAL_SECRET unless it is at least 32 bytes long. If the secret is too short, the bypass is silently disabled and the request falls through to normal session/rate-limit checks.
  • Numeric rate-limit caps added to the Security Layers table — register: 5 / 15 min per IP (+ username), login: 10 / 15 min per IP. Forgot-password and reset-password caps were already listed.
Earlier Changes — May 24, 2026
  • AUTH-1 resolved — checkApprovalGuard() added to 20 additional API routes. Every authenticated data endpoint now re-verifies the user's approval status against the database on each request. Users whose accounts are suspended or rejected mid-session are immediately denied access across all endpoints.
  • AUTH-2 resolved — SESSION_MAX_AGE_SECS constant introduced in src/lib/auth.ts. Both the JWT session.maxAge and the session cookie options.maxAge now use this single constant, ensuring they always stay in sync. The SESSION_MAX_AGE environment variable now correctly controls both.
  • CSP moved to middleware (CFG-1 partial) — Nonce-based Content Security Policy moved from a static header in next.config.js to per-request generation in the middleware. Every HTTP response now receives a fresh cryptographic nonce, making inline script protections dynamic and per-request.
Earlier Changes — May 17, 2026
  • Password policy hardened — minimum raised from 6 to 8 characters; at least one digit (0–9) is now required. Applied to both registration and password reset on the server (Zod schema) and mirrored by client-side checks on the UI pages.
  • Register page UI widened — card changed from max-w-md / p-4 to max-w-xl / p-2. Login page now uses the same wider layout.
  • Password hint text added — both the Register page and the Reset Password page display "At least 8 characters and one number." below the password field.
  • Register API response updated — field names changed to userId and approvalStatus; email is no longer echoed back.
  • Approval email added — sendApprovalEmail() added to src/lib/email.ts. The admin PATCH route now sends this email automatically when a user's account is approved. Email failures are caught and logged without blocking the admin action.
  • Test suite extended — no-digit and boundary (exactly 8 chars) cases added to register and reset-password test files; jest.mock('@/lib/email') added to register tests to prevent real email sends during test runs. Admin users test file updated with 3 new cases covering approval email send, no-email skip, and email failure resilience.

0 System Summary

MoneyGoUp uses NextAuth.js v4 with a Credentials provider backed by a MySQL user table. Sessions are JWT-based. The platform enforces a manual admin approval gate — users can register but cannot access any protected resource until an administrator approves their account.

1 Security Layers

Every authentication-related API route passes through multiple independent security controls before reaching business logic:

Origin Check (checkOrigin) — Blocks requests from untrusted origins ↓ Rate Limit (checkRateLimit) — Per-IP Redis counter; 429 if exhausted ↓ Zod Schema Validation — Rejects malformed or policy-violating input (400) ↓ Business Logic — DB lookup, bcrypt compare, token validation ↓ Response

Origin Check

The checkOrigin() utility (src/utils/originCheck.ts) validates that the Origin header (or, for mutating requests with a missing/null Origin, the Referer header) matches the configured ALLOWED_ORIGINS (falling back to NEXTAUTH_URL). The policy is fail-closed: if no allowed origins are configured the utility returns a 500 and blocks the request. Safari Private Browsing's Origin: null is treated as missing and falls through to Referer validation. Applied to all state-changing auth routes (register POST, reset-password POST, forgot-password POST).

All limiters are RedisRateLimiter instances so counters are shared across workers. The checkRateLimit helper extracts the client IP via getClientIP() (which only trusts X-Forwarded-For / X-Real-IP / CF-Connecting-IP when the direct request source is in the TRUSTED_PROXIES env list) and skips rate limiting entirely for valid internal requests (see isInternalRequest).

2 Password Policy Updated May 2026

Current requirements (enforced at API level and client-side):
  • Minimum 8 characters
  • Maximum 100 characters
  • Must contain at least one digit (0–9)

These rules are defined in Zod schemas in two server-side routes and are independently enforced client-side before the API call is made. Both layers must agree — a request that bypasses the UI still cannot create a non-compliant password.

LocationEnforcement mechanismBehavior on failure
Register page (src/app/register/page.tsx) JavaScript check in handleSubmit before fetch() Sets inline error; API call never made
Reset Password page (src/app/reset-password/page.tsx) JavaScript check in handleSubmit before fetch() Sets inline error; API call never made
POST /api/auth/register Zod z.string().min(8).max(100).regex(/\d/) HTTP 400 with validation message
POST /api/auth/reset-password Zod z.string().min(8).max(100).regex(/\d/) HTTP 400 with first failing Zod message
Password hint text: Both the Register page and Reset Password page display "At least 8 characters and one number." directly below the password input field to set user expectations before submission.

3 Registration Flow

New users self-register at /register. Accounts are not immediately active — they are placed in a pending state and require admin approval.

User fills Register form (/register) ↓ Client-side check: password ≥ 8 chars AND contains digit [fails] → inline error displayed, form blocked [passes] ↓ POST /api/auth/register { username, email, password, website } ↓ Origin check → Rate limit (5/15min per IP + username) → Zod validation ↓ Honeypot: website field non-empty? → silent fake 201 (bot blocked) ↓ SELECT: email already exists (non-rejected)? → 409 "An account with this email address is already registered." SELECT: username already taken (non-rejected)? → 409 "This username is already taken." ↓ Any prior rejected record matching email/username is archived (approval_status='archived', conflicting field suffixed with '_archived') ↓ bcrypt.hash(password, 10) INSERT users (username, email, password_hash, approval_status='pending') ↓ sendRegistrationEmail() via Resend [failure is non-fatal; logged as warning] ↓ HTTP 201 → { message, userId, approvalStatus: "pending" } ↓ User sees success banner: "Registration successful! Your account is pending admin approval..." ↓ Admin reviews account in /admin/users → approves or rejects

Success response:

{
  "message": "Account created and awaiting admin approval",
  "userId": 42,
  "approvalStatus": "pending"
}

Registration confirmation email is sent via Resend using the resend_reg_api_key environment variable. The email informs the user that their account is pending admin review. If the Resend API call fails, the error is logged as a warning and the registration still succeeds — the user account is created regardless.

4 Login Flow

Authentication is handled entirely by NextAuth.js. The login page at /login calls signIn('credentials', ...) from the NextAuth client SDK, which invokes the authorize callback in src/lib/auth.ts.

User fills Login form (/login) ↓ signIn('credentials', { username, password, redirect: false }) ↓ NextAuth authorize callback (src/lib/auth.ts) ↓ Rate limit check by IP (loginLimiter — 10/15min) ↓ SELECT users WHERE username = ? [not found] → bcrypt.compare against dummy hash (timing guard) → return null → "Invalid username or password" [found] ↓ bcrypt.compare(password, password_hash) [mismatch] → return null → "Invalid username or password" [match] ↓ evaluateApprovalStatus(approval_status, rejected_reason) [pending] → throw ACCOUNT_PENDING_APPROVAL → "Your account is awaiting admin approval." [rejected] → throw ACCOUNT_REJECTED → "Your account request was rejected." [unsubscribed] → throw ACCOUNT_REJECTED → "Your account has been deactivated." [archived] → throw ACCOUNT_REJECTED → "This account no longer exists." [approved] ↓ UPDATE users SET last_login = NOW() (async, non-blocking) JWT issued → HttpOnly session cookie set session.user = { id, name, role, approvalStatus } ↓ window.location.href = '/dashboard' (hard redirect to pick up fresh session)

5 Password Reset Flow Updated May 2026

The password reset flow spans two pages and three API calls. It is designed so that an attacker cannot discover whether a given email address is registered (all responses to the forgot-password step are identical).

Step 1 — Request a Reset Link

User visits /forgot-password ↓ POST /api/auth/forgot-password { email } ↓ Origin check → Rate limit (3 req/15 min per IP) ↓ Zod: valid email format? [no] → HTTP 200 success (identical to success — no enumeration) [yes] ↓ SELECT users WHERE email = ? AND approval_status = 'approved' [not found or not approved] → HTTP 200 success (silent) [found] ↓ DELETE existing unused tokens for this user INSERT password_reset_tokens (user_id, token_hash=SHA-256(rawToken), expires_at=+1hr) sendPasswordResetEmail(email, resetUrl) via Resend ↓ HTTP 200: "If that email address is registered, you will receive a password reset link shortly."

Step 2 — Validate the Token (page load)

User clicks email link → /reset-password?token=<64-char hex> ↓ Page mounts → GET /api/auth/reset-password?token=... ↓ token.length === 64? [no] → { valid: false, message: "Invalid or missing reset token." } [yes] ↓ SHA-256(rawToken) → lookup in password_reset_tokens [not found] → { valid: false, message: "Invalid or expired reset link." } [found] ↓ token.used_at IS NOT NULL? → { valid: false, message: "This reset link has already been used." } new Date() > expires_at? → { valid: false, message: "This reset link has expired." } [all pass] → { valid: true } ↓ Page renders password form (if valid) or error + "Request New Reset Link" button (if invalid)

Step 3 — Submit New Password

User enters new password + confirmation ↓ Client-side check: password ≥ 8 chars AND contains digit AND passwords match [fails] → inline error, API call blocked [passes] ↓ POST /api/auth/reset-password { token, password } ↓ Origin check → Rate limit (5 req/15 min per IP) Zod: token length === 64, password min 8 + digit [fails] → HTTP 400 with first Zod error message [passes] ↓ SHA-256(token) → lookup in password_reset_tokens [not found] → HTTP 400 "Invalid or expired reset link." [used] → HTTP 400 "This reset link has already been used." [expired] → HTTP 400 "This reset link has expired." [valid] ↓ bcrypt.hash(newPassword, 10) UPDATE users SET password_hash = ?, modified_at = NOW() WHERE id = ? UPDATE password_reset_tokens SET used_at = NOW() WHERE user_id = ? AND used_at IS NULL ↓ HTTP 200 { "message": "Password updated successfully." } ↓ Page shows success banner → redirects to /login after 3 seconds
Token mechanics: A 32-byte cryptographically random value is generated (randomBytes(32).toString('hex')), producing a 64-character hex string. Only the SHA-256 hash of this string is stored in the database. The raw token travels only in the email link URL and in the user's request — it never appears in the database.

8 Middleware Route Guard Updated June 2026

src/proxy.ts

All application routes (pages and API routes) that are not explicitly excluded by the matcher are protected by the NextAuth.js withAuth wrapper. A valid JWT session token must be present, the route must be in the public-paths list, or the request must carry the x-api-key internal secret header. The Next.js middleware entry point is exported from src/proxy.ts.

Per-request nonce-based CSP: The middleware generates a unique cryptographic nonce for every request using crypto.getRandomValues() over a 16-byte buffer, base64-encoded. The nonce is injected into the Content-Security-Policy response header via script-src 'self' 'nonce-{nonce}' 'strict-dynamic', and into style-src 'self' 'nonce-{nonce}' 'unsafe-inline'. The nonce is also passed to the request via the x-nonce header so the root src/app/layout.tsx can read it via headers().get('x-nonce') and embed it into inline <script> tags. In development, 'unsafe-eval' is added to script-src to support Next.js Fast Refresh; it is absent in production. default-src is set to 'self' https:.

Public paths (no session required, but still receive the nonce CSP)

The PUBLIC_PATHS array in src/proxy.ts bypasses the session check (but still runs the CSP middleware function):

  • / — marketing landing
  • /login
  • /register
  • /forgot-password
  • /reset-password
  • /contact, /api/contact
  • /legal/privacy, /legal/terms, /legal/disclaimer
  • /api/unsubscribe — public by design (RFC 8058), protected via HMAC-signed token
  • /opengraph-image, /login/opengraph-image, /register/opengraph-image
  • /sitemap.xml, /robots.txt
  • /api/analytics/model-accuracy — model accuracy stats; publicly accessible to power the marketing landing page's "Proven Track Record" section and the ModelAccuracyStats component without requiring a login

Additionally, the matcher itself excludes /api/auth/** (NextAuth internals and the custom auth routes), /_next/static/**, /_next/image/**, and the logo/favicon assets, so the middleware function does not even run for those paths.

Internal API bypass

Requests carrying the header x-api-key: <DEEPMONEY_INTERNAL_SECRET> skip session validation entirely inside the authorized callback. Important constraint: the secret is only honoured if DEEPMONEY_INTERNAL_SECRET.length >= 32; if the env var is shorter (or missing) the bypass is silently disabled and the request falls through to the normal session check. This is the mechanism used by the Python DeepMoney sync scripts (deepmoney_sync.py, update_predictions.py) to call protected API endpoints from the server without a user session.

Route handlers that want to recognise the same internal caller (for example to skip rate limiting or per-user quotas) call isInternalRequest() from src/utils/internalAuth.ts, which performs the same check using SHA-256 hashes and timingSafeEqual for constant-time comparison.

Known scope (AUTH-3, deferred): The middleware-level x-api-key bypass grants full access to every protected route — including admin routes — for any request with the secret. This is documented as outstanding security debt; the agreed remediation (move truly-internal endpoints under /api/internal/ and replace the shared secret with short-lived server-to-server tokens for dual-use routes) has not yet been implemented.

9 User Roles

The role column on the users table controls what each account can access.

RoleAccess levelQuota limits
user Standard — access to all core features within quota Enforced — watchlist, portfolio, and daily lookup caps apply
superuser Elevated — higher quota limits than standard users Enforced — same structure, higher thresholds
admin Full — access to admin console, cache stats, user management None — unlimited access to all resources

Role is embedded in the JWT at login and available throughout the session via session.user.role. Because the role is cached in the token, an admin role change takes effect at the user's next login.

10 Account Approval States Updated May 2026

The approval_status column controls whether a registered account can log in and access data.

StatusMeaningLogin outcomeAPI access
pending Newly registered; awaiting admin review Blocked — "Your account is awaiting admin approval." Denied — 403 on all protected endpoints
approved Admin has reviewed and granted access Allowed — session issued Allowed
rejected Admin has denied the account Blocked — "Your account request was rejected." Denied — 403 on all protected endpoints
unsubscribed User unsubscribed via email list-unsubscribe link Blocked — "Your account has been deactivated." Denied — 403 on all protected endpoints
archived Account archived by admin (or auto-archived when a rejected record is replaced by a fresh registration) Blocked — "This account no longer exists." Denied — 403 on all protected endpoints
Runtime re-verification (AUTH-1 fix, May 2026): In addition to the login-time check, every authenticated API route calls checkApprovalGuard(userId) (src/utils/approvalStatus.ts) which re-queries approval_status from the database on every request. This prevents users whose accounts were suspended after login from continuing to access data with a still-valid session token (up to 30 days). The guard fails closed — if the DB query errors, access is denied (returns a PENDING outcome with the message "Error verifying account status."). As of the May 24, 2026 sweep, checkApprovalGuard() is called from roughly 25 server route files spanning dashboard, prediction, stock_data, user/watchlist, user/portfolio, user/profile, user/stocks, market, worldbank, and ETF holdings endpoints.
Password reset restriction: The forgot-password route only sends a reset email if the target account has approval_status = 'approved'. Pending, rejected, unsubscribed, and archived accounts cannot reset their passwords via email — the endpoint silently returns success to prevent enumeration.

11 Email Notification System Updated May 2026

All transactional emails are sent via Resend, a developer email API. The email sending logic is centralised in src/lib/email.ts, which exports three functions. Each function uses a separate API key environment variable, allowing fine-grained access control and independent key rotation.

Function Trigger Env var (API key) Subject Failure behaviour
sendRegistrationEmail() User completes registration (POST /api/auth/register) resend_reg_api_key "Welcome to GrowMyStock — Account Pending Approval" Caught and logged as warning; registration still succeeds
sendApprovalEmail() Admin approves a user account (PATCH /api/admin/users) resend_reg_final_api_key "Your GrowMyStock Account Has Been Approved!" Caught and logged as error; admin action still returns 200
sendPasswordResetEmail() User requests a password reset (POST /api/auth/forgot-password) RESEND_API_KEY "Reset your GrowMyStock password" Propagated — outer handler catches and logs; endpoint returns 200 (silent)

Approval Email — What the User Receives

When an admin clicks "Approve" on the admin user management page, the system immediately looks up the user's email address and username from the database and sends them an approval notification. The email contains:

  • A personalised greeting using the user's username
  • Confirmation that their account has been approved
  • A prominent "Log In Now" call-to-action button linking to https://growmystock.com/login
  • A plain-text fallback URL for email clients that block HTML buttons
Resilience design: If the Resend API call fails for any reason (network error, invalid key, rate limit), the failure is caught and logged by the server. The admin's approve action is not rolled back — the user's database record remains approved, and the admin receives a 200 OK response. This ensures an email delivery issue never prevents an admin from completing a workflow. If the email is not received, the admin can manually inform the user.
No-email guard: If the approved user's record does not have an email address stored (the email column allows NULL), sendApprovalEmail() is skipped entirely. No error is thrown or logged in this case.
