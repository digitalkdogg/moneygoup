MoneyGoUp — Admin User Management

This document describes the full lifecycle of a user account in GrowMyStock/MoneyGoUp, from self-registration through admin approval, email notifications, and ongoing role management. It is current as of May 17, 2026 and is written for project managers who need to understand what the system does without reading code.

Recent Changes — May 17, 2026
  • Approval email added NEW — A new sendApprovalEmail() function was added to src/lib/email.ts. When an admin approves a user account, the system now automatically sends that user a confirmation email with a direct link to the login page.
  • Admin PATCH route updated — After successfully writing the approval to the database, PATCH /api/admin/users fetches the user's email address and calls sendApprovalEmail(). Email failures are caught and logged without affecting the admin's workflow.
  • Test suite updated — api_admin_users.test.ts was updated to mock @/lib/email and add three new test cases: email sent on approval, email skipped when no address is on file, and endpoint returns 200 even when the email send fails.

1 Summary

GrowMyStock uses a manual admin approval model. Users cannot access any protected feature until an administrator explicitly grants access. This gives the team full control over who can use the platform at any time.

AspectDetail
User registrationSelf-service at /register — anyone can create an account
Default stateAll new accounts start as pending — login is blocked
Approval mechanismAdmin-only web console at /admin/users
Email notificationsResend API — one email on registration, one on approval, one for password reset
User rolesuser, superuser, admin — changeable post-approval
Security safeguardSystem prevents demoting the last remaining admin account

2 User Account Lifecycle

Every account passes through a defined sequence of states. The diagram below shows the complete path from registration to active use, including email touchpoints.

User visits /register and submits username, email, password ↓ Server validates input (origin check, rate limit, Zod schema) ↓ Account created in database → approval_status = "pending" ↓ [EMAIL 1] Registration confirmation sent to user via Resend "Welcome — your account is pending admin approval" ↓ Admin logs in and opens /admin/users Admin sees account in "Pending Approvals" tab ↓ Admin clicks "Approve" Admin clicks "Reject" ↓ ↓ approval_status = "approved" approval_status = "rejected" approved_by = admin ID rejected_reason saved approved_at = timestamp ↓ ↓ User cannot log in [EMAIL 2] Approval email sent (rejection shown at login) "Your account is approved!" ↓ User clicks "Log In Now" → /login ↓ User accesses dashboard and all platform features

Account States at a Glance

StateWhat it meansCan the user log in?
PENDING Account created, waiting for admin to review No — "Your account is awaiting admin approval."
APPROVED Admin has granted access Yes — full access based on their role
REJECTED Admin has denied the account No — "Your account request was rejected."
Re-approval is possible: An admin can change a user's status at any time. A rejected user can be approved (and vice versa). The "Approve" and "Reject" buttons are available for all non-pending users in the All Users tab.

3 Admin Console UI

The admin user management interface is a protected page available only to users with the admin role. It is accessible at /admin/users.

Access control: The page checks the session on load. If the logged-in user is not an admin, they are immediately redirected to the homepage. The API routes perform an independent role check on every request — the UI check alone is not relied upon for security.

What admins see

The page presents a two-tab interface:

Tab 1 — Pending Approvals

Shows only accounts with approval_status = "pending". The count of pending accounts is shown as a badge on the tab. This is the default view when the page loads, surfacing the most actionable items first.

Tab 2 — All Users

Shows all accounts regardless of status. Admins can use this view to find specific users, check login history, or change roles for already-approved accounts.

Search and Filtering

A search field at the top of the table allows admins to filter results by username (partial match). Results update when the admin changes the tab or types in the search box. A manual "Refresh" button is available to reload the list without navigating away.

User table columns

UsernameThe user's chosen display name (unique)
StatusCurrent approval status shown as a colour-coded badge (amber = pending, green = approved, red = rejected)
RoleInline dropdown — admin can change role directly from the table row
Created AtDate the account was registered
Last LoginMost recent successful login, or "Never" if the user has not logged in
ActionsApprove / Reject buttons for pending users; a single toggle button for approved or rejected users

4 Approve and Reject Actions

Approving a user

  1. Admin clicks "Approve" next to a pending user.
  2. The browser sends a PATCH /api/admin/users request with { userId, approval_status: "approved" }.
  3. The server verifies the requesting session belongs to an admin.
  4. The database record is updated: approval_status = "approved", approved_by set to the admin's user ID, approved_at set to the current timestamp, rejected_reason cleared.
  5. The server fetches the user's email address and username from the database.
  6. If an email address is on file, sendApprovalEmail() is called. If it fails, the failure is logged and the response is still 200 OK.
  7. The admin console refreshes the user list automatically.

Rejecting a user

  1. Admin clicks "Reject" next to a pending (or previously approved) user.
  2. A browser prompt asks the admin to enter a rejection reason (required text field; pressing Cancel aborts the action).
  3. The browser sends a PATCH /api/admin/users request with { userId, approval_status: "rejected", rejected_reason: "..." }.
  4. The database record is updated: approval_status = "rejected", rejected_reason saved, approved_by set to the rejecting admin's ID (for audit trail).
  5. No email is sent on rejection in the current implementation.
  6. The admin console refreshes the user list.
No rejection email currently: Users are not automatically notified when their account is rejected. If your workflow requires notifying rejected applicants, this would need to be added to src/lib/email.ts and called from the PATCH handler — a similar pattern to sendApprovalEmail().

5 Role Management

User roles control access levels and quota limits across the platform. An admin can change any user's role directly from the user management table using the inline role dropdown.

RolePlatform accessUsage quotasCan manage users?
user All core features (dashboard, portfolio, watchlist, stock search) Standard limits enforced (watchlist size, portfolio size, daily lookups) No
superuser All core features, higher quota allowances Elevated thresholds (defined in the role_limits table) No
admin All features plus /admin/users and cache diagnostics Unlimited Yes

Last-admin safeguard

The system prevents an admin from demoting themselves or another admin if there is only one admin account remaining. This prevents the platform from being left in an unmanageable state where no one can reach the admin console.

Admin attempts to change role to "superuser" for user X ↓ Server counts: SELECT COUNT(*) FROM users WHERE role = "admin" [count > 1] → proceed with role change [count = 1] → check: is user X the only admin? [yes] → HTTP 400 "Cannot demote the only admin" [no] → proceed (the other admin is someone else)
Role changes take effect at next login: The user's role is embedded in their JWT session token at login time. If an admin promotes a user from user to superuser, the change is recorded immediately in the database, but the affected user will not see the new quota limits until they log out and back in.

6 Email Notification System

All outbound email is sent through Resend, a developer email service. The implementation is centralised in a single file: src/lib/email.ts. This file exports three functions, each responsible for one type of notification.

Using separate Resend API keys for different email types allows the team to:

  • Rotate keys independently without disrupting other email flows
  • Monitor and throttle each email type separately in the Resend dashboard
  • Assign different sending domains or identities per notification type if needed in the future

Technical implementation

After the database update succeeds, the PATCH handler runs the following logic:

approval_status === "approved"? [yes] ↓ SELECT email, username FROM users WHERE id = userId user.email exists? [no] → skip (no email sent, no error) [yes] ↓ try { await sendApprovalEmail(user.email, user.username) } catch (emailErr) { logger.error("Failed to send approval email", { emailErr, targetUserId }) // response is NOT affected — continues to HTTP 200 }

10 Email Failure Resilience

A key design decision across all three email types is that email failures never block the primary user action. The table below summarises the failure handling for each email.

Email Failure handling User impact Admin impact
Registration confirmation Caught, logged as warning Account still created; user does not receive confirmation email None — no admin action involved
Approval notification NEW Caught, logged as error User's account is approved in the database; they can log in; they just don't receive the notification email Admin receives HTTP 200 OK — their approve action succeeds
Password reset link Propagates to outer handler; logged; endpoint returns HTTP 200 (silent) User does not receive the reset link — they see the generic success message regardless None
Why this matters operationally: If the Resend API is down or an API key is misconfigured, user registrations and admin approvals still complete. The system logs the email failure, which can be monitored by checking server logs or a logging service. In the case of a missed approval email, an admin can inform the user manually or re-trigger by some other means.
Monitoring recommendation: Because email failures are non-fatal and the user sees no indication that the email was not sent, it is important to monitor server logs for Failed to send approval email entries. A high rate of these errors may indicate a misconfigured or expired Resend API key.

11 API Route — GET /api/admin/users

Returns a list of users for display in the admin console. Only accessible to admins.

GET /api/admin/users Admin only

Authentication

Requires a valid session token belonging to a user with role = "admin". Returns 401 if no session exists; 403 if the session belongs to a non-admin.

Email address not exposed: The GET endpoint does not return the user's email address. The email is only fetched server-side for the purpose of sending the approval notification — it is never included in the list response sent to the admin browser.

13 Database Schema

Two database tables are central to user management: users and password_reset_tokens.

users table

Stores one row per registered account. Key columns for the approval workflow:

ColumnTypeDescription
idINT (auto-increment)Primary key
usernameVARCHAR(255)Unique display name chosen at registration
emailVARCHAR(255)Unique email address; nullable (some legacy accounts may have no email)
password_hashVARCHAR(255)bcrypt hash of the user's password (cost factor 10)
roleENUM('user','superuser','admin')Access level. Default: user
approval_statusENUM('pending','approved','rejected')Controls whether the account can log in. Default: pending
approved_byINT (FK → users.id)ID of the admin who last changed approval status. NULL if not yet actioned.
approved_atDATETIMETimestamp of the most recent approval action
rejected_reasonVARCHAR(255)Free-text reason entered by the admin when rejecting. NULL otherwise.
last_loginDATETIMEAutomatically updated on each successful login
created_atTIMESTAMPAccount creation time
modified_atTIMESTAMPLast record modification time (updated on password reset)
Indexes on approval_status and role: Both columns are indexed separately in MySQL (idx_users_approval_status, idx_users_role). This makes the admin console's filtered queries fast even as the user table grows.

password_reset_tokens table

Stores one-time password reset tokens. A separate table keeps token data isolated from the main user record.

ColumnTypeDescription
idINT (auto-increment)Primary key
user_idINT (FK → users.id)The account this token belongs to. Cascades on user deletion.
token_hashVARCHAR(255)SHA-256 hash of the raw token. The raw token is never stored.
expires_atDATETIMEToken becomes invalid after this time (1 hour from creation)
used_atDATETIMESet when the token is consumed. NULL if still valid and unused.
created_atTIMESTAMPRow creation time

14 Test Coverage Updated May 2026

The admin user management API is covered by a Jest test suite in src/utils/test/api_admin_users.test.ts. The test file mocks the database helper, session provider, and email module so that no real database connections or email sends occur during automated testing.

Test cases — GET /api/admin/users

Test caseExpected outcome
No session presentHTTP 401
Session belongs to a non-admin userHTTP 403
Admin session, no filtersHTTP 200 with user list
Admin session with status, role, and search filtersHTTP 200; SQL query verified to include correct WHERE clauses and parameters

Test cases — PATCH /api/admin/users

Test caseExpected outcome
Approve a user (status update)HTTP 200; database update verified with correct fields including approved_by
Approval email sent when user has an email address NEWsendApprovalEmail() called with correct email and username
Approval email skipped when user has no email address NEWsendApprovalEmail() not called; still returns HTTP 200
Approval email send fails NEWsendApprovalEmail() throws; endpoint still returns HTTP 200 (email failure is non-fatal)
Demote the only remaining adminHTTP 400 — "Cannot demote the only admin"
Change role when multiple admins existHTTP 200; database update verified
Mocking strategy: sendApprovalEmail is mocked using jest.mock('@/lib/email', () => ({ sendApprovalEmail: jest.fn() })) at the top of the test file. This means tests run in complete isolation — no real Resend API calls are made, and tests can control whether the mock resolves or rejects to verify the failure-resilience behaviour.
