Overview

Every authenticated user has a UserStrategy — a pair of preferences stored in the user_investment_strategy database table. These preferences are loaded on each API request and used to adjust recommendation thresholds, GPS scores, and predicted-price references in real time. The underlying ML model output and stored GPS data are never mutated; the strategy system applies lightweight transformations at read time.

The single source of truth for all strategy logic is src/utils/strategy.ts. This module exports the type definitions, the lookup tables, and the resolveStrategy() function that every route and the Python batch script depend on.

Dimension 1 — Aggressiveness

Controls how strict the filtering gates are. A safe investor sees only high-confidence, lower-volatility picks. An aggressive investor accepts lower GPS floors and a wider beta range in exchange for more picks.

Values: safe neutral aggressive

Default: neutral

Dimension 2 — Investment Timeframe

Controls which prediction horizon is used. The ML model produces four horizon outputs (1-week, 1-month, 6-month, 1-year). The timeframe setting selects the column referenced for recommendations, GPS patching, and UI labels.

Values: 1_week | 1_month | 6_month | 1_year

Default: 1_month

getUserStrategy(userId)

Async function exported from strategy.ts. Queries user_investment_strategy for the given user. If no row exists, or if stored values fail validation (isValidAggressiveness() / isValidTimeframe()), DEFAULT_STRATEGY is returned. All callers wrap this with .catch(() => DEFAULT_STRATEGY) so a DB failure degrades gracefully to defaults rather than returning a 500.

const userStrategy = await getUserStrategy(userId).catch(() => DEFAULT_STRATEGY);
Aggressiveness Gates

The AGGRESSIVENESS_GATES constant maps each aggressiveness level to a set of five numeric thresholds. These gates are applied to recommendation filtering across the portfolio, watchlist, and discovery scopes.

Gate safe neutral aggressive Description
confidenceFloor 65 50 35 Minimum AI model confidence score (0–100) required to include a stock
betaCutoff 1.5 2.0 3.5 Maximum beta coefficient — filters out stocks more volatile than this multiplier of the market
gpsGate 75 65 55 Minimum GPS score (0–100) required for a BUY recommendation
predChangeGate 3.0% 1.5% 0.5% Base minimum predicted price change (%) required — multiplied by predChangeMultiplier from the timeframe config
envFloorMultiplier 1.05 1.0 0.95 Applied to environment-variable threshold baselines (GPS BUY, SELL, DISCOVERY). Safe raises the bar by 5%; aggressive lowers it by 5%.
envFloorMultiplier application: In GET /api/dashboard/recommendations, the environment-variable thresholds (GPS_RECOMMENDATION_BUY_THRESHOLD, etc.) are multiplied by this value. For example, with a buy threshold of 85 and safe aggressiveness: effective threshold = 85 × 1.05 = 89.25. With aggressive: 85 × 0.95 = 80.75.
Timeframe Config

The TIMEFRAME_CONFIG constant maps each investment timeframe to properties that affect the prediction column selected, the threshold scaling, and the UI label.

Timeframe predChangeMultiplier sellThresholdShift mlGate predictedPriceColumn displayLabel
1_week 0.5 -2 0.5% predicted_price_1w "in 1 week"
1_month 1.0 0 1.5% predicted_price_1m "in 1 month"
6_month 1.5 +3 5% predicted_price_6m "in 6 months"
1_year 2.0 +5 10% predicted_price_1y "in 1 year"

Column interpretation

  • predChangeMultiplier — multiplied by predChangeGate from aggressiveness. Final predChange gate = aggressiveness.predChangeGate × timeframe.predChangeMultiplier. A 1-week / safe user needs 3.0 × 0.5 = 1.5% predicted change; a 1-year / aggressive user needs 0.5 × 2.0 = 1.0%.
  • sellThresholdShift — added to the environment-variable GPS SELL threshold. Long-horizon investors tolerate a lower GPS before calling a sell (they hold through dips). Short-horizon investors sell sooner (shift = -2 makes the threshold stricter).
  • mlGate — minimum predicted change % for a DeepMoney pick to be validated by the ML signal. Short horizons have a low bar (small moves matter in 1 week); long horizons require significant expected gain.
  • predictedPriceColumn — the SQL column in user_stock_predictions to use for the predicted price. The four columns are populated by scripts/update_predictions.py on each batch run.
resolveStrategy()

Function signature

export function resolveStrategy(strategy: UserStrategy): {
  gates: StrategyGates;    // from AGGRESSIVENESS_GATES[strategy.aggressiveness]
  timeframe: TimeframeConfig; // from TIMEFRAME_CONFIG[strategy.investment_timeframe]
}

This is the primary consumer-facing function. It accepts a UserStrategy and returns the two resolved config objects. All API routes and the Python script call the equivalent of this function to get the numeric values to apply.

Usage pattern in API routes

// Every strategy-aware route follows this pattern:
const userStrategy = await getUserStrategy(userId).catch(() => DEFAULT_STRATEGY);
const { gates, timeframe } = resolveStrategy(userStrategy);
const priceColumn = timeframe.predictedPriceColumn;

// SQL: select the horizon-appropriate predicted price
SELECT COALESCE(usp.${priceColumn}, usp.predicted_price_1m) AS predicted_price_horizon

// Threshold calculation (recommendations route):
const effectiveGpsGate     = gates.gpsGate;
const effectivePredChange  = gates.predChangeGate * timeframe.predChangeMultiplier;
const effectiveSellShift   = timeframe.sellThresholdShift;
const envMult              = gates.envFloorMultiplier;
const buyThreshold         = envBuyThreshold * envMult;
const sellThreshold        = envSellThreshold + effectiveSellShift;
GPS Horizon Patching

The problem

GPS scores and their component breakdowns are computed once and stored globally (in stock_gps_scores) using the 1-month ML prediction as the mlpUpside component. If a user's timeframe is 6 months, the stored GPS score reflects a 1-month prediction, which is misleading.

The solution — adjustMlpUpsideForHorizon()

The function adjustMlpUpsideForHorizon(breakdown, predictedChangePctForHorizon) in src/utils/gps.ts recalculates only the mlpUpside component using the user's horizon-specific predicted price, then recomputes the GPS total. The other 7 components (analyst consensus, revenue growth, etc.) are timeframe-independent and pass through unchanged.

// src/utils/gps.ts
export function adjustMlpUpsideForHorizon(
  breakdown: GpsBreakdown,
  predictedChangePctForHorizon: number
): { breakdown: GpsBreakdown; score: number } {
  const predictionMax = process.env.GPS_PREDICTION_MAX
    ? parseFloat(process.env.GPS_PREDICTION_MAX) : 3;

  // Re-clamp the mlpUpside component to [-20, +20]
  const newMlpUpside = Math.min(
    Math.max(predictedChangePctForHorizon / predictionMax, -1), 1
  ) * 20;

  const adjusted = { ...breakdown, mlpUpside: parseFloat(newMlpUpside.toFixed(1)) };
  const total = adjusted.mlpUpside + adjusted.mlpConfidence + adjusted.revenueGrowth
              + adjusted.earningsGrowth + adjusted.technicalSignal + adjusted.analystUpside
              + adjusted.analystConsensus + adjusted.priceChange52w;

  return {
    breakdown: adjusted,
    score: parseFloat(Math.min(Math.max(total, 0), 100).toFixed(1)),
  };
}

When it is called

Every route that returns GPS data to the client applies this patch per stock item, after fetching the live current price from Yahoo Finance:

// Shared pattern in portfolio, watchlist, and recommendations routes:
const horizonPrice = item.predicted_price_horizon != null
  ? parseFloat(item.predicted_price_horizon) : null;

if (baselineBreakdown && currentPrice > 0 && horizonPrice) {
  const horizonDeltaPct = ((horizonPrice - currentPrice) / currentPrice) * 100;
  const adjusted = adjustMlpUpsideForHorizon(baselineBreakdown, horizonDeltaPct);
  perUserGpsScore    = adjusted.score;
  perUserGpsBreakdown = adjusted.breakdown;
}
Why only mlpUpside changes: The 7 other GPS components — analyst consensus, revenue growth, earnings growth, technical signal, analyst upside, price change 52w, and ML confidence — are all computed from fundamental or technical data that does not change based on prediction horizon. Only the ML model's directional prediction varies per horizon.

GPS Breakdown Modal — horizon label

When the GPS breakdown modal is opened, it receives a horizon prop (type '1_week' | '1_month' | '6_month' | '1_year', default '1_month'). The ML Prediction row label is rendered as "ML Prediction (1m)", "ML Prediction (6m)", etc., so the user knows which horizon the displayed mlpUpside score reflects.

// GpsBreakdownModal.tsx
const HORIZON_LABEL = {
  '1_week':  '1w',
  '1_month': '1m',
  '6_month': '6m',
  '1_year':  '1y',
};
const mlpLabel = `ML Prediction (${HORIZON_LABEL[horizon] ?? '1m'})`;

The gpsHorizon field is now part of the DeepmoneyCard, PortfolioCard, and WatchlistCard types (in src/app/components/cards/types.ts) and is forwarded through GpsTooltip → GpsBreakdownModal.

How the Strategy Propagates

Affected API routes

RouteStrategy use
GET /api/user/portfolio Resolves priceColumn to select horizon-specific predicted price. Calls adjustMlpUpsideForHorizon() per holding. Returns gpsHorizon per item.
GET /api/user/watchlist Same as portfolio: horizon-aware GPS patch, returns gpsHorizon per item.
GET /api/dashboard/recommendations Computes effective thresholds: buyThreshold, sellThreshold, discoveryThreshold, predChangeGate, confidenceFloor, betaCutoff. Applies horizon GPS patch. Returns gpsHorizon per recommendation.
GET /api/dashboard/deepmoney-picks Reads user strategy to return timeframe (e.g., '6_month') and timeframe_label (e.g., 'in 6 months') for the UI display label on prediction cards.
GET /api/prediction/deepmoney Resolves user's outlook and mlGate. Cache key is bucketed by outlook (hot-tickers-enriched:{outlook}) so each timeframe has an independent 5-minute cache. Passes { outlook, mlGate } to analyzeStocks().
GET/PATCH /api/user/profile GET returns the full strategy object. PATCH accepts aggressiveness and/or investment_timeframe and upserts to user_investment_strategy.

Profile API — Strategy Endpoints

GET /api/user/profile — strategy in response

The profile GET endpoint includes the full strategy in its response JSON:

{
  "username": "kevin",
  "accountType": "superuser",
  "strategy": {
    "aggressiveness": "neutral",
    "investment_timeframe": "1_month"
  },
  "stats": { "lookupCount": 12, "portfolioItemCount": 5, "watchlistItemCount": 3 }
}

If no row exists in user_investment_strategy, the response includes DEFAULT_STRATEGY values.

PATCH /api/user/profile — updating strategy

The PATCH endpoint accepts two request body shapes. Both can update aggressiveness and/or timeframe independently — unset fields are preserved from the existing stored value.

// Nested shape (sent by the Profile component's aggressiveness save):
{ "strategy": { "aggressiveness": "safe" } }

// Flat shape (sent by the timeframe pill — optimistic update):
{ "investment_timeframe": "6_month" }

// Full nested update:
{ "strategy": { "aggressiveness": "aggressive", "investment_timeframe": "1_year" } }

// Response on success:
{ "message": "Strategy updated", "strategy": { "aggressiveness": "safe", "investment_timeframe": "6_month" } }

Upsert behavior

The route always loads the current stored strategy first, merges the incoming fields, validates the combined values, then upserts to user_investment_strategy. This means a partial PATCH that sends only aggressiveness will not reset investment_timeframe to the default.

Python Mirror (scripts/update_predictions.py)

The batch prediction script update_predictions.py contains an exact mirror of resolveStrategy() logic. When computing per-user ETF holding recommendations, the script loads all user strategies in a single query (get_all_user_strategies()), then applies the same aggressiveness gates and timeframe multipliers to decide whether each ETF holding crosses the recommendation threshold.

Python strategy functions

# update_predictions.py
AGGRESSIVENESS_GATES = {
    'safe':       {'gps_gate': 75, 'pred_change_gate': 3.0, 'env_floor_multiplier': 1.05, ...},
    'neutral':    {'gps_gate': 65, 'pred_change_gate': 1.5, 'env_floor_multiplier': 1.00, ...},
    'aggressive': {'gps_gate': 55, 'pred_change_gate': 0.5, 'env_floor_multiplier': 0.95, ...},
}
TIMEFRAME_CONFIG = {
    '1_week':  {'pred_change_multiplier': 0.5,  'predicted_price_col': 'predicted_price_1w', ...},
    '1_month': {'pred_change_multiplier': 1.0,  'predicted_price_col': 'predicted_price_1m', ...},
    '6_month': {'pred_change_multiplier': 1.5,  'predicted_price_col': 'predicted_price_6m', ...},
    '1_year':  {'pred_change_multiplier': 2.0,  'predicted_price_col': 'predicted_price_1y', ...},
}

def resolve_strategy(aggressiveness, investment_timeframe):
    gates = AGGRESSIVENESS_GATES.get(aggressiveness, AGGRESSIVENESS_GATES['neutral'])
    tf    = TIMEFRAME_CONFIG.get(investment_timeframe, TIMEFRAME_CONFIG['1_month'])
    env_base = float(os.getenv('ETF_HOLDING_GPS_SURFACE_VALUE', 60))
    mult     = gates['env_floor_multiplier']
    return {
        'gps_threshold':  env_base * mult,
        'pred_threshold': max(env_base * mult, gates['pred_change_gate'] * tf['pred_change_multiplier']),
        'conf_threshold': env_base * mult,
        'price_col':      tf['predicted_price_col'],
    }
Keep in sync: Whenever AGGRESSIVENESS_GATES or TIMEFRAME_CONFIG values change in src/utils/strategy.ts, the corresponding Python dicts in scripts/update_predictions.py must be updated to match. These two files are the dual source of truth for strategy gate values.
