SEO & Public Access

Last updated: 2026-05-25 Next.js 14 App Router 3 indexed pages

Overview

GrowMyStocks is a gated application — almost every page requires a valid session. Only three pages are intentionally open to search engines: the landing page, login, and register. Everything else (dashboard, portfolio, watchlist, admin) is protected behind NextAuth session middleware.

Indexed by search engines

Three pages carry robots: index: true and appear in the sitemap. These are the only pages Google, Bing, and other crawlers are allowed to index.

  • / — Landing page
  • /login — Login page
  • /register — Register page

Public but NOT indexed

These pages are accessible without login but are explicitly blocked from indexing. They serve users who follow a direct link but should not show up in search results.

  • /legal/privacy
  • /legal/terms
  • /legal/disclaimer
  • /contact
  • /forgot-password
  • /reset-password
The global default in src/app/layout.tsx sets robots: index: false for the whole app. Individual pages override this to index: true only where needed. This "deny by default" approach means new pages are safe until explicitly opted in.

Sitemap

The sitemap is auto-generated by Next.js from a TypeScript file. There is no static sitemap.xml to maintain — Next.js builds and serves it dynamically at /sitemap.xml.

File location

src/app/sitemap.ts

Current entries

https://growmystocks.com/           priority: 1.0   weekly
https://growmystocks.com/login      priority: 0.8   monthly
https://growmystocks.com/register   priority: 0.8   monthly

How to add a page to the sitemap

Open src/app/sitemap.ts and add a new entry to the returned array: 

return [
  // ... existing entries ...
  {
    url: `${siteUrl}/your-new-page`,
    lastModified: new Date('2026-05-25'),  // use the actual publish date
    changeFrequency: 'monthly',            // 'always'|'hourly'|'daily'|'weekly'|'monthly'|'yearly'|'never'
    priority: 0.7,                         // 0.0 – 1.0
  },
]
Always use a static date for lastModified — never new Date(). Using new Date() tells Google the page changes on every crawl, which wastes crawl budget and can suppress rankings.

Verify the sitemap

Start the dev server and visit: 

http://localhost:3001/sitemap.xml

Submit to search engines

  • ✓Google Search Console — go to Sitemaps → enter sitemap.xml → Submit
  • ✓Bing Webmaster Tools — Sitemaps → Submit sitemap URL
  • ✓robots.txt already points to it — crawlers can auto-discover it without manual submission

robots.txt

Like the sitemap, robots.txt is generated by Next.js from a TypeScript file — not a static file.

File location

src/app/robots.ts

What it does

The file defines two rule sets:

  • Search bots (Googlebot, Bingbot, etc.) — allowed to crawl /, /login, /register, and /legal/*. Blocked from /dashboard, /portfolio, /admin, and /api/*.
  • Social crawlers (Facebookbot, Twitterbot, etc.) — allowed to crawl / for OG tag reading. Blocked from /api/*.

The sitemap URL is declared at the bottom so all crawlers can auto-discover it.

Verify it

http://localhost:3001/robots.txt

Page Metadata

Each of the three indexed pages has its own metadata: title, description, canonical URL, Open Graph tags, and Twitter Card tags. Metadata is defined in server components using Next.js's Metadata API.

Where metadata lives

src/app/page.tsx
Landing page (/) — exports metadata constant. This is a thin server wrapper around LandingPage.tsx.
src/app/login/layout.tsx
Login page metadata. Uses a layout instead of page because login/page.tsx is a client component ('use client') and client components cannot export metadata.
src/app/register/layout.tsx
Register page metadata. Same pattern as login — layout exports metadata, page is a client component.
src/app/layout.tsx
Root layout — sets site-wide defaults including robots: index: false (deny-by-default), fallback OG/Twitter images, and metadataBase.
src/app/legal/layout.tsx
Legal pages layout — overrides to robots: index: false, follow: true. Applies to all three legal routes automatically.

Title rules

  • ✓Keep page titles under 60 characters (Google truncates at ~60)
  • ✓The root layout uses a title template: '%s | GrowMyStocks' so child pages only need to set their own part
  • ✓Landing page overrides the full title directly (does not use the template) to avoid "GrowMyStocks | GrowMyStocks"

Description rules

  • ✓Keep meta descriptions under 160 characters (Google truncates beyond that)
  • ✓Write for humans, not keywords — Google rewrites descriptions it doesn't like anyway
  • ✓Each public page has a unique description

Canonical URLs

Each indexed page sets alternates.canonical to its absolute URL. This tells Google the "official" URL and prevents duplicate content penalties if the page is ever accessible via multiple paths. 

// Example from src/app/login/layout.tsx
alternates: {
  canonical: `${siteUrl}/login`,
}
siteUrl is read from the NEXT_PUBLIC_SITE_URL environment variable. Set this to https://growmystocks.com in your Bluehost production environment. Locally it defaults to https://growmystocks.com.

Open Graph / Social Images

Each indexed page has a dynamically generated 1200×630 PNG social card using Next.js's next/og ImageResponse API. These cards appear when the page is shared on Facebook, X/Twitter, LinkedIn, Slack, iMessage, etc.

File locations

src/app/opengraph-image.tsx
Landing page card. Served at /opengraph-image. Design: green gradient, brand name, tagline, feature pills.
src/app/login/opengraph-image.tsx
Login page card. Served at /login/opengraph-image. Subtitle: "Sign In to Your Account".
src/app/register/opengraph-image.tsx
Register page card. Served at /register/opengraph-image. Subtitle: "Create Your Free Account".

How to preview them

With your dev server running, open these URLs directly in your browser:

http://localhost:3001/opengraph-image
http://localhost:3001/login/opengraph-image
http://localhost:3001/register/opengraph-image
These paths must be in PUBLIC_PATHS in src/proxy.ts, otherwise the auth middleware will redirect them to login — breaking social sharing.

How they work

Each opengraph-image.tsx file exports:

  • runtime = 'edge' — uses the Edge runtime for fast generation
  • size = { width: 1200, height: 630 } — standard OG image dimensions
  • contentType = 'image/png'
  • A default export that returns a new ImageResponse(...) with JSX layout

Next.js detects these files and automatically injects <meta property="og:image"> and <meta name="twitter:image"> into the page's <head>.

How to update the design

Edit the JSX inside new ImageResponse(...). Only inline styles work — no CSS modules, no Tailwind classes. The JSX subset supported is limited (no display: grid, no complex CSS). Stick to display: flex, flexDirection, and gap.

Testing on social platforms

Once deployed to a public URL, use these tools to see exactly how your card will look:

  • ✓Facebook — developers.facebook.com/tools/debug — paste URL, hit Debug, then "Scrape Again" to refresh cache
  • ✓X / Twitter — cards-dev.twitter.com/validator
  • ✓LinkedIn — linkedin.com/post-inspector
  • ✓Any platform — opengraph.xyz — shows all OG tags and a visual preview

JSON-LD Structured Data

JSON-LD is machine-readable markup that helps Google understand what your page is about. It can produce rich results (enhanced listings) in search. Each of the three indexed pages has JSON-LD injected via a <script type="application/ld+json"> tag.

Schemas in use

/ — Landing page

Two schemas in a @graph:

  • WebApplication — describes GrowMyStocks as a free-to-register finance app
  • Organization — links brand name and logo

/login & /register

Single WebPage schema on each, with:

  • name, url, description
  • isPartOf pointing to the parent WebSite

Where the code lives

JSON-LD is defined as a module-level const jsonLd = {...} in the server component and injected via: 

<script
  type="application/ld+json"
  dangerouslySetInnerHTML={{ __html: JSON.stringify(jsonLd) }}
/>
This pattern works because page.tsx, login/layout.tsx, and register/layout.tsx are all server components. Client components ('use client') cannot inject <script> tags this way.

Validate it

Use Google's Rich Results Test once deployed: search.google.com/test/rich-results. It will show which schemas were detected and flag any errors.

Middleware & Auth Gates

The auth wall is enforced in a single file. Understanding it is critical for SEO — if a path isn't in PUBLIC_PATHS, crawlers get a redirect to /login instead of the page, and it will never be indexed.

File location

src/proxy.ts

How it works

NextAuth's withAuth wrapper runs on every request matched by the config.matcher regex. The authorized callback decides whether to allow the request through:

  1. If the path is in PUBLIC_PATHS → allow (no session required)
  2. If a valid x-api-key header is present → allow (internal service bypass)
  3. If a valid session token exists → allow
  4. Otherwise → NextAuth redirects to /login

Every request that passes through also gets a CSP nonce header added by the inner middleware function.

Current PUBLIC_PATHS

const PUBLIC_PATHS = [
  '/',
  '/login',
  '/register',
  '/forgot-password',
  '/reset-password',
  '/api/unsubscribe',
  '/contact',
  '/api/contact',
  '/legal/privacy',
  '/legal/terms',
  '/legal/disclaimer',
  '/opengraph-image',           // social card images
  '/login/opengraph-image',
  '/register/opengraph-image',
  '/sitemap.xml',               // crawlers need these
  '/robots.txt',
  '/api/analytics/model-accuracy', // public — powers landing page "Proven Track Record" stats
]
If you add a new page that should be public (indexed or not), you must add its path to PUBLIC_PATHS or it will redirect to login for everyone — including Google's crawler.

Matcher regex

The matcher controls which paths the middleware even runs on. Static files and Next.js internals are excluded here so they don't need to be in PUBLIC_PATHS: 

matcher: [
  "/((?!api/auth|_next/static|_next/image|growmystock_logo\\.svg|growmystock_logo_dark\\.svg|favicon\\.ico).*)",
]

Anything excluded from the matcher bypasses the middleware entirely (no auth check, no CSP header). Anything inside the matcher but not in PUBLIC_PATHS requires a session.

Adding a New Public Page

Follow all steps — skipping any one of them will either break access or result in the page not being indexed.

If the page should be indexed by Google

  1. Add to PUBLIC_PATHS

    In src/proxy.ts, add the path to the PUBLIC_PATHS array so unauthenticated visitors (and crawlers) can reach it.

  2. Add metadata with robots: index: true

    In the page's page.tsx (server component) or a layout.tsx, export a metadata object with robots: { index: true, follow: true }, a unique title, description, and alternates.canonical.

  3. Create an opengraph-image.tsx

    In the route's directory, add an opengraph-image.tsx file. Copy an existing one and update the subtitle text. This generates the social sharing card.

  4. Add the OG image path to PUBLIC_PATHS

    The generated image (e.g. /your-page/opengraph-image) also needs to be in PUBLIC_PATHS or social crawlers will be blocked from fetching it.

  5. Add to sitemap.ts

    In src/app/sitemap.ts, add a new entry with the URL, a static lastModified date, changeFrequency, and priority.

  6. Add JSON-LD (optional but recommended)

    Add a <script type="application/ld+json"> with a WebPage schema in the server component.

If the page should be public but NOT indexed

  1. Add to PUBLIC_PATHS

    Same as above — required for access.

  2. Do NOT add metadata with index: true

    The global default (robots: index: false from the root layout) will apply automatically. No action needed — just don't override it.
