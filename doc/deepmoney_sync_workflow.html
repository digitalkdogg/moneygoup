DeepMoney Analysis Workflow (v2.8)

The DeepMoney sync is a background batch process (typically run as a cron job) that discovers, validates, and persists AI-curated stock recommendations and ETF picks to the database. The results power the dashboard's "AI Picks" panel, the discovery recommendations feed, and the macro context snapshot visible to all approved users.

v2.8 changes (2026-06-20): Same single-knob pattern extended to the ETF holdings pipeline. New env var ETF_HOLDING_ALGORITHM (float 1.0–10.0, default 5) resolves via models/etf_holding_presets.json into five fields — etfGpsThreshold, topNEtfs, maxTickers, gpsSurfaceValue, minPredChangePct — all used by ETF qualification in etfDiscovery.ts, holdings scoring in etfHoldings.ts, the read-side /holdings route, the DeepMoney Picks widget, and the per-user predictions sync (via scripts/etf_holding_preset.py). Fractional levels interpolate linearly; count fields round to integers. Retired: ETF_GPS_THRESHOLD (in-code constant), ETF_HOLDING_MAX_TICKERS, ETF_HOLDING_GPS_SURFACE_VALUE, ETF_HOLDING_MIN_PRED_CHANGE.
v2.7 changes (2026-06-19): Collapsed all pipeline tuning to a single env var, DEEPMONEY_ALGORITHM (float 1.0–10.0, default 5), resolved via models/algorithm_presets.json into five fields: rankerKeepPct, mlpConfidenceFloor, volGateFloor, analystStrongBuyThreshold, signalScoreFloor. The LightGBM ranker is now mandatory and is the primary stock-level filter (keep top rankerKeepPct by rank percentile). An analyst-strongBuy override lane runs alongside the ranker — any pre-filtered stock with analyst strongBuy count ≥ analystStrongBuyThreshold (also scaled by level) bypasses the ranker keep-cut and the mlGate floor (still must yield positive predicted change). Stage 1 additionally merges holdings of ~20 popular ETFs into the candidate pool and scrapes the Yahoo Finance earnings calendar; new feeds added for oilprice.com, Defense News (land+space JSON), DIA, and a simpler SEC Form 4 endpoint. The GPS-Light path is gone; gps_score_type is always 'full'. Retired env vars: DEEPMONEY_GPS_VALUE, DEEPMONEY_RECOMMENDATION_GPS_VALUE, DEEPMONEY_ANALYST_THRESHOLD, DEEPMONEY_USE_RANKER_GATE, DEEPMONEY_TIER2_TOPK.
v2.6 changes (2026-06-18): Added the Path-A cross-sectional ranker integration (feature-flagged via DEEPMONEY_USE_RANKER_GATE). Two-pass flow in analyzer.ts: Tier-1 GPS-Light + ranker score for the full universe, Tier-2 Monte Carlo only on the top-K promoted set. Schema additions to recommended_stocks and stock_gps_scores: gps_score_type, ranker_score, hist_vol_30. End-of-run funnel summary block. ETF holdings endpoint now reads from stock_gps_scores directly (retiring the dead etf_holding_scores cache). Superseded by v2.7 — the feature flag and tier-K env vars no longer exist.
v2.5 changes (2026-06-15): Documented strategy-driven mlGate wiring in the API route (timeframe-aware prediction floor), in-process _indices_cache helper, outlook-bucketed cache key, and corrected record_prediction semantics to ON DUPLICATE KEY UPDATE (not INSERT IGNORE).
Scope note: This script writes only to recommended_stocks (both hot_stocks and etf_holding rows), macro_context_snapshots, stocks, stock_gps_scores, user_stock_predictions, and user_stocks. Analytics inserts also touch prediction_records via scripts/prediction_recorder.py. It does not write to etf_stock_recommendations — that table is populated by scripts/update_predictions.py.

0 Entrypoint & Environment Loading

scripts/deepmoney_sync.py — module scope + __main__

The file is a single-module script; if __name__ == "__main__": sync_deepmoney() is the only entrypoint. There is no CLI argument parsing — all configuration is environment-driven.

Environment loading order (later wins; load_dotenv does not overwrite by default, so the first file with a key wins):

  1. .env.production (if present)
  2. .env.local (if present)
  3. .env

Required env vars: DB_HOST, DB_USER, DB_PASSWORD, DB_DATABASE, DEEPMONEY_INTERNAL_SECRET. Optional knobs: DEEPMONEY_ALGORITHM (float 1.0–10.0, default 5), NEXTAUTH_URL (read but not used for the discovery call).

Module-level cache: _indices_cache is a process-local variable used by get_market_indices(). The first call hits /api/market/indices; subsequent calls inside the same run return the memoized payload. The function is currently defined but not called inside sync_deepmoney() — it is exported infrastructure for future use or for callers that import the module.

1 Macro Data Sync

scripts/get_macro_data.py + /api/worldbank

The foundation of the daily sync. fetch_world_bank_data() calls GET /api/worldbank via the internal localhost URL to fetch consolidated World Bank macroeconomic indicators.

  • Indicators: GDP Growth, Inflation, FDI, Trade Volume, Tech Adoption (Internet/ICT), Unemployment.
  • Countries: USA, GBR, CHN, IND, DEU.
  • Persistence: When wb_data.success is true, the script issues an INSERT ... ON DUPLICATE KEY UPDATE against macro_context_snapshots using today's date as the key. Stored fields: global_health_score, unemployment_rate, unemployment_signal, inflation_rate, gdp_growth.
  • Failure mode: the helper returns None on any network error and the script proceeds without writing a macro snapshot for that day — the stock sync still runs.

2 DeepMoney Discovery Trigger

scripts/deepmoney_sync.py — sync_deepmoney()

Initiates the core stock discovery cycle by calling the internal API endpoint.

  • Authorization: Uses DEEPMONEY_INTERNAL_SECRET via the x-api-key header. The secret is stripped of surrounding quotes before use to handle environment variable formatting quirks (secret = INTERNAL_SECRET.strip('"')).
  • Internal URL: All calls use INTERNAL_API_URL = 'http://localhost:3001' (hardcoded). This bypasses nginx and its 60-second proxy timeout — the discovery route can take over 2 minutes.
  • Endpoint called: GET /api/prediction/deepmoney?refresh=true
  • Discovery methods (server-side, Stage 1): Primary tickers come from ~28 RSS / screener / atom / JSON sources (Yahoo, MarketBeat, TheStreet, Motley Fool, CNBC, MarketWatch, Seeking Alpha, SEC EDGAR 8-K + two Form-4 endpoints, ApeWisdom, sector verticals, oilprice.com, Defense News land/space JSON via Arc Publishing, DIA). The set is then expanded by a secondary Yahoo per-ticker-feed pass (capped at 30). Three additional Stage-1 sources merge in parallel with the secondary pass: the top holdings of ~20 popular ETFs (POPULAR_ETF_TICKERS, fetched via the internal /holdings endpoint), the Yahoo Finance earnings calendar (HTML scraped for /quote/<TICKER> links), and the internal trending feed (fetchTrendingTickers calls GET /api/market/trending?window=48h&limit=50). Everything dedups into a single allTickersSet before enrichment. ETFs themselves are surfaced via performETFDiscovery().
Maintenance note: If the Next.js server port ever changes from 3001, INTERNAL_API_URL must be updated manually in each Python script — it is not controlled by an environment variable. The same hardcoded constant exists in scripts/get_macro_data.py and other sync scripts.

The response includes a meta.debug object logged during the sync showing pipeline stage counts: stocks rejected by enrichment, by signal score, by insufficient history (<100 trading days), passed to the analyzer, rejected by the LightGBM ranker, analyst-consensus surfaced, and final filtered count. meta.algorithm echoes the resolved DEEPMONEY_ALGORITHM preset so the Python sync uses the same gate values the server applied.

Parsing branches in fetchPrimaryTickers:

  • RSS / Atom (default): extractTextFromRSS walks <item> elements, joins <title> + <description>, runs the TICKER_PATTERNS regex set ($AAPL, (AAPL), Nasdaq: AAPL, NYSE: AAPL, AAPL stock).
  • SEC Form 4 atom: matched by URL pattern (type=4 + output=atom). Parsed via fast-xml-parser; tickers pulled from each entry's edgar:issuerTradingSymbol directly — no regex.
  • JSON — ApeWisdom: data.results[].ticker with a 5-mention 24h-ago pre-filter to drop low-signal noise.
  • JSON — Yahoo screener: data.finance.result[0].quotes[].symbol.
  • JSON — Arc Publishing (Defense News): walks data.content_elements[] joining each story's headlines.basic, subheadlines.basic, description.basic, then runs the same RSS-style ticker regex.

Every URL is fetched concurrently via Promise.allSettled with a 15-second timeout. Per-feed failures (timeouts, 4xx blocks, parse errors) are non-fatal — the run completes with whatever subset succeeded.

Secondary expansion: after the primary pass, the first 30 primary tickers (MAX_SECONDARY = 30) are each used to fetch a Yahoo per-ticker feed (feeds.finance.yahoo.com/rss/2.0/headline?s=<TICKER>), and any additional tickers mentioned in those feeds are added to the candidate pool. This typically doubles the discovered ticker count without re-hitting the broader news sources.

Strategy-Driven ML Gate (Server Side)

Inside src/app/api/prediction/deepmoney/route.ts, the API resolves the caller's strategy via getUserStrategy() → resolveStrategy() to obtain a TimeframeConfig. Two values flow downstream:

  • outlook — passed to the analyzer so prediction calls run against the requested horizon (1_week / 1_month / 3_month / 6_month).
  • mlGate — the minimum positive predicted_change_pct a candidate must show to survive the analyzer filter. Per-horizon values are defined in TIMEFRAME_CONFIG in src/utils/strategy.ts; see the Strategy System doc.

The response cache key is bucketed by outlook (hot-tickers-enriched:${outlook}) so each timeframe maintains its own 5-minute snapshot. ?refresh=true bypasses the cache.

When called by deepmoney_sync.py the request has no session cookie — only the x-api-key header — so sessionUserId is undefined and the route falls back to DEFAULT_STRATEGY (neutral / 1_month), giving mlGate = 1.5 and outlook = '1_month'. That is why the Python pipeline's hardcoded pred_threshold = 1.5 matches the server-side default — the two stay in sync as long as the Python script remains unauthenticated.

The aggressiveness gates (confidenceFloor, betaCutoff, gpsGate, predChangeGate, envFloorMultiplier) live in AGGRESSIVENESS_GATES in the same file and apply to interactive recommendation surfaces; the sync script itself does not consume them — it uses its own env-driven GPS gates and a fixed prediction threshold.

Volatility-Adjusted Confidence Gate (preset-driven, v2.7)

Each candidate is evaluated against a confidence threshold pulled from the resolved meta.algorithm preset. The floor scales with beta: low-beta stocks use mlpConfidenceFloor, high-beta stocks (> 2.5) use the higher volGateFloor.

conf_score = pred_input.get('confidence_score') or pred_input.get('confidence_score_1m') or 0
beta_val = s.get('beta') or 1.0

confidence_floor = vol_gate_floor if beta_val > 2.5 else mlp_confidence_floor
if conf_score < confidence_floor:
    print(f"  [vol-gate] SKIP {ticker}: CS {conf_score} < floor {confidence_floor} (beta {beta_val:.2f})")
    counters["vol_gate_rejected"] += 1
    continue

Rationale: high-beta stocks amplify both upside and downside. The model's confidence score already reflects data quality and historical accuracy, but a confidence of, say, 52 on a stock with beta 3.5 represents a riskier recommendation than the same score on a beta-1.0 stock. The two-floor scheme enforces a higher evidentiary bar for volatile names.

Beta rangeMinimum confidence score
beta ≤ 2.5mlpConfidenceFloor (preset)
beta > 2.5volGateFloor (preset, always ≥ mlpConfidenceFloor)

Example values: at DEEPMONEY_ALGORITHM=5 the floors are 60 / 65; at level 1 they are 75 / 75; at level 10 they are 30 / 35. See Environment Config for the full table. Floors are calibrated to the MLP's discrete confidence-score buckets observed at runtime ({35, 50, 65, 75}).

ATH Proximity Warning Flag

Stocks that pass all gates but are near their 52-week high with elevated beta receive a warning appended to the metric_label stored in recommended_stocks:

hi_ratio = s.get('hiRatio52w') or 0
if hi_ratio > 0.97 and beta_val > 2.0:
    print(f"  [ath-warn] {ticker}: Near ATH ({hi_ratio:.2%}) with high beta ({beta_val:.2f})")
    metric_lbl = f"{metric_lbl} ⚠️ATH" if metric_lbl else "⚠️ATH"

The ⚠️ATH label is visible in the admin dashboard view and any UI component that renders metric_label. It does not cause the stock to be filtered out — it is informational only, surfacing the same mean-reversion risk that the High-Beta Penalty in the prediction model already penalizes in the price target itself.

Conditions: hiRatio52w > 0.97 (price is within 3% of the 52-week high) AND beta > 2.0.

4 Dashboard Qualification

deepmoney_sync.py — MLP confidence floor (from algorithm preset)

Stocks that passed the volatility-adjusted gate are then evaluated for inclusion in individual user dashboards. GPS-based dashboard gating has been retired; the gate is now on the MLP's own 1-month confidence score:

  • Confidence threshold: conf_score_1m ≥ mlpConfidenceFloor (resolved from DEEPMONEY_ALGORITHM via meta.algorithm).
  • Prediction gate: predicted_change_pct ≥ 1.5% (hardcoded as pred_threshold = 1.5; this matches the neutral / 1-month mlGate in TIMEFRAME_CONFIG).

Before this gate runs, every qualifying stock is upserted into stocks (insert when missing) and its GPS score is upserted into stock_gps_scores via INSERT ... ON DUPLICATE KEY UPDATE — but only if the GPS score has actually changed when rounded to one decimal place. Unchanged scores are skipped to keep as_of timestamps meaningful. The write uses source = 'deepmoney_sync'.

When a stock additionally passes both Dashboard thresholds, the script iterates over every approved user (fetched once via SELECT id FROM users WHERE approval_status = 'approved') and upserts:

  • user_stock_predictions: predicted_price_1m + last_requested_at = NOW(). (GPS columns were removed from this table — they now live in stock_gps_scores.)
  • user_stocks: is_purchased = 0, user_confirmed = 0, is_active = 1. The ON DUPLICATE KEY UPDATE clause is guarded so confirmed/purchased positions are never overwritten (user_confirmed = IF(is_purchased = 0, 0, user_confirmed), is_active = IF(is_purchased = 0, 1, is_active)).

Qualifying stock_ids are also collected into a qualifying_stock_ids set used by the post-sync cleanup (Step 6).

5 ETF Holdings

deepmoney_sync.py — hot_etfs loop + /api/stock_data/[ticker]/holdings

For every hot ETF returned in data.hot_etfs, the script fetches GET /api/stock_data/{etf_ticker}/holdings (30-second timeout). The endpoint pulls the live holdings list from yfinance, then enriches each holding with its current GPS score for surfacing.

v2.6 change (2026-06-18): The endpoint now reads holding scores from stock_gps_scores joined to stocks by symbol. Previously it read from etf_holding_scores — a cache that the /deepmoney discovery route stopped populating (skipHoldingsScoring: true at route.ts:538), causing the cache to go stale and the sync to surface 0 holdings most days. The new query path is independent of any cache refresh schedule and reflects whatever the analyzer just wrote this run.

Surfacing criteria (in holdings/route.ts):

  • gps_score ≥ preset.gpsSurfaceValue — resolved from ETF_HOLDING_ALGORITHM via models/etf_holding_presets.json (default level 5 = 60).
  • Breakdown's mlpUpside component clears (preset.minPredChangePct / GPS_PREDICTION_MAX) × 20. With level-5 defaults (1.8% / 3), this is mlpUpside ≥ 12. The proxy works because mlpUpside = clip(predicted_change_pct / GPS_PREDICTION_MAX, -1, 1) × 20 in calculateGpsScore, so the inverse recovers a predicted_change_pct threshold from the stored breakdown alone — no extra columns required.

predicted_change_pct and bearish_signal are still returned in the response shape (recovered from mlpUpside) so existing consumers don't break. beta is always null now — it isn't stored in stock_gps_scores, and the surfacing logic no longer enforces a beta cap. The ETF_HOLDING_MAX_BETA env var is kept for backward compatibility but is no longer read by the read-side route.

For each holding flagged surfaced: true, a row is inserted into recommended_stocks with:

  • type = 'etf_holding'
  • parent_etf_ticker, holding_percent, the looked-up gps_score and gps_breakdown
  • bearish_signal = 0 (surfaced = non-bearish by definition)
  • classification = 'ETF Holding'
  • discovery_source = "etf_holdings/{etf_ticker}"
  • metric_label = score_source (e.g. cached / live) for traceability
  • snapshot_date = today

A counter (holdings_written) is printed at the end of the loop. Holding rows share the same recommended_stocks table as hot stocks and are distinguished only by type.

Tuning note: If holdings rarely surface in your environment, check the distribution of stock_gps_scores.gps_score against preset.gpsSurfaceValue (resolved from ETF_HOLDING_ALGORITHM). Levels ≤ 2 set the floor to 72–75 and produce near-empty holding sets on most market days since the analyzer's GPS output peaks in the 50–60 range during typical conditions. Raise ETF_HOLDING_ALGORITHM (toward 10) to loosen all five ETF gates at once.

5.5 Dashboard Tenure Reconciliation new

deepmoney_sync.py — dashboard_tenure UPSERT block (after ETF holdings, before stale-discovery cleanup)

Tracks how many consecutive days each hot-stocks ticker has appeared on the dashboard so /api/dashboard/recommendations and /api/dashboard/deepmoney-picks can rotate stale mega-caps off the Recommendations section. See dashboard_tenure for the table schema.

Why this step exists outside recommended_stocks

The sync's first act is DELETE FROM recommended_stocks (see step 6) — so tenure state cannot live inside that table. Instead, the sync stashes the pre-DELETE ticker set into a Python set before the wipe, then reconciles it against the just-inserted set here after all hot-stocks and ETF-holdings inserts have committed.

Three branches per ticker

Set membershipSQL actionEffect
Returning — in both prior and current sets UPDATE dashboard_tenure SET consecutive_days = consecutive_days + CASE WHEN last_seen_at < today THEN 1 ELSE 0 END, last_seen_at = today, evicted_at = NULL WHERE ticker = ? Streak advances only when a calendar day has actually passed — same-day re-runs of the sync don't double-count. Clears any lingering evicted_at defensively.
New arrival — in current only INSERT ... ON DUPLICATE KEY UPDATE first_seen_at = today, last_seen_at = today, consecutive_days = 1, evicted_at = NULL Brand-new tickers get a fresh row. Tickers returning from a prior eviction have their streak reset — they're treated as a new arrival, not a continuation of the old stint.
Evicted — in prior only UPDATE dashboard_tenure SET evicted_at = NOW() WHERE ticker = ? AND evicted_at IS NULL Stamps the drop-out moment so the API cooldown filter (DASHBOARD_TENURE_COOLDOWN_DAYS) can hold the ticker out for a few syncs before re-admitting it.

What's tracked

Only type = 'hot_stocks' rows participate. ETF holdings rotate via their parent-ETF cadence and their tenure is not tracked. Sector-leader and trending-48h fast-path stocks that never land in recommended_stocks are also not tracked — the reconciliation is scoped to what's actually about to render on the dashboard.

Counter output: The end-of-run summary block reports dashboard_tenure_new, dashboard_tenure_returning, and dashboard_tenure_evicted so you can see how much churn is happening day to day. Log line at the end of the block: "Dashboard tenure: N new, R continuing, E evicted."

Env vars that consume this state

All read-side; the sync writes unconditionally regardless of these values. See Overview → Dashboard Rotation env vars for full docs.

  • DASHBOARD_TENURE_ROTATION — master switch (default on)
  • DASHBOARD_TENURE_MAX_DAYS — days-in-streak before demotion (default 7)
  • DASHBOARD_TENURE_COOLDOWN_DAYS — hold-out after eviction (default 5)
  • DASHBOARD_TENURE_TARGET_CARDS / DASHBOARD_TENURE_MIN_CARDS — cap + backfill floor for the rotatable pool

6 Persistence & Stale Entry Cleanup

deepmoney_sync.py — post-sync cleanup + off-market mover scan

The sync begins with a hard DELETE FROM recommended_stocks — the table is fully rebuilt every run with today's snapshot_date. Hot stocks, ETF holdings (type = 'etf_holding'), and off-market movers (type = 'off_market_mover') all share this same table.

Off-Market Movers August 2026

After all stocks and ETF holdings are processed, sync_off_market_movers() scans the full processed ticker universe for pre- and post-market moves. Qualifying movers (absolute move ≥ OFF_MARKET_MIN_CHANGE_PCT = 3.0%, positive metric_value) are written to recommended_stocks with type = 'off_market_mover' and snapshot_date = today, replacing any previous rows for that date. Market states POSTPOST and PREPRE (overnight Yahoo states) are normalized to POST for storage. The full ticker universe (all_processed_tickers) is used — not just ranker survivors — so any stock the sync touched can appear as a mover regardless of its GPS fate.

Stale discovery entries from previous runs are then removed. The approach is exact: only stocks that did not qualify in today's run (i.e., not in qualifying_stock_ids) and are still marked as active unconfirmed discoveries are removed from user_stocks and user_stock_predictions.

If qualifying_stock_ids is empty (degenerate case), all active unconfirmed discoveries are eligible for removal — purchased positions remain untouched because of the user_confirmed = 0 filter.

This post-sync cleanup replaced an earlier pre-clear approach and is safe for concurrent runs because it only touches is_active = 1 AND user_confirmed = 0 rows — confirmed (user-purchased) positions are never removed.

The entire DB block is wrapped in try / except; on any error the transaction is rolled back and the cursor/connection are closed in finally.

Analytics Recording corrected 2026-06-15

For every qualifying hot stock with a current price and at least one horizon prediction, deepmoney_sync.py fires a per-stock record_prediction() call (imported from scripts/prediction_recorder.py). This writes a row to the prediction_records analytics table using INSERT ... ON DUPLICATE KEY UPDATE keyed on (symbol, predicted_at = CURDATE()):

  • If no row exists for the symbol today, it is inserted and the recorder prints [analytics] Prediction recorded for <ticker>.
  • If a row already exists, the recorder uses COALESCE(VALUES(col), col) to fill in any horizon columns that were previously null, refreshes price_at_prediction and updated_at, and prints [analytics] Duplicate prediction (ignored) for <ticker> on same day.

Each call opens its own MySQL connection — the recorder is independent of the sync script's connection. The payload includes all four horizons:

record_prediction(
    symbol=ticker,
    price_at_prediction=price,
    predicted_price_1w=predicted_price_1w,
    predicted_price_1m=predicted_price_1m,
    predicted_price_3m=predicted_price_3m,
    predicted_price_6m=predicted_price_6m,
)

This call is independent of the GPS / user-dashboard logic — it runs as soon as the stock passes the ML gate + volatility gate, before the Dashboard Qualification threshold is checked. The result feeds the /api/analytics/model-accuracy endpoint and the ModelAccuracyWidget headline direction-accuracy metric (Prediction Tracking System, Phase 2–5).

End-of-Run Summary new 2026-06-18

The script prints a structured funnel summary at the end of every run, regardless of whether the main DB transaction committed or rolled back. The summary lives in _print_run_summary() and is invoked from the finally block, so partial-run numbers still print on exceptions.

8 Cross-sectional Ranker + Analyst Override v2.7 hard filter

analyzer.ts + scripts/score_ranker.py + models/ranker_v1_regression.txt

As of v2.7 the LightGBM ranker is the primary stock-level filter. It is no longer feature-flagged: the analyzer always fetches OHLCV payloads for the full pre-filtered universe, scores everything with the trained LightGBM model in one batch, sorts by rank_pct descending, and keeps only the top rankerKeepPct fraction (resolved from DEEPMONEY_ALGORITHM via models/algorithm_presets.json). The rest are normally discarded.

Analyst-strongBuy override lane: any pre-filtered stock whose current-month analyst strongBuy count (Yahoo recommendationTrend 0m period) meets the preset's analystStrongBuyThreshold bypasses the ranker keep-cut and joins the survivor list. These stocks still go through Monte Carlo + GPS-Full, and they still require positive predicted change to be surfaced — but they skip the mlGate percentage floor. Their discovery_source is 'analyst_consensus' at write time; ranker-and-mlGate survivors are 'v2_engine'.

Tuning: set DEEPMONEY_ALGORITHM in .env.local. Level 1 keeps the top 5% by ranker and requires 10 strongBuys for override; level 10 keeps the whole universe and requires only 1 strongBuy. See the algorithm preset table for the full mapping.

Failure mode: if score_ranker.py errors or returns no scores, the analyzer logs a loud error and falls through with every pre-filtered stock treated as a survivor for that run. The analyst override still runs on top in this mode (no-ops since everything is already a survivor). This is a degraded-mode escape hatch, not a normal path — investigate the log if the funnel summary shows zero rejected by ranker.

Rollout & Rollback

Files required when gate is on:

  • models/ranker_v1_regression.txt — trained LightGBM booster (~72 features)
  • models/feature_manifest.json — feature column order, training metadata, drift guard
  • scripts/ranker_features.py, scripts/score_ranker.py — feature computation + inference
  • src/utils/rankerInference.ts — TS bridge (shared macro fetch + subprocess invocation)
  • Python deps: lightgbm (offline-only; not imported when the gate is off)

Rollback (full pipeline-off): there is no per-run rollback — the ranker is mandatory. To soften the filter without code changes, raise DEEPMONEY_ALGORITHM toward 10 (level 10 keeps the entire pre-filtered universe). Schema columns stay (additive, harmless when unused).

Failure mode: if score_ranker.py fails or the subprocess errors, scoreWithRanker() logs and returns an empty score map. The analyzer detects the empty map and falls through with every pre-filtered stock treated as a survivor for that run. No silent stock loss, but the funnel summary will show zero ranker-rejections — that is the signal to investigate the log.

Retraining: the v1 model was trained on 24 months of weekly cross-sectional snapshots (~50K rows from ranking_training_snapshots). To retrain: rerun scripts/build_ranking_dataset.py against current data, then scripts/train_ranker.py. Both are offline scripts — not invoked by the sync. The output replaces models/ranker_v1_regression.txt + models/feature_manifest.json; the inference path picks them up on the next subprocess call (no restart needed).

Scheduling Considerations

The script is designed to be invoked by cron on the same host as the Next.js server. Recommended cadence is once per market day, after the close.

  • Runtime budget: a full discovery pass can take 2+ minutes (RSS aggregation, enrichment, AI analysis). The hardcoded http://localhost:3001 URL exists specifically to bypass nginx's 60-second proxy timeout.
  • Idempotency: safe to re-run on the same day. recommended_stocks is fully rebuilt, stock_gps_scores skips unchanged writes, prediction_records upserts via (symbol, CURDATE()), and the stale-entry cleanup is set-based on qualifying_stock_ids.
  • Concurrency: the post-sync cleanup is exact rather than pre-clearing, so an overlapping run can complete without wiping in-flight discovery entries. That said, two simultaneous runs are not recommended — both will issue DELETE FROM recommended_stocks at the top and race each other's bulk inserts.
  • Failure modes: a failed World Bank fetch leaves the macro snapshot untouched but the stock sync proceeds. A failed discovery API call aborts the run entirely. A DB exception triggers conn.rollback(); the cursor and connection are always closed in finally.
  • Logging: all output is plain print() to stdout. Operators should capture stdout/stderr in a cron log file. Key lines to watch for: [config], [debug], [vol-gate], [ath-warn], [analytics], ETF holdings persisted, and Sync completed successfully.
