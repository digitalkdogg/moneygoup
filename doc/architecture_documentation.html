Auth & Approval Flow

Registration Flow

  1. User submits registration form (username, email, password)
  2. POST /api/auth/register validates input via Zod. Checks email + username uniqueness.
  3. Password hashed with bcryptjs (10 rounds). User inserted with approval_status: 'pending'.
  4. Resend sends confirmation email to user and notification to admin.
  5. User cannot log in until an admin approves the account.

Admin Approval Flow

  1. Admin views pending users at /admin/users.
  2. Admin clicks Approve. PATCH /api/admin/users sets approval_status = 'approved'.
  3. Resend sends an approval notification email to the user.
  4. User can now log in. evaluateApprovalStatus() in auth.ts passes the check.

Login Flow

  1. User submits credentials (email + password).
  2. NextAuth CredentialsProvider calls loginLimiter rate check.
  3. Looks up user by email. Runs bcryptjs.compare(password, hash).
  4. Calls evaluateApprovalStatus() — throws a descriptive error if pending or rejected.
  5. JWT created with id, role, approvalStatus. Redirects to home.

Password Reset Flow

  1. User submits email on /forgot-password. Always shows success message (anti-enumeration).
  2. If email found: SHA256 token generated, stored in password_reset_tokens (1-hour expiry). Resend emails reset link.
  3. User clicks link → /reset-password?token=…
  4. GET /api/auth/reset-password validates token.
  5. User submits new password. POST validates + consumes token, bcryptjs hashes, updates user.

Session & Middleware (updated May 2026)

All routes except public ones are protected by NextAuth withAuth middleware defined in src/proxy.ts. The middleware reads the JWT session token from the cookie and redirects unauthenticated requests to /login. Server-to-server internal calls bypass authentication using an x-api-key header matching DEEPMONEY_INTERNAL_SECRET.

The middleware also generates a per-request cryptographic nonce and sets a Content-Security-Policy header on every response. The nonce is passed to page components via the x-nonce request header to enable inline script execution.

Two-layer session verification: The JWT session token carries id, role, and approvalStatus (set at login time). For every authenticated API request, all protected endpoints additionally call checkApprovalGuard(userId) which re-queries the database to verify the account is still approved. This prevents stale sessions from accessing data after an account is suspended. The guard fails closed: on DB error, access is denied.
Data Flow

Portfolio Data Flow (updated June 2026)

  1. Dashboard or PortfolioPage mounts; calls GET /api/user/portfolio.
  2. API queries user_stocks JOIN stocks JOIN user_stock_predictions JOIN stock_brand.
  3. For each holding, fetches live quote + analyst summary from Yahoo Finance in parallel. The quoteResult.quoteType field is checked: if it equals 'ETF' (case-insensitive), the item is flagged is_etf: true. This replaces the previous approach of looking up the static company_tickers.json, which was missing many ETFs such as VGT.
  4. Returns enriched portfolio array (now includes is_etf per item) with totals (costBasis, marketValue, unrealizedGain/Loss).
  5. PortfolioPage derives portfolioEtfTickers (symbols where is_etf === true) and hasEtfInPortfolio from the response. When hasEtfInPortfolio is true, the RecommendationsSection scopes array is extended with 'etf_holding' and portfolioEtfTickers is forwarded to filter those cards to the user's actual ETF positions.
is_etf detection change (June 2026): ETF status is now determined dynamically from Yahoo Finance's quoteType field at request time, rather than from the static company_tickers.json file. This correctly identifies fund-of-fund structures and thematic ETFs (e.g., VGT, QQQ, SCHD) that were absent from the SEC dataset.

Stock Detail Data Flow

  1. User navigates to /search/[ticker]. Page renders Stock component with ticker prop.
  2. Stock fires parallel requests: GET /api/stock_data/{ticker} (price, history, news, earnings, technicals) + GET /api/stock_data/{ticker}/gps + GET /api/dashboard/on?ticker=.
  3. Stock detail page assembles: price header, portfolio/watchlist action buttons (if applicable), StockSignalPanel, StockChart, TechnicalIndicatorsDisplay, analyst table, earnings table, StockNews.
  4. User can trigger prediction via StockPrediction (two-step: /api/stock_data/{ticker}/data → POST /api/prediction/{ticker}).

Watchlist Data Flow

  1. WatchlistSection calls GET /api/user/watchlist on mount.
  2. API fetches watchlist items, enriches each with Yahoo Finance live price and 6-month moving average from stocksdailyprice table.
  3. User can: (a) remove — DELETE /api/user/watchlist?stockId=, or (b) move to portfolio — opens PurchaseFromWatchlistModal which POSTs to /api/user/stocks.

Recommendations Data Flow (updated June 2026)

  1. RecommendationsSection calls GET /api/dashboard/recommendations.
  2. API fetches user's saved predictions from user_stock_predictions for portfolio and watchlist scopes. ETF holding recommendations are fetched separately from etf_stock_recommendations.
  3. Fetches current prices from Yahoo Finance to compare against predicted prices.
  4. Calls GET /api/worldbank (6-hour cached) to get macro dampeners: if unemployment is bearish, BUY threshold rises by 2%; globalHealthScore adjusts delta multiplier.
  5. Returns recommendations sorted by |deltaPct|, tagged with scope (portfolio, watchlist, discovery, or etf_holding). ETF holding items also carry an etfTicker field.
  6. On the /portfolio page, RecommendationsSection receives a portfolioEtfTickers prop and client-side filters etf_holding cards so only holdings within the user's actual ETF positions are shown (not watchlist ETFs).
ETF holding card badge: Cards with scope === 'etf_holding' render a teal badge labelled "etf holding" and display "In {etfTicker}" in the sub-label instead of the standard last-updated timestamp.
AI Prediction Pipeline

Two-Step Architecture

The prediction system uses a two-step client/server architecture to separate data collection from model execution.

  1. Step 1 — Data fetch: StockPrediction component calls GET /api/stock_data/{ticker}/data, which assembles an enriched payload (historical prices, fundamentals, technicals, analyst data, macro context) formatted for the Python model. Result cached in stockDataCache.
  2. Step 2 — Model run: Component POSTs the payload to POST /api/prediction/{ticker}. Route checks predictionCache first. If no cache hit, validates ≥200 days history, then acquires a semaphore slot to cap concurrent Python spawns.
  3. Python execution: child_process.spawn runs scripts/predict_weighted_analysis.py, passing the JSON payload via stdin. The script outputs prediction JSON to stdout.
  4. Result handling: Route caches the result in predictionCache and fires an async POST to /api/prediction/save to persist the result in user_stock_predictions.
  5. Display: StockPrediction renders 4 horizon cards (1W/1M/3M/6M), an SVG trajectory chart with confidence bands, and a metric analysis accordion.

Post-Hoc Adjustment Stack Variant (added July 2026)

The Python model applies a post-hoc adjustment stack (bearish-regime damping, momentum-overreach cap, calibration deadband, etc.) after raw model output. Which stack version runs is selected by the MODEL_VARIANT env var, read at import time in scripts/predict_weighted_analysis.py:54.

ValueBehavior
v3Legacy adjustments only (pre-June 2026).
v4Adds inline telemetry + expanded bearish-regime handling.
v5Default. Adds beta-scaled deadband, momentum-overreach ceiling (30-day return > 30% caps upside), and bearish-cascade damping when beta > 0.8 and 30d/90d returns are both negative.
MODEL_VARIANT is independent of CS_MODEL_VERSION — the former selects the post-hoc adjustment code path in predict_weighted_analysis.py; the latter selects which cross-sectional model pickle is loaded (e.g. long_term_cs_v2.pkl). Unrecognized values fall back to v5 with a stderr warning.

GPS Score (Global Performance Score)

A composite 0–100 score computed by the Python model. Combines 6 sub-scores:

Sub-scoreSource
Analyst UpsideAnalyst 12-month target price vs. current price
Revenue GrowthYoY revenue growth from earnings data
Earnings GrowthYoY EPS growth
52-Week Price ChangeCurrent price vs. 52-week low/high midpoint
MLP AlphaMulti-layer perceptron model alpha signal
AI ConfidenceModel prediction confidence level

GPS scores are stored in user_stock_predictions.gps_score (user-specific) and also in the recommended_stocks table (system-wide). The GET /api/stock_data/{ticker}/gps endpoint checks user predictions first, then falls back to system scores.

Card System Architecture

Discriminated Union Pattern

All stock display cards use a single discriminated union type StockCardModel with four variants. This allows a single StockCard entry point to route to the correct view without prop drilling.

// src/app/components/cards/types.ts

  | SearchTrendingCard  // variant: 'search-trending' — price + hot rating, no actions

Weighted Average Price Calculation

When a user buys additional shares of an already-owned stock, the purchase price is recalculated as a weighted average:

newAvgPrice = (existingShares × existingAvgPrice + newShares × newPrice)
              / (existingShares + newShares)

SEC Company Tickers

The full SEC company ticker list is served as a static public asset at /company_tickers.json. It is no longer the source for the Search component — that flow was replaced by GET /api/search, which reads directly from the stocks table's FULLTEXT index and returns category-aware hits (e.g. "Large Retail" → WMT). The static file is still used by src/app/api/stock_data/[ticker]/route.ts (fetchCompanyNameFromSec) as a name-lookup fallback when Yahoo Finance is unreachable. Note: this file is not used for ETF detection — ETF status is determined at runtime via Yahoo Finance's quoteType.

Search Index (FULLTEXT)

Ticker/company/category search is served by /api/search against the stocks table's ft_stocks_search FULLTEXT index. The Search component debounces keystrokes (180 ms) and aborts in-flight requests on new input. Backing columns — sector, industry, size_bucket, search_tsv — are populated by scripts/backfill_stock_search.py, which pulls Yahoo assetProfile data, computes size buckets from market_cap, and expands industries through a hand-curated synonym map so colloquial queries ("chip", "banks", "Large Retail") reach the intended tickers.

Brand Color Enrichment

When a user adds a stock to their portfolio (POST /api/user/stocks), a background async call fires getBrandColorFromScript(ticker). This fetches the company's primary brand color and stores it in the stock_brand table. The color is then used as the accent bar at the top of each PortfolioCardView. This is a best-effort operation — it does not block the portfolio add response.

Ollama (local LLM)

Runs on the same host as the Next.js app at OLLAMA_BASE_URL (default http://localhost:11434). Two features route through it:

  • DeepMoney NER pass — extracts tickers from news article text during the nightly sync; uses OLLAMA_MODEL (default llama3.2) with tight timeouts and JSON output mode.
  • AI Take — GET /api/prediction/[ticker]/ai-take generates the ~120-180 word paragraph on /search/[ticker] via gemma3:4b (OLLAMA_MODEL_AI_TAKE). Cache-first: hits ai_ticker_takes keyed on a SHA-256 of model+data. Fresh calls run with keep_alive: '24h' so the model stays resident between clicks.

Both features share one client in src/utils/ollamaClient.ts with isOllamaEnabled() as the master gate (OLLAMA_ENABLED=true) and checkOllamaReachable() as a cheap probe. Every consumer must accept null as "Ollama unavailable" and degrade gracefully — the wrapper never throws.

Peak RAM footprint on gemma3:4b: ~3.5 GB while resident. On a shared VPS, plan headroom accordingly; see the deployment notes below.

Key Utilities

In-Flight Request Deduplication

The stock data route (GET /api/stock_data/[ticker]) maintains a module-level Map:

const inflightRequests = new Map<string, Promise<Response>>()

If a second request for the same ticker arrives while the first is still awaiting Yahoo Finance, the second request is attached to the existing Promise instead of spawning a duplicate fetch. The entry is deleted from the Map once the Promise resolves.

The AI Take route (GET /api/prediction/[ticker]/ai-take) uses the same pattern keyed on (ticker, data_hash): if two users click Ask AI on the same ticker within seconds of each other, only one Gemma inference actually runs — the second request awaits the first's promise. Important because concurrent gemma3:4b runs on CPU would thrash a shared host.

Boot-time Model Warmup (src/instrumentation.ts) new

Next.js instrumentation hook that runs once per server process at startup. Fires a fire-and-forget POST to Ollama's /api/generate with the AI Take model and keep_alive: '24h', preloading the ~3.5 GB gemma3:4b weights into memory before any user click.

Without warmup, the first Ask AI click of the day would eat a 30-40 s cold-load penalty on top of the normal 10-20 s generation. With it, that penalty is paid at boot instead. Warmup respects the same env gates as the feature (AI_TAKE_ENABLED=off short-circuits the ping) and never blocks the server on failure — an unreachable Ollama produces a single stderr warning and the app keeps booting.

Guarded by process.env.NEXT_RUNTIME !== 'nodejs' so the Edge runtime never attempts to reach a localhost service.
