Business Rules

This is the authoritative, code-grounded list of business rules that govern GrowMyStocks. Each rule is derived from the actual production codebase — Next.js app routes, Python sync scripts, and MySQL schema — not from policy intent.

How to read this

Every rule has a stable ID (e.g. BR-4.2) you can quote in tickets, PRDs, or stand-up. The ID is the section number plus a sequence number within that section. Tags identify whether the rule is enforced by the Web App, a Python script, the Database schema, or via Config / Env. Each rule cites the file(s) where it's enforced so an engineer can verify it in one hop. Rules outlined in red are data-integrity-critical — breaking them produces silent data loss or wrong answers in the UI.

1. Users & Access

See also: Auth Flow · Admin User Mgmt

BR-1.1
Web App Config

Registration requires a username (3–50 chars), a valid email, and a password 8–100 chars containing at least one digit. Submissions are rejected with a generic validation error if any constraint fails.

src/app/api/auth/register/route.ts · register validator
BR-1.2
Web App

Every new registration enters approval_status = 'pending' and cannot log in until an admin promotes the row to approved. There is no auto-approval path.

src/app/api/auth/register/route.ts · users.approval_status
BR-1.3
Web App

If a previously rejected account tries to re-register with the same email or username, the old row is auto-archived (renamed with an _archived suffix) and the new registration proceeds. This prevents permanent lockout from a wrong-button-click rejection.

src/app/api/auth/register/route.ts · archive-on-conflict path
BR-1.4
Web App

Approval gate distinguishes five states: pending, approved, rejected, unsubscribed, archived. Only approved users can hit authenticated routes. The four denial states each produce a distinct status code so the frontend can show the right message.

src/utils/approvalStatus.ts · checkApprovalGuard
BR-1.5
Web App

The approval check re-queries the database on every protected API route — not just at login — so revoking access takes effect immediately for any user already holding a session token.

src/utils/approvalStatus.ts · re-query pattern
BR-1.6
Web App Config

Session TTL defaults to 30 days. Override via SESSION_MAX_AGE env var (seconds). When the TTL expires, the user is bounced from whichever page they're on to /login.

src/lib/auth.ts · NextAuth options
BR-1.7
Web App

Failed login responses are timing-equalized: unknown usernames still trigger a bcrypt hash on a dummy value so attackers can't enumerate which usernames exist by measuring response time.

src/lib/auth.ts · authorize()
BR-1.8
Web App

users.last_login is updated asynchronously (fire-and-forget) on successful login. A DB failure here does not block the auth response — the user still gets in.

src/lib/auth.ts · last_login update

2. Authorization

See also: Auth Flow · Admin User Mgmt · App Overview · Env Vars (System)

BR-2.1
Database

The schema defines three account roles: user, superuser, admin. admin is the only role allowed to approve or reject pending registrations through /admin/users.

doc/moneygoup_schema.sql · users.role
BR-2.2
Web App Python Config

Python sync scripts (deepmoney_sync.py, update_predictions.py) authenticate to the Next.js API via the x-api-key header. Value must match DEEPMONEY_INTERNAL_SECRET. The secret must be at least 32 bytes; shorter values disable internal auth entirely.

src/utils/internalAuth.ts · timing-safe SHA256 compare
BR-2.3
Web App

Requests authenticated via the internal x-api-key header bypass all rate limits. Browser sessions never carry this header.

src/utils/rateLimitMiddleware.ts
BR-2.4
Web App Config

When the app is behind a proxy or CDN, X-Forwarded-For / X-Real-IP / CF-Connecting-IP headers are only trusted if the direct peer IP appears in the TRUSTED_PROXIES comma-separated env var. Otherwise the headers are ignored and the direct peer IP is used. This prevents IP-spoof bypass of rate limits.

3. Strategy & Personalization

See also: Strategy System · App Overview · Personalization Model

The two-axis strategy is the single source of truth for every personalized number on screen. If the dashboard shows a "wrong" number for a user, the explanation almost always lives in the strategy row.
BR-3.1
Web App

Each user has a strategy made of two axes: aggressiveness (safe / neutral / aggressive) and investment_timeframe (1_week / 1_month / 6_month / 1_year). All personalized scores, gates, and predictions are derived from this pair.

src/utils/strategy.ts
BR-3.2
Web App

Default strategy is neutral + 1_month. Missing rows fall back to this default; invalid values snap to the default without raising errors.

src/utils/strategy.ts · DEFAULT_STRATEGY
BR-3.3
Web App

Aggressiveness sets five hard gates that every personalized read uses:

AxisSafeNeutralAggressive
confidenceFloor655035
betaCutoff1.52.03.5
gpsGate756555
predChangeGate (1m baseline)3.0%1.5%0.5%
envFloorMultiplier (applied to env thresholds)×1.05×1.0×0.95
Where this fires: These gates are applied at dashboard read time (src/app/api/dashboard/recommendations/route.ts), not during the deepmoney sync. The sync produces a single global candidate pool using DEEPMONEY_ALGORITHM (BR-6.1) and is unaware of any user's aggressiveness. When a user loads /dashboard, the same sync-produced rows are filtered through that user's gates — so two users with identical portfolios but different aggressiveness see different cards from the same underlying data.
src/utils/strategy.ts · STRATEGY_GATES · src/app/api/dashboard/recommendations/route.ts (read-side application)
BR-3.4
Web App

Investment timeframe scales the predicted-change gate: 1w ×0.5, 1m ×1.0, 6m ×1.5, 1y ×2.0. So an aggressive user on a 1-year timeframe needs a stricter percentage move than the same user on 1-week.

src/utils/strategy.ts · timeframeMultipliers
BR-3.5
Web App

SELL thresholds are shifted per timeframe: 1w −2, 1m 0, 6m +3, 1y +5. Longer-timeframe users tolerate more downside before a SELL warning fires.

src/utils/strategy.ts · timeframeShifts

4. GPS Score

See also: GPS Score · Technical Indicators · App Overview · Env Vars (Prediction / GPS)

BR-4.1
Web App Python

GPS is a 100-point composite of eight components: ML Predicted Change 1m (20), AI Model Confidence (5), Revenue Growth YoY (12), Earnings Growth YoY (12), Technical Signal (20), Analyst Price Target Upside (12), Analyst Consensus (9), 52-Week Momentum (10). The TypeScript implementation (src/utils/gps.ts) and Python mirror (scripts/update_predictions.py · calculate_gps_v3) must stay in lockstep.

src/utils/gps.ts · calculateGpsScore
BR-4.2
Web App Config

The ML Predicted Change component saturates at GPS_PREDICTION_MAX% (default 3, production 15). A +GPS_PREDICTION_MAX% prediction earns the full 20 pts; anything beyond clamps. Lower values = component saturates faster.

src/utils/gps.ts · mlpUpside
BR-4.3
Web App

A bearish signal flag fires whenever the underlying predicted_change_pct is negative, regardless of the resulting GPS score. The UI uses this flag to override the BUY label even when other components keep the score high.

src/utils/gps.ts · bearishSignal
BR-4.4
Web App

GPS labels: ≥80 = Strong Buy, ≥65 = Buy, ≥45 = Hold, ≥30 = Sell, <30 = Strong Sell. These bands are independent of the per-user BUY / SELL thresholds — they're the universal label scale.

src/utils/gps.ts · classifyScore
BR-4.5
Web App

Per-horizon GPS adjustment patches the mlpUpside and mlpConfidence components after the initial calculation, so the displayed score matches the user's timeframe exactly. No separate GPS row is stored per horizon — one cached score is mutated read-side.

src/utils/gps.ts · adjustGpsForHorizon
BR-4.6
Web App

GPS-Light is the fast variant used during the ranker phase (before Monte Carlo). It replaces the MLP block (20 + 5 pts) with rankerScorePct (20 pts) + a vol-based confidence proxy (5 pts). The other 75 pts are identical to GPS-Full.

src/utils/gps.ts · calculateGpsLight
BR-4.7
Web App

The user's investment_timeframe is honored at read time, not write time. Every authenticated card-rendering surface applies adjustGpsForHorizon using the user's per-horizon change% + confidence from user_stock_predictions. Surfaces that do this:

  • /api/dashboard/recommendations — Portfolio / Watchlist / Discovery cards
  • /api/dashboard/recommendations — ETF Holding cards (joins to user_stock_predictions when the user owns/watches the holding directly; falls back to esr.predicted_change_pct otherwise)
  • /api/dashboard/deepmoney-picks — hot stocks AND ETF holdings in the DeepMoney Picks widget; hot_etfs rows are not adjusted
  • /api/user/portfolio · /api/user/watchlist · /api/market/trending
  • /api/stock_data/[ticker]/gps — feeds the /search/[ticker] GPS panel + "View score" modal

For tickers the user has no user_stock_predictions row for, every surface falls back gracefully to the raw 1-month baseline from stock_gps_scores. The DB-stored GPS values (stock_gps_scores, recommended_stocks, etf_stock_recommendations) are always the 1-month baseline — no per-horizon rows exist.

multiple routes · src/utils/gps.ts:adjustGpsForHorizon

5. Predictions

See also: Prediction Workflow · Database · GPS Score

BR-5.1
Database Python

Each (symbol, predicted_at) pair in prediction_records is unique. Writes use ON DUPLICATE KEY UPDATE with COALESCE so that re-running a prediction for the same day updates the row but never overwrites a non-null horizon with NULL.

scripts/prediction_recorder.py · record_prediction
BR-5.2
Python

Predictions are recorded for every ranker survivor in deepmoney_sync.py — including stocks rejected by the local vol-gate. This is intentional: it lets the team measure how often the floor was right to reject.

scripts/deepmoney_sync.py · record_prediction before vol-gate
BR-5.3
Python

ETF-holding predictions are also recorded to prediction_records via run_prediction_for_holding, so they contribute to the same accuracy statistics as hot-stock predictions.

scripts/update_predictions.py · run_prediction_for_holding
BR-5.4
Python

Per-horizon predicted prices are persisted in four columns: predicted_price_1w, predicted_price_1m, predicted_price_6m, predicted_price_1y. Only predicted_price_1m is NOT NULL; the others may be missing for short-history symbols.

scripts/update_predictions.py · save_prediction
BR-5.5
Python

Prediction outputs are sanitized before persistence. Per-horizon caps (base 1w ±15%, 1m ±30%, 6m ±60%, 1y ±100%) are multiplied by max(1, min(2.5, realized_vol_60d / 0.30)), so a high-vol name gets proportionally wider ceilings and doesn't clip on every prediction. Prices are floored at 0.01. Confidence is demoted to 25 only when the clamp catches a real outlier — not when both 6m + 1y coherently push against their vol-scaled caps in the same direction (a coherent extrapolation keeps the model's own confidence and sets at_model_ceiling_* flags so the UI shows a directional pill instead of a false-precision point target). A trajectory-smoothness gate catches legitimate cyclical peak-and-reverse forecasts and drops confidence to 60 (Medium) rather than 25. Each horizon-specific adjustment stamps a confidence_reason_{h} string the tooltip surfaces on Medium/Low badges.

scripts/predict_core.py · _sanitize_predictions
BR-5.6
Python

The regime vector and the raw feature matrix passed into the scaler are run through numpy.nan_to_num before scoring so that international tickers with NaN macro inputs (e.g. SRU-UN.TO, ENR.DE) don't crash the pipeline.

scripts/predict_weighted_analysis.py · nan_to_num passes
BR-5.7
Python

A stock must have at least 200 days of OHLCV history before any inference runs. Stocks below the floor are silently skipped — no error surfaces to the user, no row is written.

scripts/update_predictions.py · 200-day gate
BR-5.8
Python

resolve_predictions.py loops in 1000-row batches per horizon and skips any row whose predicted_price_* is NULL. Without this filter, older rows with NULL longer-horizon columns would burn one Yahoo fetch per run and stall the resolver.

scripts/resolve_predictions.py · WHERE filter
BR-5.9
Python

If a target resolution date falls on a non-trading day, resolve_predictions.py looks up to 6 days forward and uses the first available close. This handles weekends and US market holidays without losing data.

scripts/resolve_predictions.py · get_trading_day_price
BR-5.10
Python

When the GPS pipeline persists a hot-stock recommendation and the symbol is missing from the stocks table, the row is auto-inserted with the ticker as a placeholder company name. Prevents silent data loss when a brand-new ticker surfaces.

scripts/update_predictions.py · save_gps_score_to_db
BR-5.11
Python

The MODEL_VARIANT env var gates which post-hoc adjustment stack is applied inside predict(). Three valid values: v3 (no adjustments, bare model output — used as a control), v4 (v4 adjustments only), v5 (default; v4 base minus the VIX-conf mult, plus Fix A/B/C/D). Unknown values log a warning to stderr and fall back to v5. The variant is orthogonal to CS_MODEL_VERSION, which selects the cross-sectional model pickle file (models/long_term_cs_{v1,v2}.pkl).

scripts/predict_weighted_analysis.py · _MODEL_VARIANT gate
BR-5.12
Python

v4 post-hoc adjustments (applied when MODEL_VARIANT ∈ {v4, v5}): (a) 90d momentum drift — when |ret90d| > 15%, the raw 6m/1y prices are multiplied by 1 + (ret90d × 0.75) and 1 + (ret90d × 1.25) respectively. (b) Direction deadband — a new field predicted_direction_{h} ∈ {up, down, neutral} is written; |change| < 2% ⇒ neutral. (c) RSI-beta short-term gate — RSI > 70 with β > 0.8 boosts 1w/1m confidence ×1.10; RSI > 70 with β < 0.5 damps ×0.85. (d, v4 only) VIX × beta confidence multiplier — nerfs all 4 confidence scores when VIX > 20 proportional to beta. In v5 this is replaced by Fix B (a price multiplier, not confidence).

scripts/predict_weighted_analysis.py · inline v4 block + _apply_variant_adjustments
BR-5.13
Python

v5 post-hoc price adjustments (applied when MODEL_VARIANT = v5, layered after v4 drift): Fix A (Downtrend Trap) — high-beta names (β > 0.8) with both 30d < -5% and 90d < -10% get a downside price ceiling. Fix B (Beta-signed VIX price mult) — applied before predict_long_term(); low-beta (β < 0.5) gets a boost in high VIX (flight-to-quality), high-beta gets a softer dampener floored at 0.55. Fix C (Structural Decline) — >20% below 52w high AND 90d < -15% triggers a continued-slow-decline prediction (5-10% down at 6m, 8-15% at 1y). Fix D (Extreme Momentum) — when 90d > 30%, scale the predicted move delta by up to 1.5× to counter mean-reversion bias in the extreme tail. All price adjustments use min()/composition-safe math so Fix A and C can both fire without over-clipping.

scripts/predict_weighted_analysis.py · inline v5 block (Fix A/B/C/D)
BR-5.14
Python

The direction deadband propagates to compute_accuracy_metrics() in both resolve_predictions.py and backtest_predictions.py. When |predicted_change_pct| < 2%, direction_correct_{h} is written as NULL, not 0. This excludes near-flat calls from the direction-accuracy metric instead of counting them wrong. DIRECTION_DEADBAND_PCT = 0.02 is a shared constant across both scripts and mirrors V4_DEADBAND_PCT in the predictor.

scripts/resolve_predictions.py + scripts/backtest_predictions.py · compute_accuracy_metrics
BR-5.15
Python

Fixes E, F, G (SMCI vol-bypass on Fix D, moderate-β VIX branch on Fix B, RSI recovery guard on Fix A/C) were implemented and tested against a 15-ticker v5-efg-newset backtest, showed no measurable improvement, and were reverted on 2026-07-12. Cache schema version 23 marks the revert. If reintroduced, they should be re-tested against the same v5-newset baseline.

reports/data_4way_newset.txt · v5-newset vs v5-efg-newset

6. DeepMoney Discovery

See also: DeepMoney Sync · App Overview · Env Vars (DeepMoney)

BR-6.1
Web App Config

DEEPMONEY_ALGORITHM (float 1.0–10.0, default 5) is the single knob that drives the entire discovery pipeline. Lower = stricter, higher = more permissive. Fractional values (e.g. 1.5) interpolate linearly between adjacent integer rows.

src/utils/algorithmPreset.ts · models/algorithm_presets.json
BR-6.2
Web App

The preset resolves into five fields: rankerKeepPct, mlpConfidenceFloor, volGateFloor, analystStrongBuyThreshold, signalScoreFloor. The Next.js route echoes them in meta.algorithm; deepmoney_sync.py reads back from that echo so TS and Python can never drift apart.

src/utils/algorithmPreset.ts · loadAlgorithmPreset
BR-6.3
Web App

Interpolated mlpConfidenceFloor and volGateFloor values are snapped up to the nearest discrete CS bucket {35, 50, 65, 75}. The MLP only emits those four confidence values, so an unsnapped floor of 71.5 would behave identically to 75 — the snap makes the resolved preset honest.

src/utils/algorithmPreset.ts · snapToBucketCeiling
BR-6.4
Web App

Discovery sources merged per run, with Set semantics deduping the union:

  • ~45 RSS / JSON / atom feeds — PRIMARY_FEED_URLS. Includes 9 Yahoo predefined screeners (most_actives, undervalued_growth_stocks, aggressive_small_caps, small_cap_gainers, day_gainers, top_mutual_funds, solid_large_growth_funds, conservative_foreign_funds, high_yield_bond); 7 SEC EDGAR atom feeds (Form 4 ×2, 8-K, SC 13D, SC 13G, S-1, 425); sector / industry trade press (FierceBiotech, FiercePharma, FierceHealthcare, FierceElectronics, SpaceNews, OilPrice, NaturalGasIntel, Mining.com, DIA, DefenseNews ×2); mainstream financial press (Marketbeat, TheStreet, Motley Fool, CNBC ×2, MarketWatch, Seeking Alpha, Investing.com, TipRanks, InvestmentNews, S&P Market Intelligence, Benzinga, Zacks, Barchart); plus Reddit-style mention aggregator (ApeWisdom). Mutual-fund / bond-fund screeners surface ~100 tickers that drop at the analyzer pre-filter (no OHLCV history) — kept for institutional-flow signal even though they don't surface.
  • Yahoo earnings calendar HTML scrape
  • Popular-ETF holdings — top 20 per ETF (raised from 5; capped at 20 in the /holdings route) across 20 pre-named ETFs
  • Per-primary-ticker Yahoo RSS pass — capped at MAX_SECONDARY = 60 primary tickers (raised from 30) to roughly double the per-ticker mention pool
  • Trending feed (Yahoo most_actives) — limit 100 (raised from 50); the window=48h param is cache-key-only, not an actual time filter
  • Sector leaders — top-25 per canonical Yahoo sector (11 sectors via ms_<sector> screener). Yahoo does not expose ms_<industry> predefined screeners (verified — all 404), so no finer-grained industry lane exists here.
src/app/api/prediction/deepmoney/route.ts
BR-6.5
Web App

Pre-filter drops any stock whose tradingSignalScore is below preset.signalScoreFloor (or undefined). At L5 the floor is 0 (matches the historic ≥ 0 gate); at L1–4 still 0; L6+ slides negative to surface contrarian picks.

src/app/api/prediction/deepmoney/analyzer.ts · pre-filter
BR-6.6
Web App

The LightGBM ranker is the single hard filter. After scoring, stocks are sorted by rank percentile descending and the top rankerKeepPct fraction is kept. The rest never run Monte Carlo and never appear in the output.

src/app/api/prediction/deepmoney/analyzer.ts
BR-6.7
Web App

The analyst-strongBuy override lane lets stocks bypass the ranker keep-cut if their current-month strongBuy count is ≥ preset.analystStrongBuyThreshold. These are tagged discovery_source: 'analyst_consensus' and still require positive predicted change, but skip the mlGate floor.

src/app/api/prediction/deepmoney/analyzer.ts
BR-6.8
Python

Local vol-gate in deepmoney_sync.py uses volGateFloor for high-beta stocks (beta > 2.5) and mlpConfidenceFloor for everything else. The skip log tags (vol-floor) vs (mlp-floor) so auditing a run is straightforward.

scripts/deepmoney_sync.py · vol-gate check
BR-6.9
Python

The ranker model loader (score_ranker.py · load_model_and_manifest) accepts order-only manifest drift. If the column SET matches but the order differs, it uses the manifest's order (the order the model was trained with). Set-level drift (added or removed columns) still raises an error.

scripts/score_ranker.py
BR-6.10
Web App

The trending-48h override lane is a full-coverage feed: every ticker from fetchTrendingTickers(50) with valid enrichment and ≥100 days of OHLCV history gets Monte Carlo + GPS-Full, regardless of technical signal score or predicted direction. The lane bypasses (a) the signalScoreFloor pre-filter — bearish-technical trending stocks reach MC via a parallel trendingPreFiltered pool, (b) the ranker keep-cut, (c) the mlGate floor, and (d) the positive-prediction requirement used by the analyst override. Survivors are tagged discovery_source: 'trending_48h' (unless they also clear the mlGate, in which case they're tagged v2_engine). In deepmoney_sync.py the vol-gate is split for trending: pass → regular path (writes both recommended_stocks and stock_gps_scores); fail → GPS-only fast path (writes stock_gps_scores only, skips recommended_stocks + dashboard). Together these guarantees ensure that every ticker on the /search trending grid renders a GPS rating. Surfaced count is exposed via meta.debug.trending48hSurfaced.

src/app/api/prediction/deepmoney/route.ts · src/app/api/prediction/deepmoney/analyzer.ts (trendingPreFiltered + Phase 3c) · scripts/deepmoney_sync.py (split vol-gate)

7. ETF Holdings

See also: DeepMoney Sync · App Overview · Bucket 4: ETF Holding · App Overview · ETF Env Vars

BR-7.1
Web App Config

ETF_HOLDING_ALGORITHM (float 1.0–10.0, default 5) is the single knob for ETF qualification + holdings surfacing. Same shape as DEEPMONEY_ALGORITHM; lower = stricter, fractional levels interpolate.

src/utils/etfHoldingPreset.ts · models/etf_holding_presets.json
BR-7.2
Web App

Resolves into five fields: etfGpsThreshold (min ETF GPS to qualify as "hot"), topNEtfs (how many qualifying ETFs survive), maxTickers (per-ETF holdings fetch + scoring cap), gpsSurfaceValue (min holding GPS to surface), minPredChangePct (min predicted change %).

src/utils/etfHoldingPreset.ts

Web App Config

scripts/update_predictions.py · ETF holdings scan
BR-7.7
Web App

When the user doesn't directly own/watch the holding, no user_stock_predictions row exists — the route falls back to esr.predicted_change_pct (the value the sync persisted at scan time) so the breakdown still patches against a horizon-appropriate change% rather than displaying the unpatched 1m baseline.

src/app/api/dashboard/recommendations/route.ts · etfRecs loop
BR-7.4
Web App Config

Holdings with beta > ETF_HOLDING_MAX_BETA (default 2.0) are dropped before scoring so the surfaced set isn't dominated by volatile names.

src/utils/etfHoldings.ts
BR-7.5
Web App Config

Cached etf_holding_scores rows are recomputed if they're older than ETF_HOLDING_STALENESS_HOURS hours (default 4). Lower = fresher cards, more compute; higher = cheaper, more stale.

src/utils/etfHoldings.ts
BR-7.6
Web App

For non-ETF tickers, the holdings API path logs the missing topHoldings module as INFO ("ticker is not an ETF"), not ERROR. Prior behavior was flooding logs for the common-case rejection.

src/utils/etfHoldings.ts · fetchETFHoldings logging

Web App

src/utils/gps.ts · src/app/components/GpsCallLabel.tsx · src/app/components/modals/GpsBreakdownModal.tsx
BR-8.8

16. AI Take & Rationale

BR-16.1
Web App new — 2026-07-18

Cache-first policy. The /api/prediction/[ticker]/ai-take endpoint always looks up ai_ticker_takes before generating. Cache hit criteria: matching (ticker, data_hash) AND generated_at > NOW() - INTERVAL AI_TAKE_CACHE_HOURS HOUR. Hits return in <100 ms; misses trigger a Gemma inference (typically 10-20 s warm, 60-90 s cold).

src/app/api/prediction/[ticker]/ai-take/route.ts
BR-16.2
Web App new — 2026-07-18

data_hash includes the model name. The SHA-256 covers {model, ticker, gps_score, gps_breakdown, predicted_change_pct, analyst_upside_pct, trading_signal}. News headlines are intentionally excluded from the hash — their high churn would invalidate the cache on every sync cycle, defeating the point of caching. Any change to the included fields forces regeneration. Swapping OLLAMA_MODEL_AI_TAKE automatically invalidates every cached take site-wide — no manual flush needed.

src/app/api/prediction/[ticker]/ai-take/route.ts (hashPromptInputs)
BR-16.3
Web App new — 2026-07-18

Rate limit falls back to cache, not 429. The AI_TAKE_RATE_LIMIT_PER_HOUR per-user-per-ticker rate limit only applies to fresh generations (fresh=1 or cache miss). When a throttled request has a valid cached copy to fall back to, the server returns 200 with rateLimited: true and a rateLimitNote; the UI renders a subtle italic note under the paragraph. A 429 is only returned when the user is throttled AND there is genuinely no cache to serve.
