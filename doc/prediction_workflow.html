AI Prediction Workflow & Algorithm

This document details the end-to-end execution path and mathematical logic behind the Stock Prediction System (v3.5). The pipeline produces 1-week, 1-month, 6-month, and 1-year price targets with Monte Carlo uncertainty bands and an 18-month trajectory chart. A single Python invocation returns all four horizons at once. Two model paths exist and are selected at runtime by the USE_LEGACY_PREDICTION_MODEL environment variable; the v3-split path further selects a cross-sectional long-term model version via CS_MODEL_VERSION. See Model Path Selection for the full matrix.

v5 / July 2026 — Variant-gated post-hoc fix stack:
  • The orchestrator (scripts/predict_weighted_analysis.py) now applies a stack of post-hoc adjustments gated by the MODEL_VARIANT env var: v3 = bare model (no adjustments), v4 = 90d drift + VIX×beta confidence multiplier + direction deadband + RSI-beta short-term gate, v5 (default) = v4 base minus the VIX-conf multiplier plus Fix A/B/C/D. See the new MODEL_VARIANT Fix Stack section for the full flow.
  • Fix B (beta-signed VIX modifier on long_term_multiplier) runs before predict_long_term(), so the multiplier flows into the raw 6m/1y price. Low-beta names (β<0.5) get a flight-to-quality boost; high-beta names get a softer dampener than v4 (threshold VIX=25, scale 35pts, floored at 0.55).
  • v4 90d drift (unchanged, fires in v4 and v5) — when |ret90d| > 15%, multiplies 6m/1y prices by 1 + ret90d × 0.75/1.25.

  • RSI-beta short-term gate — RSI>70 boosts (β>0.8) or damps (β<0.5) confidence_score_1w/1m.

L End-to-End Lifecycle

The complete path from "user clicks predict" to "row written to user_stock_predictions / stock_gps_scores":

  1. UI trigger. User clicks the Predict button in StockPrediction.tsx on /search/[ticker]. The component first fetches enriched data from GET /api/stock_data/[ticker]/data, then posts the resulting JSON body to POST /api/prediction/[ticker].
  2. Guard chain. The route validates origin, session, approval status, lookup quota, ticker format, body shape (historicalData length ≥ 365 + stockMetrics object), and the outlook query value. Internal calls (x-api-key) skip session + lookup checks.
  3. Cache check. Unless ?refresh=true is set, the route consults the in-memory predictionCache at key {ticker}_{outlook}. On a hit, the Python script is skipped entirely — but GPS is still computed live from the cached result because GPS is per-user.
  4. Concurrency gate. If the cache misses, the route acquires a slot from predictionSemaphore (503 Busy if full).
  5. Python model. A temp JSON file is written and scripts/predict_weighted_analysis.py is spawned. The Python script always trains a fresh MLP and returns all four horizons in one call (see Single Call → 4 Horizons). The result includes predicted_price_{1w,1m,6m,1y}, predicted_change_pct_{1w,1m,6m,1y}, confidence_score_{1w,1m,6m,1y}, the 18-month trajectory, accuracy metrics, and regime info.
  6. Analytics record. Immediately after Python returns, recordPrediction() fires once (fire-and-forget) to insert a row into prediction_records.
  7. Generic-key backfill + cache write. The route populates legacy predicted_price / predicted_change_pct / confidence_score keys based on the requested outlook and stores the result in predictionCache.
  8. Dual GPS computation. buildResponse() computes the neutral 1m baseline GPS (used for persistence) and the user-horizon GPS (returned to the caller). See Dual GPS Computation.
  9. Async persistence. savePredictionAsync() POSTs the model output to /api/prediction/save with all four horizon prices, all four per-horizon change percentages, all four per-horizon confidence scores, and the baseline 1m GPS. This call is fire-and-forget; the user response does not wait for it.
  10. Save route. /api/prediction/save upserts user_stock_predictions (per-user, prices + per-horizon stats) and upserts stock_gps_scores + appends stock_gps_score_history with the GPS baseline (global, one row per stock).
  11. Response. The caller receives the full model output merged with source, gps_score (horizon-matched), gps_breakdown, and gps_horizon.

S Strategy Integration

A user's investment strategy has two dimensions: aggressiveness (safe / neutral / aggressive) and investment timeframe (1_week / 1_month / 6_month / 1_year). Both are stored in the user_investment_strategy database table and fetched via getUserStrategy(userId) which falls back to DEFAULT_STRATEGY (neutral / 1_month) if no row exists.

GPS horizon patching downstream

The baseline GPS persisted globally uses the 1-month predicted change as the mlpUpside component. When a downstream route serves a user whose timeframe is not 1-month, only the mlpUpside component needs to change — the other 7 components (revenue growth, earnings growth, technicals, analyst upside, analyst consensus, 52-week momentum, AI confidence) are horizon-independent. adjustMlpUpsideForHorizon(breakdown, horizonDeltaPct) in src/utils/gps.ts swaps mlpUpside with the new value and recomputes the total.

// Horizon delta = (predicted_price_horizon - current_price) / current_price * 100 // adjusted mlpUpside = clamp(horizonDelta / predictionMax, -1, 1) * 20 // adjusted score = sum of all 8 components with new mlpUpside, clamped [0, 100]

Because /api/prediction/save now persists the per-horizon predicted_change_pct_* + confidence_score_* directly, downstream routes can plug the model's own outputs into the GPS formula rather than deriving the delta from possibly-stale price columns.

M Model Path Selection (env var) v3.5

Every prediction path in the codebase honors the same two env vars so a single switch in .env.local reconfigures the whole system — UI prediction button, backtest script, nightly batch sync, and DeepMoney discovery analyzer. No restart required for spawned Python (each invocation reads the env fresh); Next.js picks up the change on next dev/prod reload.

predict_long_term.py loads models/long_term_cs_{version}.pkl once at module import:

The pkl holds a sklearn-compatible .predict() object (for v1) or a KerasModelWrapper instance (for v2) that lazy-loads the underlying .keras file on first call. The wrapper makes the v2 model look like an sklearn regressor so the predict-time code path is identical regardless of which backend was used to train.

prediction_records tagging

The unique key on prediction_records is (symbol, predicted_at, model_version) — so legacy and v3-split backtests for the same (ticker, date) can coexist as separate rows. Backtest runs can override the tag via MODEL_VERSION_TAG env var (e.g. v3split_v2, v3split_v3) for ad-hoc CS-version A/B tests without colliding on the unique key.

Fix-by-fix reference

Fix B — Beta-signed VIX modifier on long_term_multiplier (v5 only)

predict_weighted_analysis.py:387-401. Runs BEFORE predict_long_term(). Reads current VIX and ticker beta:

if beta < 0.5: # low-beta defensive (KO/JNJ/PG) vix_mod = 1.0 + max(0, (vix - 20) / 30) * 0.15 # flight-to-quality boost else: # everyone else vix_raw = 1.0 - max(0, (vix - 25) / 35) * (beta / 1.5) vix_mod = max(0.55, vix_raw) # floored — never fully suppress long_term_multiplier *= vix_mod

Softer than v4's confidence-only nerf: threshold VIX=25 instead of 20, scale over 35pts instead of 30, floor at 0.55. The flight-to-quality branch is new in v5 — low-beta names get a boost in high VIX because their direction is more predictable, not less.

v4 Fix #4 — 90d momentum drift (v4 and v5)

predict_weighted_analysis.py:461-469. Runs AFTER predict_long_term().

if abs(ret90d) > 0.15 and current_price > 0: predicted_price_6m *= (1.0 + ret90d * 0.75) predicted_price_1y *= (1.0 + ret90d * 1.25)

The 1y multiplier is larger than the 6m multiplier because 90d momentum shows up more clearly at longer horizons. Fires in both v4 and v5. Fix D extends this for the extreme-momentum tail (ret90d > 30%).

Fix A — Downtrend trap ceiling (v5 only)

predict_weighted_analysis.py:471-484. Gate: beta > 0.8 AND ret30d < -5% AND ret90d < -10%. Beta-scaled cap:

severity = min(1.0, (-ret90d - 0.10) / 0.25) cap = 1.0 - (severity * 0.08 * min(beta, 2.0) / 2.0) predicted_price_6m = min(predicted_price_6m, current_price * cap) predicted_price_1y = min(predicted_price_1y, current_price * (cap - 0.03))

Excludes low-beta defensives that genuinely mean-revert after dips.

Fix C — Structural decline (v5 only)

predict_weighted_analysis.py:486-503. Gate: pct_from_52w_high < -20% AND ret90d < -15%. The double gate (depth + recency) prevents misfiring on crash-then-recovery cases (e.g. AAPL April 2025).

decline_sev = min(1.0, (-pct_from_52w - 0.20) / 0.30) f6m = 1.0 - (0.05 + decline_sev * 0.05) # 5-10% down at 6m f1y = 1.0 - (0.08 + decline_sev * 0.07) # 8-15% down at 1y predicted_price_6m = min(predicted_price_6m, current_price * f6m) predicted_price_1y = min(predicted_price_1y, current_price * f1y)
Fix D — Extreme positive momentum (v5 only)

predict_weighted_analysis.py:505-518. Gate: ret90d > 30%. Scales the move delta, not the absolute price, so we amplify the direction of the model's call rather than pushing toward an arbitrary level. Mutually exclusive with Fix A/C by sign of ret90d.

excess = ret90d - 0.30 extra = min(0.50, excess * 2.0) # capped at +50% xtscale = 1.0 + extra # in [1.0, 1.5] predicted_price_6m = current_price + (predicted_price_6m - current_price) * xtscale predicted_price_1y = current_price + (predicted_price_1y - current_price) * xtscale
Direction deadband + predicted_direction_{h} (v4 and v5)

predict_weighted_analysis.py:732-747 inside _apply_variant_adjustments(). Writes a new field on the result dict for every horizon:

V4_DEADBAND_PCT = 0.02 change = (predicted_price_h - current_price) / current_price if abs(change) < deadband: predicted_direction_h = 'neutral' elif change > 0: predicted_direction_h = 'up' else: predicted_direction_h = 'down'

Downstream propagation: the deadband threshold is duplicated in compute_accuracy_metrics() in both scripts/resolve_predictions.py:48-84 and scripts/backtest_predictions.py:477-514. When a prediction lands inside the deadband it produces direction_correct = NULL — excluded from the direction-accuracy metric surfaced by /api/analytics/model-accuracy instead of counted as a miss. In v3, the deadband is 0.0 so every non-zero prediction produces up/down.

v4 VIX × beta confidence multiplier (v4 ONLY — removed in v5)

predict_weighted_analysis.py:749-761. In v5 this is replaced by Fix B on long_term_multiplier (Fix B moves the price; the v4 mult only nerfed confidence). For A/B comparison it still runs when MODEL_VARIANT=v4:

stress = max(0, (vix - 20) / 30) # 0 at VIX≤20, 1 at VIX=50 beta_absorb = max(0, beta) / 1.5 # beta=1.5 ⇒ full absorption vix_conf_mult = max(0, 1.0 - stress * beta_absorb) # multiplies confidence_score_{1w, 1m, 6m, 1y}
RSI-gated short-term confidence (v4 and v5)

predict_weighted_analysis.py:763-776. Only fires when RSI_14 > 70. Multiplies confidence_score_1w and confidence_score_1m only (long-horizon confidence unaffected):

  • High-beta (β > 0.8) overbought ⇒ ×1.10 (boost — the trend is real)
  • Low-beta (β < 0.5) overbought ⇒ ×0.85 (damp — reversal likely)

Per-Horizon Optimizations — Short-Term vs Long-Term v3.5

The whole point of splitting the model is that different signals dominate at different timescales. A 1-week forecast is mostly about technical momentum, intraday volatility regime, and post-earnings drift; a 1-year forecast is mostly about fundamental revaluation, macro regime, and analyst-revision velocity. Mixing both signal families through one shared 4-output head — what the legacy MLP did — forces the network to compromise across horizons. Splitting lets each module specialize.

6. Why long-term predicts first

The orchestrator at predict_weighted_analysis.py:272 calls predict_long_term() before predict_short_term() because the short-term 1w blend formula needs predicted_price_6m as its trajectory anchor:

_traj_anchor_1w = current_price + (predicted_price_6m - current_price) * (5 / 126) _blended_1w = 0.50 × _mlp_1w_raw + 0.50 × _traj_anchor_1w

The short-term module's predict_short_term() signature explicitly takes predicted_price_6m and confidence_score_6m as required arguments — no implicit imports between horizon files. If the 6m forecast says "WMT to $130 in 6 months" (+12%), the trajectory anchor for 1w is at ~$115.95, and the 1w MLP output gets pulled halfway toward that anchor. If the 6m forecast collapses to current_price, the anchor pulls the 1w prediction toward "no change" — which is a useful sanity check on the short-term MLP's tendency to extrapolate from noisy recent technicals.

Sanitize Layer — _sanitize_predictions v3.7 (Jul 2026)

scripts/predict_core.py — defined in baseline and v3-split paths

Final post-processing pass on the prediction result. Rather than a blunt "clamp fires → floor confidence to 25" mechanic, the current sanitizer distinguishes between model failure (numerical breakage, uncorrelated horizons, opposite-sign disagreement) and coherent extrapolation (raw signal exceeded the cap but the horizons agree with each other about direction and magnitude). Confidence is only mechanically demoted in the former case; in the latter, the model's own confidence is preserved and the UI renders a directional pill instead of a false-precision point target.

1. Vol-scaled per-horizon caps

Base caps 1w ±15%, 1m ±30%, 6m ±60%, 1y ±100% — calibrated to roughly 3σ moves for a 30%-annualized-vol equity. Each is multiplied by max(1, min(2.5, realized_vol_60d / 0.30)) so a high-vol name like WULF (~90% annualized vol) gets caps of 37.5 / 75 / 150 / 250 and doesn't trip the ceiling on every prediction. The realized_vol_60d input is computed from log returns at the top of predict() and stamped onto the result dict for observability.

2. Two-pass confidence rules (Proposal A: signal-aware)

The horizon loop no longer sets confidence in-line. Instead it records a clamp_events map, then a post-loop pass inspects the pattern and decides:

PatternEffect on confidence & ceiling flags
Both 6m + 1y clamped, same direction Keep the model's own confidence_score_6m/1y. Set at_model_ceiling_6m = at_model_ceiling_1y = true, ceiling_direction = 'up' / 'down'. Coherent extrapolation — not a model failure.
Only 1y clamped, 6m same-signed AND |pct_6m| ≥ 0.5 × cap_6m_scaled Same as above but only at_model_ceiling_1y = true. Typical shape: +57% at 6m → clamped +100% at 1y (HBM-style growth).
Only 6m clamped, 1y same-signed AND |pct_1y| ≥ 0.5 × cap_1y_scaled Symmetric to above. Only at_model_ceiling_6m = true.
Only 1y clamped, 6m near zero or opposite direction Confidence → 25 (real outlier). confidence_reason_1y populated with a plain-language explanation the tooltip renders.
Price floor fires (predicted_price < 0.01) Always confidence → 25 — negative price is a numerical failure regardless of horizon shape.
1w clamp — special case Keep confidence if the 1w direction agrees with 1m AND |pct_1w| < |pct_1m| (a volatile stock hitting its 1w cap on the way to a legitimate 1m target). Otherwise floor to 25.
1m clamp Always floor to 25 — no cross-horizon rule at the 1m boundary.
3. Cross-horizon consistency + trajectory smoothness (Proposal 2 + 4)

The historical |pct_6m| > 1.5 × |pct_1y| same-sign check used to blindly clamp pct_6m and floor its confidence to 25. That was a false positive for legitimate cyclical-peak forecasts (semis at ADI-style inflection points: +20% at 6m → +4% at 1y → −13% at 18m). The current gate checks the trajectory shape:

  • Smooth transition (waypoints 6→12 in monthly_trajectory are monotonic) → model is deliberately forecasting peak-and-reverse. Keep the raw 6m target; drop confidence to 60 (Medium) and populate confidence_reason_6m.
  • Non-smooth (waypoint 7 jumps back toward the 1y anchor — real spike outlier) → clamp pct_6m to 1.3 × pct_1y, patch monthly_trajectory[6] to match, drop confidence to 60.
  • Opposite-sign disagreement (|pct_6m| > 5 AND |pct_1y| > 5) → glide-path pct_6m to pct_1y × 0.5, floor confidence to 25.
4. Trajectory + range re-centering

Whenever a horizon clamp fires, both predicted_range_{h} and monthly_trajectory[6]/[12] are re-centered on the clamped price (preserving spread). This prevents the earlier UI bug where the "Range" text on the 6m card floated above the target.

5. Confidence-breakdown emission

confidence_score() now returns (score, breakdown) when return_breakdown=True. The breakdown carries per-component points (cv_mape, history, features, analyst) + raw input values (cv_mape %, history years, imputed field list, analyst count). It flows through predict_long_term.py → the result JSON → prediction_records.confidence_breakdown → the UI tooltip on Medium/Low badges. When the sanitizer manually adjusts a horizon's confidence, it also stamps confidence_reason_{h} with a plain-language explanation that takes precedence over the component-based tooltip.

Both paths run sanitize: the legacy baseline and the v3-split orchestrator each have their own definition of _sanitize_predictions. When updating clamp logic, edit both. The legacy version lives at scripts/predict_weighted_analysis_baseline.py; the v3-split version at scripts/predict_core.py. Both emit [sanitize] stderr lines per clamp event for observability.

8 update_predictions.py — Batch Portfolio Sync

scripts/update_predictions.py

This cron-scheduled Python script is the offline backbone of the prediction pipeline. It runs independently of any user request and produces the data that the recommendations and GPS endpoints serve.

What it does (high level)

  • Queries active portfolio and watchlist positions for users who logged in within the last 7 days.
  • For each unique ticker, fetches enriched data from GET /api/stock_data/{ticker}/data and runs the Python prediction model via POST /api/prediction/{ticker}?outlook=... (one call per timeframe, results merged).
  • Computes GPS v3.0 scores locally using calculate_gps_v3(), the Python mirror of src/utils/gps.ts.
  • Persists all four horizon prices and all eight per-horizon stats to user_stock_predictions via POST /api/prediction/save.
  • Records to prediction_records via record_prediction() (Python sibling of recordPrediction).
  • Scans each user's ETF positions for hot holdings and saves qualifying recommendations to etf_stock_recommendations.

Prediction caching across users

The script maintains a module-level prediction_cache dictionary keyed by ticker. When multiple users share the same stock, the expensive prediction model run happens only once. GPS inputs are stored in the cache entry alongside the raw results so they can be reused without recomputing.

GPS v3.0 mirror: calculate_gps_v3() at the top of update_predictions.py is a direct mirror of calculateGpsScore() in src/utils/gps.ts. Both use the same 8-component model with identical coefficients and clamping logic. When GPS v3.0 changes, both files must be kept in sync.

  4. Call save_prediction() with all four horizon prices + all 8 per-horizon stats + GPS data.
  5. Call record_prediction() to write to prediction_records.
  6. ETF Holdings Scan (see below).
  7. conn.commit() to flush direct GPS writes. Close DB connections.

ETF Holdings Scan

After the main portfolio loop, the script iterates over each user's positions to detect ETFs. For each ETF, it calls GET /api/stock_data/{ticker}/holdings?limit=10 to get the top 10 holdings. For each holding, it runs a full prediction + GPS calculation inside run_prediction_for_holding() (using the shared prediction_cache to avoid redundant model runs). The function also calls record_prediction() internally so every ETF-holding prediction is persisted to prediction_records for accuracy auditing — without this, holdings predictions would be computed and discarded for analytics purposes.

A holding is saved as a recommendation (POST /api/etf/holdings-recommendation) only if it passes all three threshold gates:

  • gps >= gps_threshold
  • predicted_change_pct >= pred_threshold
  • confidence_score >= conf_threshold

GPS scores for holding tickers are also written directly to stock_gps_scores (global per-stock table) via save_gps_score_to_db(), feeding the GET /api/stock_data/{ticker}/gps endpoint's search path.

Strategy-Aware ETF Gates

ETF holding thresholds are computed per user using three layers (v2.8 — preset-driven):

  1. Preset baseline: preset.gpsSurfaceValue and preset.minPredChangePct resolved from ETF_HOLDING_ALGORITHM (1.0–10.0, default 5) via scripts/etf_holding_preset.py → models/etf_holding_presets.json. The independent env var ETF_HOLDING_MIN_CONFIDENCE (default 60) is the third floor.
