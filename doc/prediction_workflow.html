AI Prediction Workflow & Algorithm

scripts/predict_weighted_analysis.py scripts/update_predictions.py src/app/api/prediction/[ticker]/route.ts src/app/api/prediction/save/route.ts src/utils/predictionRecorder.ts src/app/components/StockPrediction.tsx Updated 2026-06-12

This document details the end-to-end execution path and mathematical logic behind the Stock Prediction System (v3.3). The pipeline runs an MLPRegressor (sklearn) trained fresh per request on 5 years of enriched historical data, producing 1-week, 1-month, 6-month, and 1-year price targets with Monte Carlo uncertainty bands and an 18-month trajectory chart.

v3.3 (2026-06-03): Primary short-term outlook changed from 1-day to 1-week (T+5). MLP now has a 4-output head: [T+1, T+5, T+126, T+252]. The 1-week prediction is a blended output (30% MLP T+5 / 70% trajectory interpolation) with an ATR-based movement cap. 118 total FEATURE_COLUMNS including 13 newly added columns. Cache schema version bumped to v2.
v3.4 / June 2026 — Strategy Integration: The prediction pipeline is now strategy-aware end-to-end. The Python script persists all four horizon prices (predicted_price_1w / _1m / _6m / _1y) to the database. The recommendations route, portfolio route, and watchlist route all read the user's investment_timeframe to select the correct horizon column and dynamically patch the GPS breakdown's mlpUpside component via adjustMlpUpsideForHorizon(). The DeepMoney real-time discovery route uses the user's timeframe to set the ML gate threshold and cache bucket. See Strategy Integration and the Strategy System doc for full details.
Regime-Aware Model status (Phases 1–3 complete): Per-request GMM/KMeans regime detection over a 10-dim market vector (VIX, VIX 20d avg, Treasury 10Y, HYG/LQD credit-spread proxy, sector ETF correlation, etc.). select_regime_k() picks K=3 or K=4 against minimum state population (≥15%) and temporal flip-rate (≤30%) constraints. Regime probabilities are appended as 11 additional feature columns before scaling and feed all four MLP horizons.
Prediction Tracking System status (Phases 2–5 complete): Every live UI prediction and every DeepMoney sync stock writes a row to prediction_records via recordPrediction() (fire-and-forget). /api/analytics/model-accuracy is the read consumer and ModelAccuracyWidget surfaces the result. Direction accuracy is the headline metric (per-symbol percentage of resolved predictions whose direction matched the realized price move).

S Strategy Integration (June 2026)

A user's investment strategy has two dimensions: aggressiveness (safe / neutral / aggressive) and investment timeframe (1_week / 1_month / 6_month / 1_year). Both are stored in the user_investment_strategy database table and fetched via getUserStrategy(userId) which falls back to neutral / 1_month if no row exists.

GPS horizon patching

The GPS score is computed globally once and stored in stock_gps_scores using the 1-month predicted change as the mlpUpside component. When a user has a different timeframe set, only the mlpUpside component needs to change — the other 7 components (revenue growth, earnings growth, technicals, analyst upside, analyst consensus, 52-week momentum, AI confidence) are horizon-independent. The adjustMlpUpsideForHorizon(breakdown, horizonDeltaPct) function in src/utils/gps.ts swaps out mlpUpside with the new value computed from horizonDeltaPct / GPS_PREDICTION_MAX × 20 and recomputes the total, delivering a personalized GPS score without re-running the full GPS formula.

// Horizon delta = (predicted_price_horizon - current_price) / current_price * 100 // adjusted mlpUpside = clamp(horizonDelta / predictionMax, -1, 1) * 20 // adjusted score = sum of all 8 components with new mlpUpside, clamped [0, 100]

Market Regime Analysis (Phases 1–3 complete)

GMM on a 10-dimension market vector dominated by VIX (level + 20d average), HYG/LQD credit-spread proxy, Treasury 10Y, sector-ETF correlation, and rolling return distribution stats. K selected by select_regime_k() evaluating K=3 and K=4 against a minimum state population fraction ≥15% and a temporal flip rate ≤30%. Four named states: risk_on_trending, risk_off_stress, high_vol_choppy, low_vol_mean_reverting. Regime probabilities are concatenated with the base feature tensor (11 extra columns) so every MLP horizon output sees the current regime context.

6 Signal Weighting & Trajectory

metric_analysis() + confidence_score()

The raw MLP price targets are multiplied by an impact_multiplier built from additive heuristic signals including RSI, trend, analyst consensus, earnings beat streak, consumer sector multiplier, and high-beta penalty.

1-Week Prediction Blend Logic

_blended_1w = 0.30 * mlp_T5_raw + 0.70 * traj_anchor_1w # traj_anchor = current_price + (predicted_6m - current_price) * (5 / 126) _atr_cap = 2.0 * ATR_14 * sqrt(5) predicted_1w = clip(_blended_1w, current_price - _atr_cap, current_price + _atr_cap)

18-Month Trajectory Generation

19 waypoints at trading-day offsets: [5, 21, 42, 63, 84, 105, 126, …, 378]. The UI prepends a t=0 "Now" dot. MC runs provide spread bands only; midpoints use deterministic MLP outputs.

1-Month Earnings-Window Confidence Dampening

if days_to_earnings <= 14: cs1m = max(0, cs6m - 10) else: cs1m = min(100, cs6m + 10) cs1w = min(100, cs1m + 3)

7 Persistence Layer

POST /api/prediction/save — route.ts + src/utils/predictionRecorder.ts

After a successful prediction run, the API fires two independent async (fire-and-forget) writes:

  • User-facing save: POST /api/prediction/save with the neutral 1-month GPS baseline payload. The save payload accepts all four horizon columns (predicted_price_1w / _1m / _6m / _1y) as optional fields — downstream routes pick the correct column per the user's active timeframe.
  • Analytics record: recordPrediction() (see below) writing one row per (symbol, day) into prediction_records.

Analytics Recording (recordPrediction) documented 2026-06-12

src/utils/predictionRecorder.ts → table prediction_records

Every successful live prediction run from POST /api/prediction/[ticker] fires a fire-and-forget call to recordPrediction() immediately after the Python script returns and before the response is sent. The function does a single INSERT IGNORE keyed on (symbol, predicted_at = CURDATE()), so the second prediction for the same ticker on the same calendar day is silently dropped — preserving the "one prediction per symbol per day" semantic the analytics layer depends on.

INSERT IGNORE INTO prediction_records (
  symbol, predicted_at, price_at_prediction,
  predicted_price_1w, predicted_price_1m, predicted_price_6m, predicted_price_1y
) VALUES (?, CURDATE(), ?, ?, ?, ?, ?)

The same writer is used by scripts/deepmoney_sync.py (via the Python sibling scripts/prediction_recorder.py) so the analytics table accumulates predictions from both the live UI path and the nightly DeepMoney sync without double-counting same-day duplicates.

Downstream consumers:

  • GET /api/analytics/model-accuracy — joins prediction_records with realized-price snapshots and exposes per-symbol direction accuracy, MAPE, hit rate, and sample size.
  • ModelAccuracyWidget — surfaces the headline direction accuracy metric (Phases 2–5 of the Prediction Tracking System are complete).
  • scripts/resolve_predictions.py — backfills realized prices once each horizon matures.

8 update_predictions.py — Batch Portfolio Sync

scripts/update_predictions.py

This cron-scheduled Python script is the backbone of the offline prediction pipeline. It runs independently of the Node.js server and produces the data that the recommendations and GPS endpoints serve.

What it does (high level)

  • Queries active portfolio and watchlist positions for users who logged in within the last 7 days.
  • For each unique ticker, fetches enriched data from GET /api/stock_data/{ticker}/data and runs the Python prediction model via POST /api/prediction/{ticker}?outlook=1_month.
  • Computes GPS v3.0 scores locally using the same formula as src/utils/gps.ts (mirrored Python implementation).
  • Persists all four horizon prices (predicted_price_1w / _1m / _6m / _1y) to user_stock_predictions via POST /api/prediction/save.
  • Scans each user's ETF positions for hot holdings and saves qualifying recommendations to etf_stock_recommendations.

Prediction caching across users

The script maintains a module-level prediction_cache dictionary keyed by ticker. When multiple users share the same stock, the expensive prediction model run happens only once. GPS inputs are stored in the cache entry alongside the raw results so they can be reused without recomputing them.

GPS v3.0 mirror: The Python implementation of calculate_gps_v3() at the top of update_predictions.py is a direct mirror of calculateGpsScore() in src/utils/gps.ts. Both use the same 8-component model with identical coefficients and clamping logic. When GPS v3.0 changes, both files must be kept in sync.

Step-by-step flow

  1. Connect to MySQL. Execute ACTIVE_PORTFOLIO_QUERY — joins users, user_stocks, stocks. Filters last_login >= NOW() - INTERVAL 7 DAY, is_active = 1, user_confirmed = 1, and either is_purchased = 1 AND shares > 0 (portfolio) or is_purchased = 0 (watchlist).
  2. Batch-fetch all user strategies via get_all_user_strategies(cursor, user_ids). This loads each user's aggressiveness and investment_timeframe for later use in ETF gate calculation.
  3. For each row: check prediction_cache. If miss, call fetch_stock_data(ticker) and run_prediction(ticker, stock_data). Compute GPS. Store in cache.
  4. Call save_prediction() with all four horizon prices and GPS data.
  5. ETF Holdings Scan (see below).
  6. conn.commit() to flush direct GPS writes. Close DB connections.

ETF Holdings Scan

After the main portfolio loop, the script iterates over each user's positions to detect ETFs. For each ETF, it calls GET /api/stock_data/{ticker}/holdings?limit=10 to get the top 10 holdings. For each holding, it runs a full prediction + GPS calculation (using the shared prediction_cache to avoid redundant model runs).

A holding is saved as a recommendation (POST /api/etf/holdings-recommendation) only if it passes all three threshold gates:

  • gps >= gps_threshold
  • predicted_change_pct >= pred_threshold
  • confidence_score >= conf_threshold

GPS scores for holding tickers are also written directly to stock_gps_scores (global per-stock table) via save_gps_score_to_db(), feeding the GET /api/stock_data/{ticker}/gps endpoint's search path.

Strategy-Aware ETF Gates updated 2026-06-09

ETF holding thresholds are not one-size-fits-all. They are computed per user using three layers:

  1. Environment baseline: ETF_HOLDING_GPS_SURFACE_VALUE (default 60), ETF_HOLDING_MIN_PRED_CHANGE (default 1.5%), ETF_HOLDING_MIN_CONFIDENCE (default 60).
  2. Aggressiveness multiplier from resolve_strategy(user_strategy): safe=1.05, neutral=1.0, aggressive=0.95. Applied to all three baseline thresholds. Safe users require higher scores; aggressive users accept lower scores.
  3. Predicted-change floor: max(env_pred_threshold * mult, gates['predChangeGate']). This means if the strategy's own absolute gate (safe=3%, neutral=1.5%, aggressive=0.5%) is stricter than the env-scaled baseline, it takes priority.
gps_threshold = ETF_HOLDING_GPS_SURFACE_VALUE * mult pred_threshold = max(ETF_HOLDING_MIN_PRED_CHANGE * mult, gates.predChangeGate) conf_threshold = ETF_HOLDING_MIN_CONFIDENCE * mult # Example: safe user (mult=1.05, predChangeGate=3.0) # gps_threshold = 60 * 1.05 = 63.0 # pred_threshold = max(1.5 * 1.05, 3.0) = max(1.575, 3.0) = 3.0% # conf_threshold = 60 * 1.05 = 63.0 # Example: aggressive user (mult=0.95, predChangeGate=0.5) # gps_threshold = 60 * 0.95 = 57.0 # pred_threshold = max(1.5 * 0.95, 0.5) = max(1.425, 0.5) = 1.425% # conf_threshold = 60 * 0.95 = 57.0

Cache Architecture

  • Result cache (v2): keyed by MD5(ticker + last_date + data_len + "v2"). Full prediction JSON stored as {key}.json. Bumping CACHE_SCHEMA_VERSION constant invalidates all stale caches automatically.
  • Feature cache: full feature DataFrame stored as {ticker}_features_df.pkl. Incremental updates only recompute new rows.
  • Server-side in-memory cache: predictionCache keyed by {ticker}_{outlook}. Bypassed by ?refresh=true.

CPU throttled via environment variables (OMP_NUM_THREADS=1, etc.) and os.nice(15).
