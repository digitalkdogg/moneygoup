AI Prediction Workflow & Algorithm

scripts/predict_weighted_analysis.py scripts/update_predictions.py src/app/api/prediction/[ticker]/route.ts src/app/api/prediction/save/route.ts src/utils/predictionRecorder.ts src/app/components/StockPrediction.tsx Updated 2026-06-15

This document details the end-to-end execution path and mathematical logic behind the Stock Prediction System (v3.4). The pipeline runs an MLPRegressor (sklearn) trained fresh per request on 5 years of enriched historical data, producing 1-week, 1-month, 6-month, and 1-year price targets with Monte Carlo uncertainty bands and an 18-month trajectory chart. A single Python invocation returns all four horizons at once.

v3.4.1 / June 2026 — Dual-GPS & full horizon persistence:
  • POST /api/prediction/[ticker] now runs the Python model once and computes two GPS scores from the result: a neutral 1-month baseline (saved to the global stock_gps_scores table) and a user-horizon GPS built from the horizon-matched predicted_change_pct_* / confidence_score_* fields and returned in the response as gps_score + gps_breakdown + gps_horizon.
  • savePredictionAsync() now forwards all eight per-horizon outputs (four predicted_change_pct_{1w,1m,6m,1y} + four confidence_score_{1w,1m,6m,1y}) plus all four predicted_price_{1w,1m,6m,1y} to /api/prediction/save. Previously only the 1m price was sent.
  • POST /api/prediction/save accepts those eight new optional Zod fields and persists them to user_stock_predictions. The dashboard can now recompute horizon-aware GPS using the model's own outputs instead of a price-derived approximation.
  • scripts/update_predictions.py captures all eight per-horizon stats from the Python result, threads them through save_prediction() kwargs, and stores them in the in-process prediction_cache (and the _empty_cache_entry() sentinel) so cached-prediction branches also forward the per-horizon fields.
v3.3 (2026-06-03): Primary short-term outlook changed from 1-day to 1-week (T+5). MLP now has a 4-output head: [T+1, T+5, T+126, T+252]. The 1-week prediction is a blended output (30% MLP T+5 / 70% trajectory interpolation) with an ATR-based movement cap. 118 total FEATURE_COLUMNS including 13 newly added columns. Cache schema version bumped to v2.
Regime-Aware Model status (Phases 1–3 complete): Per-request GMM/KMeans regime detection over a 10-dim market vector (VIX, VIX 20d avg, Treasury 10Y, HYG/LQD credit-spread proxy, sector ETF correlation, etc.). select_regime_k() picks K=3 or K=4 against minimum state population (≥15%) and temporal flip-rate (≤30%) constraints. Regime probabilities are appended as 11 additional feature columns before scaling and feed all four MLP horizons.
Prediction Tracking System status (Phases 2–5 complete): Every live UI prediction and every DeepMoney sync stock writes a row to prediction_records via recordPrediction() (fire-and-forget). /api/analytics/model-accuracy is the read consumer and ModelAccuracyWidget surfaces the result. Direction accuracy is the headline metric.

L End-to-End Lifecycle

The complete path from "user clicks predict" to "row written to user_stock_predictions / stock_gps_scores":

  1. UI trigger. User clicks the Predict button in StockPrediction.tsx on /search/[ticker]. The component first fetches enriched data from GET /api/stock_data/[ticker]/data, then posts the resulting JSON body to POST /api/prediction/[ticker].
  2. Guard chain. The route validates origin, session, approval status, lookup quota, ticker format, body shape (historicalData length ≥ 365 + stockMetrics object), and the outlook query value. Internal calls (x-api-key) skip session + lookup checks.
  3. Cache check. Unless ?refresh=true is set, the route consults the in-memory predictionCache at key {ticker}_{outlook}. On a hit, the Python script is skipped entirely — but GPS is still computed live from the cached result because GPS is per-user.
  4. Concurrency gate. If the cache misses, the route acquires a slot from predictionSemaphore (503 Busy if full).
  5. Python model. A temp JSON file is written and scripts/predict_weighted_analysis.py is spawned. The Python script always trains a fresh MLP and returns all four horizons in one call (see Single Call → 4 Horizons). The result includes predicted_price_{1w,1m,6m,1y}, predicted_change_pct_{1w,1m,6m,1y}, confidence_score_{1w,1m,6m,1y}, the 18-month trajectory, accuracy metrics, and regime info.
  6. Analytics record. Immediately after Python returns, recordPrediction() fires once (fire-and-forget) to insert a row into prediction_records.
  7. Generic-key backfill + cache write. The route populates legacy predicted_price / predicted_change_pct / confidence_score keys based on the requested outlook and stores the result in predictionCache.
  8. Dual GPS computation. buildResponse() computes the neutral 1m baseline GPS (used for persistence) and the user-horizon GPS (returned to the caller). See Dual GPS Computation.
  9. Async persistence. savePredictionAsync() POSTs the model output to /api/prediction/save with all four horizon prices, all four per-horizon change percentages, all four per-horizon confidence scores, and the baseline 1m GPS. This call is fire-and-forget; the user response does not wait for it.
  10. Save route. /api/prediction/save upserts user_stock_predictions (per-user, prices + per-horizon stats) and upserts stock_gps_scores + appends stock_gps_score_history with the GPS baseline (global, one row per stock).
  11. Response. The caller receives the full model output merged with source, gps_score (horizon-matched), gps_breakdown, and gps_horizon.

S Strategy Integration

A user's investment strategy has two dimensions: aggressiveness (safe / neutral / aggressive) and investment timeframe (1_week / 1_month / 6_month / 1_year). Both are stored in the user_investment_strategy database table and fetched via getUserStrategy(userId) which falls back to DEFAULT_STRATEGY (neutral / 1_month) if no row exists.

GPS horizon patching downstream

The baseline GPS persisted globally uses the 1-month predicted change as the mlpUpside component. When a downstream route serves a user whose timeframe is not 1-month, only the mlpUpside component needs to change — the other 7 components (revenue growth, earnings growth, technicals, analyst upside, analyst consensus, 52-week momentum, AI confidence) are horizon-independent. adjustMlpUpsideForHorizon(breakdown, horizonDeltaPct) in src/utils/gps.ts swaps mlpUpside with the new value and recomputes the total.

// Horizon delta = (predicted_price_horizon - current_price) / current_price * 100 // adjusted mlpUpside = clamp(horizonDelta / predictionMax, -1, 1) * 20 // adjusted score = sum of all 8 components with new mlpUpside, clamped [0, 100]

Because /api/prediction/save now persists the per-horizon predicted_change_pct_* + confidence_score_* directly, downstream routes can plug the model's own outputs into the GPS formula rather than deriving the delta from possibly-stale price columns.

Dual GPS Computation v3.4.1

After the Python script returns (or a cached result is read), buildResponse() computes two GPS scores from the same prediction result:

GPS variantInputsUsed for
Baseline 1m GPS (baselineGps)predicted_change_pct_1m + confidence_score_1mPersisted globally to stock_gps_scores by savePredictionAsync(). One row per stock; horizon-neutral so the global table stays coherent across users.
User-horizon GPS (computedGps)predicted_change_pct_{horizon} + confidence_score_{horizon} where {horizon} is resolved from getUserStrategy(userId).investment_timeframeReturned in the HTTP response as gps_score, gps_breakdown, and gps_horizon. Not persisted.

The suffix map inside buildResponse() is:

{ '1week': '1w', '1month': '1m', '6month': '6m', '1year': '1y' }

If the user's timeframe is missing or unrecognised, the function falls back to the 1m fields, meaning the user-horizon GPS equals the baseline GPS for the default neutral / 1_month strategy.

Internal calls (userId === 'internal') skip GPS computation entirely — buildResponse() only computes GPS when !isInternal and the result contains predicted_price_1m. Internal consumers (DeepMoney sync, batch update) compute GPS themselves using calculate_gps_v3() in Python.

The cache-hit branch deliberately skips persistence: the global GPS row was already written when the cache entry was first computed, so re-writing it on every subsequent hit during the cache lifetime would be wasted work. GPS is still computed live on hits so the response always reflects the calling user's timeframe.

Market Regime Analysis (Phases 1–3 complete)

GMM on a 10-dimension market vector dominated by VIX (level + 20d average), HYG/LQD credit-spread proxy, Treasury 10Y, sector-ETF correlation, and rolling return distribution stats. K selected by select_regime_k() evaluating K=3 and K=4 against a minimum state population fraction ≥15% and a temporal flip rate ≤30%. Four named states: risk_on_trending, risk_off_stress, high_vol_choppy, low_vol_mean_reverting. Regime probabilities are concatenated with the base feature tensor (11 extra columns) so every MLP horizon output sees the current regime context.

6 Signal Weighting & Trajectory

metric_analysis() + confidence_score()

The raw MLP price targets are multiplied by an impact_multiplier built from additive heuristic signals including RSI, trend, analyst consensus, earnings beat streak, consumer sector multiplier, and high-beta penalty.

1-Week Prediction Blend Logic

_blended_1w = 0.30 * mlp_T5_raw + 0.70 * traj_anchor_1w # traj_anchor = current_price + (predicted_6m - current_price) * (5 / 126) _atr_cap = 2.0 * ATR_14 * sqrt(5) predicted_1w = clip(_blended_1w, current_price - _atr_cap, current_price + _atr_cap)

18-Month Trajectory Generation

19 waypoints at trading-day offsets: [5, 21, 42, 63, 84, 105, 126, …, 378]. The UI prepends a t=0 "Now" dot. MC runs provide spread bands only; midpoints use deterministic MLP outputs.

1-Month Earnings-Window Confidence Dampening

if days_to_earnings <= 14: cs1m = max(0, cs6m - 10) else: cs1m = min(100, cs6m + 10) cs1w = min(100, cs1m + 3)

7 Persistence Layer

savePredictionAsync() → POST /api/prediction/save → user_stock_predictions + stock_gps_scores

After a successful livedata prediction run, the route fires two independent fire-and-forget writes:

  • Analytics record (always, immediately after Python returns): recordPrediction() inserts one row per (symbol, CURDATE()) into prediction_records.
  • User-facing save (only when source === 'livedata' and a baseline GPS was computed): savePredictionAsync() posts to /api/prediction/save with prices + per-horizon stats + the baseline 1m GPS.

Why all 8 per-horizon stats? Persisting predicted_change_pct_* and confidence_score_* next to the prices lets the dashboard, portfolio, and watchlist routes recompute horizon-aware GPS using the model's own outputs. Previously they had to derive the horizon delta from predicted_price_horizon − current_price, which becomes inaccurate as the current price drifts between prediction runs.

Field assignment is surgical: each field is only written when present in the payload. A run that produces a 1m price but no 6m price will not clobber an existing predicted_price_6m in the database.

Writes:

  1. Upsert user_stock_predictions (unique key (user_id, stock_id)) — prices + per-horizon stats + last_requested_at.
  2. Skip-if-unchanged guard on the global GPS write: reads current gps_score from stock_gps_scores and only proceeds if it differs at one-decimal precision.
  3. Upsert stock_gps_scores (one row per stock) — sets as_of, gps_score, gps_breakdown, source = 'prediction_engine'.
  4. Append stock_gps_score_history (INSERT IGNORE) — time-series ledger of every score change.
  5. Legacy sync: UPDATE recommended_stocks for the most recent snapshot_date of this ticker (no-op if absent).

Analytics Recording (recordPrediction)

src/utils/predictionRecorder.ts → table prediction_records

Every successful live prediction run from POST /api/prediction/[ticker] fires a fire-and-forget call to recordPrediction() immediately after the Python script returns and before the response is sent. The function does a single INSERT IGNORE keyed on (symbol, predicted_at = CURDATE()), so the second prediction for the same ticker on the same calendar day is silently dropped — preserving the "one prediction per symbol per day" semantic the analytics layer depends on.

INSERT IGNORE INTO prediction_records (
  symbol, predicted_at, price_at_prediction,
  predicted_price_1w, predicted_price_1m, predicted_price_6m, predicted_price_1y
) VALUES (?, CURDATE(), ?, ?, ?, ?, ?)

8 update_predictions.py — Batch Portfolio Sync

scripts/update_predictions.py

This cron-scheduled Python script is the offline backbone of the prediction pipeline. It runs independently of any user request and produces the data that the recommendations and GPS endpoints serve.

What it does (high level)

  • Queries active portfolio and watchlist positions for users who logged in within the last 7 days.
  • For each unique ticker, fetches enriched data from GET /api/stock_data/{ticker}/data and runs the Python prediction model via POST /api/prediction/{ticker}?outlook=... (one call per timeframe, results merged).
  • Computes GPS v3.0 scores locally using calculate_gps_v3(), the Python mirror of src/utils/gps.ts.
  • Persists all four horizon prices and all eight per-horizon stats to user_stock_predictions via POST /api/prediction/save.
  • Records to prediction_records via record_prediction() (Python sibling of recordPrediction).
  • Scans each user's ETF positions for hot holdings and saves qualifying recommendations to etf_stock_recommendations.

Prediction caching across users

The script maintains a module-level prediction_cache dictionary keyed by ticker. When multiple users share the same stock, the expensive prediction model run happens only once. GPS inputs are stored in the cache entry alongside the raw results so they can be reused without recomputing.

GPS v3.0 mirror: calculate_gps_v3() at the top of update_predictions.py is a direct mirror of calculateGpsScore() in src/utils/gps.ts. Both use the same 8-component model with identical coefficients and clamping logic. When GPS v3.0 changes, both files must be kept in sync.

Step-by-step flow

  1. Connect to MySQL. Execute ACTIVE_PORTFOLIO_QUERY — joins users, user_stocks, stocks. Filters last_login >= NOW() - INTERVAL 7 DAY, is_active = 1, user_confirmed = 1, and either is_purchased = 1 AND shares > 0 (portfolio) or is_purchased = 0 (watchlist).
  2. Batch-fetch all user strategies via get_all_user_strategies(cursor, user_ids). This loads each user's aggressiveness and investment_timeframe for later use in ETF gate calculation.
  3. For each row: check prediction_cache. If miss, call fetch_stock_data(ticker) and run_prediction(ticker, stock_data). Extract all 8 per-horizon stats. Compute GPS v3.0. Store everything in cache.
  4. Call save_prediction() with all four horizon prices + all 8 per-horizon stats + GPS data.
  5. Call record_prediction() to write to prediction_records.
  6. ETF Holdings Scan (see below).
  7. conn.commit() to flush direct GPS writes. Close DB connections.

ETF Holdings Scan

After the main portfolio loop, the script iterates over each user's positions to detect ETFs. For each ETF, it calls GET /api/stock_data/{ticker}/holdings?limit=10 to get the top 10 holdings. For each holding, it runs a full prediction + GPS calculation (using the shared prediction_cache to avoid redundant model runs).

A holding is saved as a recommendation (POST /api/etf/holdings-recommendation) only if it passes all three threshold gates:

  • gps >= gps_threshold
  • predicted_change_pct >= pred_threshold
  • confidence_score >= conf_threshold

GPS scores for holding tickers are also written directly to stock_gps_scores (global per-stock table) via save_gps_score_to_db(), feeding the GET /api/stock_data/{ticker}/gps endpoint's search path.

Strategy-Aware ETF Gates

ETF holding thresholds are computed per user using three layers:

  1. Environment baseline: ETF_HOLDING_GPS_SURFACE_VALUE (default 60), ETF_HOLDING_MIN_PRED_CHANGE (default 1.5%), ETF_HOLDING_MIN_CONFIDENCE (default 60).
  2. Aggressiveness multiplier from resolve_strategy(user_strategy): safe=1.05, neutral=1.0, aggressive=0.95. Applied to all three baseline thresholds. Safe users require higher scores; aggressive users accept lower scores.
  3. Predicted-change floor: max(env_pred_threshold * mult, gates['predChangeGate']). If the strategy's own absolute gate (safe=3%, neutral=1.5%, aggressive=0.5%) is stricter than the env-scaled baseline, it takes priority.
gps_threshold = ETF_HOLDING_GPS_SURFACE_VALUE * mult pred_threshold = max(ETF_HOLDING_MIN_PRED_CHANGE * mult, gates.predChangeGate) conf_threshold = ETF_HOLDING_MIN_CONFIDENCE * mult # Example: safe user (mult=1.05, predChangeGate=3.0) # gps_threshold = 60 * 1.05 = 63.0 # pred_threshold = max(1.5 * 1.05, 3.0) = max(1.575, 3.0) = 3.0% # conf_threshold = 60 * 1.05 = 63.0 # Example: aggressive user (mult=0.95, predChangeGate=0.5) # gps_threshold = 60 * 0.95 = 57.0 # pred_threshold = max(1.5 * 0.95, 0.5) = max(1.425, 0.5) = 1.425% # conf_threshold = 60 * 0.95 = 57.0

Cache Architecture

  • Python result cache (v2): keyed by MD5(ticker + last_date + data_len + "v2"). Full prediction JSON stored as {key}.json on disk. Bumping CACHE_SCHEMA_VERSION invalidates all stale caches automatically.
  • Python feature cache: full feature DataFrame stored as {ticker}_features_df.pkl. Incremental updates only recompute new rows.
  • Node in-memory cache: predictionCache (defined in src/utils/cache.ts) keyed by {ticker}_{outlook}. Short-lived (TTL constant in cache.ts; ≈ 15 minutes by design). Bypassed by ?refresh=true. The cached entry includes every horizon's price, change %, and confidence score so user-horizon GPS can be recomputed on subsequent calls without re-running Python.
  • Batch script in-process cache: the prediction_cache dict inside update_predictions.py lives only for the duration of one sync run. Keyed by ticker; entries include all 8 per-horizon stats and the GPS result so multiple users sharing a ticker each get the right values without re-running the model.

CPU throttled via environment variables (OMP_NUM_THREADS=1, etc.) and os.nice(15).
