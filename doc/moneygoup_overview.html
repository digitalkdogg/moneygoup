MoneyGoUp Web Application Overview

A brief end-to-end tour of the product, the stack, and how the pieces fit together. This page is the front door for the documentation set — every section ends with a pointer to a deeper doc when one exists.

1. What is MoneyGoUp

MoneyGoUp (brand: GrowMyStocks) is a personalized investing dashboard. It combines live market data, an in-house AI prediction model, and a unified GPS score to surface BUY / HOLD / SELL signals against the user's portfolio, watchlist, and a daily discovery feed.

The defining product idea is that every personalized number on screen is filtered through the user's own strategy — an investment_timeframe (1 week / 1 month / 6 month / 1 year) crossed with an aggressiveness setting (safe / neutral / aggressive). Two users looking at the same ticker on the same day can see different scores, different recommendations, and different price targets.

A secondary, but core, capability is that every AI forecast the platform produces is silently logged and graded against reality. Direction accuracy (did the model get up/down right?) is the headline quality metric exposed back to users on the dashboard.

4. Key User Flow

  1. Sign in. NextAuth resolves the session. New accounts must be admin-approved before this step succeeds — see Admin User Mgmt.
  2. Dashboard loads. Portfolio cards, watchlist cards, and a three-bucket recommendations feed (portfolio / watchlist / discovery) are aggregated from /api/dashboard and /api/dashboard/recommendations.
  3. Strategy is resolved. The user's investment_timeframe and aggressiveness are read from user_investment_strategy via src/utils/strategy.ts. Defaults are neutral + 1_month.
  4. GPS scores are patched per-horizon. Cached scores are read from stock_gps_scores and then adjusted with adjustGpsForHorizon (src/utils/gps.ts) so the displayed score matches the user's timeframe exactly — no separate row is stored per horizon.
  5. User drills into a ticker. /search/[ticker] renders the GPS signal panel + AI prediction card. Clicking the prediction CTA spawns the Python MLP inline through POST /api/prediction/[ticker].
  6. Predictions are recorded. Every successful inference fires recordPrediction() as a non-blocking side-effect, writing one row per (symbol, predicted_at) into prediction_records for later grading.

Deeper dives: Prediction Workflow, Recommendation Buckets, GPS Score.

5. Personalization Model

The two strategy axes combine into a single StrategyConfig object that every personalized route reads before producing numbers.

  • Aggressiveness safe / neutral / aggressive — sets the gating bar (confidence floor, beta cutoff, GPS gate, predicted-change gate, and an env-floor multiplier of 1.05× / 1.0× / 0.95×).
  • Investment timeframe 1_week / 1_month / 6_month / 1_year — selects which predicted-price column to read from user_stock_predictions, sets the outlook passed to the Python MLP, scales the predicted-change gate, shifts the sell-side threshold, and chooses the DeepMoney ML gate and the UI display label.
  • Where it is applied Recommendation gates, DeepMoney candidate filtering, single-ticker GPS adjustment, and the prediction outlook are all derived from the same resolved config.
The single source of truth for the gate matrix, default fallback, and every multiplier is Strategy System. If a number on the dashboard looks "wrong" for a given user, the explanation almost always lives in their strategy row.

6. Recommendation Buckets

The recommendation engine classifies stocks into four buckets so that user-owned positions, monitored interests, AI discoveries, and ETF top-holding breakouts each get the right level of urgency and validation. Every BUY / SELL card on the dashboard belongs to one of these four buckets.

June 2026: A fourth bucket — ETF Holding — was added. When a user holds ETFs in their portfolio, the /portfolio page surfaces BUY recommendations for high-GPS individual stocks found inside those ETFs.
📊 Bucket 1: Portfolio

Positions the user has officially purchased and confirmed. Real financial stakes, so signals require the highest precision.

  • Signals: Surfaces both BUY (add to position) and SELL (exit/trim) alerts.
  • Logic: Compares the AI 1-month prediction against the current live market price.
  • Badge color: Blue (bg-blue-100 text-blue-700)
is_purchased = 1 AND user_confirmed = 1 AND shares > 0 AND is_active = 1
Positive: +3% (default)
Negative: -3% (default)
👀 Bucket 2: Watchlist

Stocks the user is actively monitoring but doesn't yet own. Explicitly "confirmed" by the user (e.g. via "Add to Watchlist").

  • Signals: Surfaces BUY alerts only.
  • Logic: Monitors for significant upward breakouts predicted by the AI.
  • Badge color: Amber (bg-amber-100 text-amber-700)
is_purchased = 0 AND user_confirmed = 1 AND is_active = 1
Threshold: +5% (default)
✨ Bucket 3: Discovery

High-potential stocks identified automatically by the deepmoney_sync.py engine. Appear as "unconfirmed" and don't show in "My Watchlist" until the user interacts with them.

  • Discovery logic: Stocks qualify when they survive the full deepmoney pipeline (signalScoreFloor pre-filter + ranker keep-cut + MLP confidence floor + predicted-change gate). All thresholds are resolved from DEEPMONEY_ALGORITHM via models/algorithm_presets.json.
  • Target users: Qualifying stocks are added for every approved user.
  • Signals: Surfaces BUY alerts only.
  • Badge color: Purple (bg-purple-100 text-purple-700)
is_purchased = 0 AND user_confirmed = 0 AND is_active = 1
Threshold: +5% (default)
🏭 Bucket 4: ETF Holding new

Individual stocks that are top holdings inside ETFs the user already owns. When the ML pipeline identifies a high-GPS breakout candidate inside one of the user's ETFs, it surfaces that holding as a direct BUY recommendation with a teal "etf holding" badge.

  • Signals: Surfaces BUY alerts only (holdings are pre-filtered by the ETF sync before being written to etf_stock_recommendations).
  • Source: Written by scripts/update_predictions.py during the ETF Holdings scan phase, which runs after standard portfolio predictions.
  • Detection: Each portfolio item is checked against Yahoo Finance's quoteType. If quoteType === 'ETF', the item is flagged is_etf: true and its top holdings are fetched via GET /api/stock_data/{ticker}/holdings.
  • Thresholds (all three must be met):
    • GPS score ≥ preset.gpsSurfaceValue (L5 default 60) — resolved from ETF_HOLDING_ALGORITHM via models/etf_holding_presets.json
    • Predicted price change ≥ preset.minPredChangePct% (L5 default 1.8%) — same source
    • AI confidence score ≥ ETF_HOLDING_MIN_CONFIDENCE (default 60) — independent of the preset
  • Card sub-label: "In {ETF ticker}" (e.g. "In VGT") so the user knows which of their ETFs contains this holding.
  • Badge color: Teal (bg-teal-100 text-teal-700) · Scope: 'etf_holding' · Extra field: etfTicker
Source: etf_stock_recommendations table
GPS ≥ preset.gpsSurfaceValue (L5=60)
predicted_change_pct ≥ preset.minPredChangePct (L5=1.8%)
confidence_score ≥ ETF_HOLDING_MIN_CONFIDENCE (default 60)
Preset resolved from ETF_HOLDING_ALGORITHM (1.0..10.0, default 5)

UI filtering on the Portfolio page

The etf_holding scope is only enabled on /portfolio — the dashboard home page (/) doesn't include it. Controlled by the scopes prop on RecommendationsSection.

The /portfolio page derives two values from the portfolio API response:

  • portfolioEtfTickers — array of symbols where is_etf === true (e.g. ['VGT', 'QQQ'])
  • hasEtfInPortfolio — boolean derived from portfolioEtfTickers.length > 0

When hasEtfInPortfolio is true, the page passes:

scopes={['portfolio', 'watchlist', 'etf_holding']}
portfolioEtfTickers={portfolioEtfTickers}

Inside RecommendationsSection, a secondary client-side filter ensures etf_holding cards only show when r.etfTicker is in the portfolioEtfTickers set. This prevents watchlist-only ETF holding cards from leaking onto the portfolio grid. Users without ETFs get the scope omitted entirely, so no ETF holding cards render.

7. Background Jobs

Two Python scripts keep cached predictions and discovery picks fresh. Both authenticate to the Next.js API using the internal x-api-key header (src/utils/internalAuth.ts) and hit http://localhost:3001 directly to bypass the nginx 60-second proxy timeout.

  • scripts/update_predictions.py — Refreshes cached MLP predictions overnight (and on demand) so the dashboard does not have to spawn Python for every render.
  • scripts/deepmoney_sync.py — Runs the DeepMoney discovery pipeline: macro context fetch, recursive news discovery, ML validation gate, then commits to recommended_stocks and hot_etfs. Full breakdown in DeepMoney Sync.

DeepMoney sync pipeline + ETF holdings
DEEPMONEY_ALGORITHM optional · 5
OverviewThe single knob controlling deepmoney pipeline aggressiveness end-to-end. Float 1.0–10.0; lower = stricter, higher = more permissive. Resolves through models/algorithm_presets.json into five fields: rankerKeepPct, mlpConfidenceFloor, volGateFloor, analystStrongBuyThreshold, signalScoreFloor. Fractional values (e.g. 1.5) interpolate linearly; mlpConfidenceFloor and volGateFloor are then snapped UP to the next discrete MLP bucket in {35, 50, 65, 75} (the only values the model emits). Replaces the retired DEEPMONEY_GPS_VALUE, DEEPMONEY_RECOMMENDATION_GPS_VALUE, DEEPMONEY_ANALYST_THRESHOLD, DEEPMONEY_USE_RANKER_GATE, and DEEPMONEY_TIER2_TOPK.
Where usedsrc/utils/algorithmPreset.ts (single read), src/app/api/prediction/deepmoney/route.ts (echoes the resolved preset in meta.algorithm), scripts/deepmoney_sync.py (reads back from meta.algorithm). Full detail: DeepMoney Sync.
Visible onThe dashboard's DeepMoney Picks widget, the DISCOVERY cards on /dashboard, and the per-user ETF Holding cards on /portfolio — all three are populated by the nightly deepmoney_sync.py run, which uses the resolved preset to gate every stock written to recommended_stocks. Lower the number = fewer cards everywhere; higher = more.
TuningMove the whole pipeline in one direction with one number: 
DEEPMONEY_ALGORITHM=1.5   # very strict: top ~7% by ranker, effective CS ≥ 75 (top bucket only)
DEEPMONEY_ALGORITHM=5     # default: top 25%, effective CS ≥ 65 (raw 60 snaps up)
DEEPMONEY_ALGORITHM=8     # loose: top 60%, effective CS ≥ 50 (raw 45 snaps up)
ETF_HOLDING_ALGORITHM optional · 5
OverviewThe single knob controlling ETF qualification + holdings surfacing aggressiveness end-to-end. Float 1.0–10.0; lower = stricter, higher = more permissive. Resolves through models/etf_holding_presets.json into five fields: etfGpsThreshold (minimum ETF GPS to qualify as "hot"), topNEtfs (how many qualifying ETFs survive), maxTickers (per-ETF holdings fetch + scoring cap), gpsSurfaceValue (minimum holding GPS to surface), minPredChangePct (minimum predicted-change % for a holding to surface). Fractional values (e.g. 1.5) interpolate linearly. Replaces the retired ETF_GPS_THRESHOLD (in-code constant), ETF_HOLDING_MAX_TICKERS, ETF_HOLDING_GPS_SURFACE_VALUE, and ETF_HOLDING_MIN_PRED_CHANGE.
Where usedsrc/utils/etfHoldingPreset.ts (single read), src/utils/etfDiscovery.ts (qualification + top-N + per-ETF cap), src/utils/etfHoldings.ts (post-dedup cap + surfacing thresholds), src/app/api/stock_data/[ticker]/holdings/route.ts (read-side surfacing), src/app/api/dashboard/deepmoney-picks/route.ts (widget read-side filter), scripts/update_predictions.py (per-user ETF holding sync, via scripts/etf_holding_preset.py).
Visible onThe ETF Holding cards on /portfolio when the user owns an ETF (e.g. SPY, QQQ, VGT), the dashboard's DeepMoney Picks widget (which ETFs render), and the per-ETF holdings response served by /api/stock_data/<TICKER>/holdings. Lower the number = stricter qualification + fewer holdings surface across all three; higher = more.
TuningMove the whole ETF pipeline in one direction with one number:

ETF_HOLDING_ALGORITHM=5     # default:   GPS≥58, top 11, 56 holdings, surface≥60, pred≥1.8%
ETF_HOLDING_ALGORITHM=10    # loosest:   GPS≥45, top 20, 100 holdings, surface≥45, pred≥0.5%

OverviewBaseline minimum MLP confidence (0–100) for an ETF holding to surface as a recommendation. Scaled per-user by aggressiveness. Independent of ETF_HOLDING_ALGORITHM; layers on top as a third gate (GPS ∧ pred-change ∧ confidence).

Prediction / GPS scoring
GPS_PREDICTION_MAX optional · 3
OverviewSaturation point for the mlpUpside component of the GPS score. Formula: mlpUpside = clamp(predicted_change_pct / GPS_PREDICTION_MAX, -1, 1) × 20. Lower = component saturates faster (a +3% prediction pegs the full 20 pts); higher = component is more discriminating across a wider range.
Where usedsrc/utils/gps.ts (calculateGpsScore and adjustGpsForHorizon), scripts/update_predictions.py (calculate_gps_v3 mirror), src/app/api/stock_data/[ticker]/holdings/route.ts (inverse — recovers predicted_change_pct from stored breakdown).
Visible onThe GPS number on every card with a GPS score — portfolio cards on /portfolio, watchlist cards on /dashboard, BUY / SELL / DISCOVERY cards on /dashboard, the GPS panel on /search/[ticker], and the GpsBreakdownModal shown when a user taps a GPS number. Changing it shifts how aggressively prediction strength gets converted into the visible score.
Tuning 
GPS_PREDICTION_MAX=3      # default: tight 3% saturation
GPS_PREDICTION_MAX=15     # current prod: 15% saturation
GPS_BASELINE optional · 65
OverviewAnchor for the dashboard's BUY / SELL / DISCOVERY card rendering. BUY threshold = GPS_BASELINE; SELL = baseline + GPS_SELL_OFFSET; DISCOVERY = baseline + GPS_DISCOVERY_OFFSET. Then strategy envFloorMultiplier (safe×1.05, aggressive×0.95) scales BUY and DISCOVERY per user.
Where usedsrc/app/api/dashboard/recommendations/route.ts.
Visible onThe BUY cards on the /dashboard Recommendations strip, and the matching cards on /portfolio. Raising = fewer BUY cards render; safe-strategy users see an even tighter set than aggressive users for the same baseline.
TuningRaise to be more selective on BUY cards: 
GPS_BASELINE=62           # current: BUY at 62, scales 65.1 (safe) / 58.9 (aggressive)
GPS_BASELINE=75           # stricter: BUY only above 75
GPS_SELL_OFFSET optional · -20
OverviewOffset added to GPS_BASELINE to compute the SELL warning threshold. Almost always negative — SELL fires when GPS drops well below the BUY anchor. Not scaled by aggressiveness; warnings fire regardless of strategy.
Where usedsrc/app/api/dashboard/recommendations/route.ts.
Visible onThe SELL warning cards on /dashboard (red-bordered cards on the portfolio side). More negative = SELL warnings fire later (only on deeper score drops); less negative = warnings fire more eagerly.
Tuning 
GPS_SELL_OFFSET=-30       # SELL fires at GPS ≤ baseline - 30
GPS_DISCOVERY_OFFSET optional · +5
OverviewOffset added to GPS_BASELINE for the DISCOVERY card threshold. Set negative to put DISCOVERY below BUY (surface promising-but-unconfirmed picks). The code default of +5 puts it above BUY — usually the wrong direction; override it deliberately.
Where usedsrc/app/api/dashboard/recommendations/route.ts.
Visible onThe DISCOVERY cards on the /dashboard Recommendations strip (stocks the user doesn't own yet but the system thinks are interesting). More negative = more DISCOVERY cards surface; the default +5 means almost none ever show.
Tuning 
GPS_DISCOVERY_OFFSET=-25  # DISCOVERY fires at GPS ≥ baseline - 25
GPS_DEEPMONEY_MIN_SCORE optional · 65
OverviewRead-side GPS floor for the dashboard's DeepMoney Picks widget only. Filters which rows of recommended_stocks show in that widget. Independent from the BUY/SELL/DISCOVERY classification — a stock can clear this filter and still render as a non-BUY card.
Where usedsrc/app/api/dashboard/deepmoney-picks/route.ts.
Visible onThe dashboard's DeepMoney Picks widget only — the carousel of AI-curated stocks on /dashboard. Doesn't affect the BUY / SELL / DISCOVERY classification elsewhere on the page; it just filters which sync-persisted rows render in this specific widget.
TuningEffectively disable the widget filter (rely on the sync's own gates): 
GPS_DEEPMONEY_MIN_SCORE=4    # almost everything passes
GPS_DEEPMONEY_MIN_SCORE=65   # default: only the top tier shows
Ollama / AI Take
OLLAMA_ENABLED optional · false
OverviewMaster switch for LLM-backed features (NER extraction in the DeepMoney sync, AI Take on /search/[ticker]). Must be the exact string true to enable — anything else, including unset, disables all LLM calls. Read once at module load by isOllamaEnabled().
Where usedsrc/utils/ollamaClient.ts, scripts/deepmoney_sync.py.
Visible onThe 🤖 AI Take panel on /search/[ticker] — falls back to hidden when off (the route returns 503 and the panel removes itself). Also gates the NER pass in the nightly sync (silently no-ops when off).
Tuning 
OLLAMA_ENABLED=true
OLLAMA_BASE_URL optional · http://localhost:11434
OverviewHTTP endpoint of the Ollama server. Override when Ollama runs on a different host, port, or behind a reverse proxy.
Where usedsrc/utils/ollamaClient.ts, src/instrumentation.ts (boot-time warmup ping), scripts/deepmoney_sync.py.
Visible onBoth LLM-backed features route through this URL. Misconfigured → /api/prediction/[ticker]/ai-take returns 503 and the AI Take card hides itself; NER pass silently no-ops in the sync log.
Tuning 
OLLAMA_BASE_URL=http://gpu-box.internal:11434
OLLAMA_MODEL optional · llama3.2
OverviewDefault model for generic Ollama calls (NER extraction over article text, other short classification tasks). Feature-specific overrides (e.g. OLLAMA_MODEL_AI_TAKE) take precedence within their own feature and don't affect this default.
Where usedsrc/utils/ollamaClient.ts as the fallback in GenerateOptions.model.
Visible onThe DeepMoney sync's NER output (tickers extracted from news articles). Not consumed by AI Take, which resolves its own model via OLLAMA_MODEL_AI_TAKE.
Tuning 
OLLAMA_MODEL=llama3.2:3b
OLLAMA_TIMEOUT_MS optional · 8000 (8s)
OverviewDefault hard timeout for a single Ollama /api/generate call. Suited to short classification jobs. AI Take overrides this via AI_TAKE_TIMEOUT_MS because paragraph generation on CPU takes much longer, especially on cold-load.
Where usedsrc/utils/ollamaClient.ts.
Visible onHow long the NER pass waits per article before giving up. Raising it may reduce dropped extractions on a slow Ollama host at the cost of sync throughput.
Tuning 
OLLAMA_TIMEOUT_MS=15000     # 15s — more tolerant of slow first calls
OLLAMA_MODEL_AI_TAKE optional · gemma3:1b
OverviewFeature-local model override for the AI Take feature only. Kept independent from OLLAMA_MODEL so the NER pass can keep using a smaller/faster model. Must be a model already pulled locally (ollama pull). The chosen model name is included in the AI Take cache data_hash so swapping it forces a regeneration of every cached take. Default changed to gemma3:1b (2026-07-24) for lower RAM footprint (~1 GB vs 3.5 GB) while keeping comparable prose quality for short 60-80 word outputs.
Where usedsrc/app/api/prediction/[ticker]/ai-take/route.ts, src/instrumentation.ts (boot warmup ping preloads this exact model with keep_alive: 24h).
Visible onThe AI Take card on /search/[ticker]. Model choice affects prose quality, tone, and generation latency (8-18s warm, 12-25s cold on CPU for gemma3:1b).
Tuning 
OLLAMA_MODEL_AI_TAKE=llama3.2:3b      # comparable size, alternative prose style
OLLAMA_MODEL_AI_TAKE=gemma3:4b        # higher quality, ~3.5 GB RAM
AI_TAKE_ENABLED optional · on (unset = enabled)
OverviewKill switch for the AI Take route and its UI panel. Unset defaults to enabled. Set to off to hard-disable — the route returns 503 and the AiTakePanel component hides itself for the rest of the browser session. Also short-circuits the boot warmup ping so a disabled feature doesn't touch Ollama at all.
Where usedsrc/app/api/prediction/[ticker]/ai-take/route.ts, src/instrumentation.ts.
Visible onThe 🤖 AI Take card on /search/[ticker]. When off: card doesn't render at all.
Tuning 
AI_TAKE_ENABLED=off      # temporarily disable the whole feature
AI_TAKE_CACHE_HOURS optional · 12
OverviewTTL for cached AI Take paragraphs in the ai_ticker_takes table. Cache is also keyed on a SHA-256 of the model name + GPS + prediction + news headlines, so cache entries also invalidate on material data change — this TTL is a secondary expiry that forces periodic refresh even when data is stable.
Where usedsrc/app/api/prediction/[ticker]/ai-take/route.ts (cacheLookup).
Visible onThe 🤖 AI Take card. Higher = fewer regenerations, less CPU load; lower = fresher takes, more Ollama traffic. Users see the "Cached" state until either the TTL expires or the underlying data hash changes.
Tuning 
AI_TAKE_CACHE_HOURS=24      # halve daily regeneration traffic
AI_TAKE_RATE_LIMIT_PER_HOUR optional · 1
OverviewHow many fresh generations one user can trigger per ticker per hour. Cache hits are always free. A throttled user still gets the cached paragraph back (with a subtle "regeneration limited" italic note under it) — a 429 is only returned when there is genuinely nothing cached to fall back to.
Where usedsrc/app/api/prediction/[ticker]/ai-take/route.ts (in-memory rate bucket keyed on userId:ticker). Not backed by a DB table today — cheap enough for a single-node VPS deploy; swap to Redis when scaling out.
Visible onThe ↻ Regenerate button behavior on the AI Take card. When over budget with a cache, the paragraph doesn't error — it silently returns the cached copy with an italic footer note.
Tuning 
AI_TAKE_RATE_LIMIT_PER_HOUR=3      # allow ~3 regens/hour per ticker per user
AI_TAKE_TIMEOUT_MS optional · 120000 (120s)
OverviewHard timeout for a single AI Take generation. Sized to allow model cold-loads on CPU-only hardware, which can hit 60-90s the first time after boot or after ollama pull. Warm-model generations typically return in 10-20s.
Where usedsrc/app/api/prediction/[ticker]/ai-take/route.ts (passed as timeoutMs into generate(), overriding the default OLLAMA_TIMEOUT_MS).
Visible onThe AI Take spinner state on /search/[ticker]. If exceeded, generate() returns null and the UI shows "The AI service returned an error". Raise on resource-constrained hosts where cold-loads legitimately need more time.
Tuning 
AI_TAKE_TIMEOUT_MS=180000       # 3 min — very slow first-loads
AI_TAKE_TIMEOUT_MS=45000        # tighter — warm-only, fail fast on cold miss
Dashboard Recommendations Rotation
DASHBOARD_TENURE_ROTATION optional · on (unset = enabled)
OverviewMaster switch for tenure-based rotation of the dashboard Recommendations section. When on, stocks that have been surfaced too many days in a row get demoted so newly-discovered tickers can rise. Tenure is tracked in the dashboard_tenure table (written by deepmoney_sync.py at the end of each run). Set to off to fall back to a flat GPS-sorted feed.
Where usedsrc/app/api/dashboard/recommendations/route.ts, src/app/api/dashboard/deepmoney-picks/route.ts.
Visible onThe 💡 Recommendations section on /dashboard — non-portfolio BUY cards (watchlist / discovery / etf_holding) participate in rotation; SELL warnings and portfolio-scope cards are always kept regardless of tenure. Also affects the DeepMoney Picks search-page widget.
Tuning 
DASHBOARD_TENURE_ROTATION=off     # legacy: flat GPS sort, no rotation
DASHBOARD_TENURE_MAX_DAYS optional · 7
OverviewConsecutive days a ticker can be surfaced before rotation demotes it out of the "fresh pool". Newly-arriving stocks get a green NEW pill next to the ticker for the first 3 days. Once a ticker crosses this threshold and drops out, it goes into a DASHBOARD_TENURE_COOLDOWN_DAYS-long hold-out before it can return.
Where usedsrc/app/api/dashboard/recommendations/route.ts, src/app/api/dashboard/deepmoney-picks/route.ts.
Visible onHow long a mega-cap (NVDA, 2330.TW, SMCI) stays visible on /dashboard before rotating off. Higher = more stability, less churn; lower = feels fresher day-to-day.
Tuning 
DASHBOARD_TENURE_MAX_DAYS=14      # biweekly rotation
DASHBOARD_TENURE_COOLDOWN_DAYS optional · 5
OverviewHow long an evicted ticker stays out of the fresh pool before it becomes eligible again. Without this cooldown, a demoted mega-cap would re-qualify on the next sync and never actually rotate. Cooldown is enforced via dashboard_tenure.evicted_at.
Where usedsrc/app/api/dashboard/recommendations/route.ts, src/app/api/dashboard/deepmoney-picks/route.ts.
Visible onHow quickly a demoted stock can return to /dashboard. Higher = enforced break; lower = ticker can return sooner (approaches a no-op if you drop it to 0).
Tuning 
DASHBOARD_TENURE_COOLDOWN_DAYS=3      # shorter break
DASHBOARD_TENURE_TARGET_CARDS optional · 12
OverviewPreferred cap on rotatable BUY cards in the recommendations feed. Portfolio-scope BUYs and all SELL warnings do NOT count against this cap — they always render. Fresh pool is filled to this size ordered by GPS DESC; anything beyond is dropped.
Where usedsrc/app/api/dashboard/recommendations/route.ts, src/app/api/dashboard/deepmoney-picks/route.ts.
Visible onThe size of the rotatable card grid on /dashboard. Portfolio + SELL cards render on top; the cap only affects the discovery / watchlist / ETF-holding subset.
Tuning 
DASHBOARD_TENURE_TARGET_CARDS=8      # tighter curation
DASHBOARD_TENURE_MIN_CARDS optional · 8
OverviewSafety valve: if the fresh pool has fewer than this many stocks (e.g. rotation demoted most of the qualified set on the same day), the section is backfilled from the stale/evicted pool by GPS DESC so the user never sees an empty grid. Backfill only fires when fresh count is below this floor.
Where usedsrc/app/api/dashboard/recommendations/route.ts, src/app/api/dashboard/deepmoney-picks/route.ts.
Visible onWhether stale mega-caps briefly reappear on /dashboard when the fresh pool is thin. Lower = more tolerant of small sections; higher = stale names re-emerge more aggressively.
Tuning 
DASHBOARD_TENURE_MIN_CARDS=4      # allow smaller sections without backfill
