Database Documentation

This document provides a complete overview of the MoneyGoUp MySQL database schema, relationships, and the core business logic governing user data. Column lists are verified against the canonical schema dump at doc/moneygoup_schema.sql.

Core Business Logic

Portfolio vs. Watchlist vs. Discovery Logic

The system uses the user_stocks table to manage all stock relationships. Status is determined by a combination of is_purchased and user_confirmed:

  • Watchlist State: is_purchased = 0 AND user_confirmed = 1. The user has explicitly added this stock to their monitoring list. Shows in "My Watchlist".
  • Portfolio State: is_purchased = 1 AND user_confirmed = 1 AND shares > 0. The user owns a confirmed position.
  • Discovery State: is_purchased = 0 AND user_confirmed = 0. Stocks automatically identified by the AI engine. These generate recommendations but remain hidden from the user's primary watchlist until confirmed.
  • Closed Position: is_active = 0. Set when shares reach zero after being sold. The row is retained for history but excluded from active portfolio displays.

Authentication & Governance

User accounts are managed in the users table. Governance is enforced through registration approvals and role-based limits.

  • Approval Workflow: New users are created with approval_status = 'pending'. Only 'approved' users can establish a session. Administrators can 'reject' users with a specific reason.
  • Role-Based Limits: The system enforces quotas based on role (user, superuser, admin) for watchlist size, portfolio positions, and daily lookups. These are controlled by the role_limits configuration table.
  • Last Login: The last_login field is updated asynchronously every time a user successfully authenticates.
  • Password Reset: Users with a registered email can request a reset link via POST /api/auth/forgot-password. Tokens are stored (hashed) in password_reset_tokens and expire after 1 hour. Only approved accounts can receive reset emails.

user_investment_strategy

Per-user investment strategy preferences. Drives the gates and timeframe knobs in src/utils/strategy.ts that scale GPS thresholds, prediction-change cutoffs, beta tolerance, the DeepMoney ML validation gate, and the per-horizon column selected from user_stock_predictions (e.g. predicted_price_1w, predicted_change_pct_6m, confidence_score_1y). Read via getUserStrategy(); written via the PATCH handler in src/app/api/user/profile/route.ts. When a row is missing for a user, the resolver falls back to the default { aggressiveness: 'neutral', investment_timeframe: '1_month' }.

Note: this table is referenced throughout the application but is not present in the trimmed schema dump at doc/moneygoup_schema.sql; column list below reflects the runtime contract used by the strategy resolver and profile API.

ColumnTypeNotes
user_idINTPrimary Key. FK to users.id ON DELETE CASCADE. One row per user.
aggressivenessENUM('safe','neutral','aggressive')Default 'neutral'. Maps to confidence floor, beta cutoff, GPS gate, and env-floor multiplier in AGGRESSIVENESS_GATES.
investment_timeframeENUM('1_week','1_month','6_month','1_year')Default '1_month'. Selects which predicted_*_<sfx> column the dashboard reads from user_stock_predictions when recomputing horizon-aware GPS.
updated_atTIMESTAMPAuto-updated via ON UPDATE CURRENT_TIMESTAMP when either preference changes.
Upsert pattern: The Profile PATCH route runs an INSERT INTO user_investment_strategy (user_id, aggressiveness, investment_timeframe) VALUES (?, ?, ?) ON DUPLICATE KEY UPDATE aggressiveness = VALUES(aggressiveness), investment_timeframe = VALUES(investment_timeframe). The request body accepts either field individually (the timeframe pill UX sends only the field that changed) or both inside a { strategy: {...} } envelope (the dropdown's Save Strategy button). Missing fields are filled from the current row before the upsert so partial updates never null-out the other column.

prediction_records

Analytics + prefetch ledger of multi-horizon model predictions. Two roles: (1) source of the headline accuracy KPIs surfaced by the ModelAccuracyWidget, and (2) source of the prefetched prediction shown on /search/[ticker] when the freshest row is < 12 hours old (via GET /api/stock_data/[ticker]/latest-prediction). Written fire-and-forget by recordPrediction() in src/utils/predictionRecorder.ts (browser flow) and record_prediction() in scripts/prediction_recorder.py (batch). Actuals (actual_price_*, accuracy_pct_*, direction_correct_*, resolved_*) are populated by scripts/resolve_predictions.py after each horizon elapses.

Write pattern: Plain INSERT (no INSERT IGNORE or ON DUPLICATE KEY UPDATE) — every fresh prediction gets a new row. The browser flow writes on outlook=all external calls; the batch update_predictions.py writes via Python's record_prediction(). The [ticker] route gates its recordPrediction call on outlook=='all' && !isInternal to avoid duplicate writes when the batch (internal) calls the same route.
Read patterns:
  • GET /api/stock_data/[ticker]/latest-prediction: SELECT ... WHERE symbol = ? AND model_version = ? AND created_at >= NOW() - INTERVAL 12 HOUR ORDER BY created_at DESC LIMIT 1. Returns full prediction payload + ageMinutes, or null if none is fresh enough.
  • GET /api/analytics/model-accuracy: aggregates direction_correct_* and accuracy_pct_* across all rows. Requires ≥ 30 resolved rows summed across horizons before transitioning out of insufficient_data. Direction accuracy is the canonical headline metric.
Accuracy formulas: For each row/horizon the resolver computes accuracy_pct = MAX(0, 1 - ABS(predicted - actual) / actual) × 100. direction_correct = 1 when sign(predicted - price_at_prediction) == sign(actual - price_at_prediction).
