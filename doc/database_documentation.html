Database Documentation

This document provides a complete overview of the MoneyGoUp MySQL database schema, relationships, and the core business logic governing user data.

Core Business Logic

Portfolio vs. Watchlist vs. Discovery Logic

The system uses the user_stocks table to manage all stock relationships. Status is determined by a combination of is_purchased and user_confirmed:

  • Watchlist State: is_purchased = 0 AND user_confirmed = 1. The user has explicitly added this stock to their monitoring list. Shows in "My Watchlist".
  • Portfolio State: is_purchased = 1 AND user_confirmed = 1 AND shares > 0. The user owns a confirmed position.
  • Discovery State: is_purchased = 0 AND user_confirmed = 0. Stocks automatically identified by the AI engine. These generate recommendations but remain hidden from the user's primary watchlist until confirmed.

Authentication & Governance

User accounts are managed in the users table. Governance is enforced through registration approvals and role-based limits.

  • Approval Workflow: New users are created with approval_status = 'pending'. Only 'approved' users can establish a session. Administrators can 'reject' users with a specific reason.
  • Role-Based Limits: The system enforces quotas based on role (user, superuser, admin) for watchlist size, portfolio positions, and daily lookups. These are controlled by the role_limits configuration table.
  • Last Login: The last_login field is updated asynchronously every time a user successfully authenticates.
  • Password Reset: Users with a registered email can request a reset link via POST /api/auth/forgot-password. Tokens are stored (hashed) in password_reset_tokens and expire after 1 hour. Only approved accounts can receive reset emails.

Stores core user account data and authentication metadata. Registration requires an email address, which is used for password reset flow.

ColumnTypeNotes

password_reset_tokens

Stores single-use, time-limited tokens for the password reset flow. The raw token is sent to the user's email; only its SHA-256 hash is persisted here. Tokens expire after 1 hour.

ColumnTypeNotes
idINTPrimary Key.
user_idINTFK to users.id. The account the reset applies to.
token_hashVARCHAR(64)SHA-256 hash of the raw 32-byte hex token sent in the reset link.
expires_atDATETIMEExpiry timestamp (1 hour from creation).
used_atDATETIMENULL until consumed; set to NOW() when the POST /reset-password succeeds. Used tokens are rejected on subsequent attempts.
created_atDATETIMERow creation timestamp (auto-set by DB default).
Security note: Any existing unused tokens for a user are deleted before a new one is created, ensuring only one active reset link per user at a time.
